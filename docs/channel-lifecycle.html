Channel Lifecycle: Close, Free & Regions

Why Vela requires explicit .close() on channels instead of tying them to lexical region exit, the exact distinction between closing and freeing, and alternatives to prevent forgotten channel leaks.

Runtime Architecture Close vs. Free Leak Risk Analysis Design Alternatives

🔀 1. Closing vs. Freeing: Two Completely Different Steps

It is easy to assume ch.close() immediately calls free() on the channel — similar to freeing a region at fi. In Vela's C runtime (runtime/vela_rt.h), closing and freeing are two separate lifecycle phases on purpose:

Phase A: Closing (vela__rt__chan_close)

A coordination / half-close protocol signal ("no more writes").

  • Sets chan->closed = true under chan->lock.
  • Wakes all blocked senders, blocked receivers, and active select waiters (not_empty, not_full, vela__rt__chan_wake_waiters_locked), and schedules any attached actor so it observes closure.
  • Does NOT discard unread buffered items! Receivers can keep draining queued messages after close via receive(), <<-, or select.

Phase B: Freeing (vela__rt__chan_destroy)

Actual memory, mutex, and table-slot teardown.

  • Triggered only once the channel is both closed and empty (chan->count == 0), either inside close() if empty or by the final draining read inside recv / try_recv / select.
  • Clears the slot in vela__rt__global_chan_table and increments slot->generation so any copied int64_t handle fails lookup safely afterward (no UAF).
  • Spins briefly while in-flight pinned operations finish (chan->ops == 0), destroys mutex/condvars, and calls free(chan->buffer) and free(chan).
Key takeaway: Closing means "stop accepting sends and broadcast EOF once drained." Freeing means "all queued data is gone and zero threads still pin the struct — reclaim heap memory now." You cannot safely free a channel the instant the producer closes it if consumers are still reading buffered messages!

🧭 2. Why Regions Do Not Close or Free Channels Automatically

Vela regions close and free allocations automatically at lexical block exit. Why don't channels live inside a region r and auto-close when r ends? Because regions and channels solve opposite lifetime problems:

Property Lexical region r Concurrent Chan[T]
Thread ownership Thread-local to one active execution stack; pointers carry @r so they can never cross threads. Shared concurrently across producers, consumers, spawned actors, and select calls; Chan[T] intentionally has no @r.
Lifetime shape Strictly lexical: dies at the declaring block's fi. Dynamic & cross-scope: routinely returned from helpers, stored inside reply messages, or handed to long-lived actors.
Teardown rule Instant bulk wipe when execution leaves the block. Two-phase drain: producer closes → consumers drain remaining items → final reader destroys buffer once ops == 0.

Concrete Failure If Channels Tied to Creator's region

task start_pipeline() -> Chan[int]
    region r default
    fixed ch = chan_new<int>(8)
    fixed w = spawn Worker(ch)    ; another thread now holds ch
    <- ch                         ; if 'region r' auto-closed ch here, Worker's channel dies on return!
fi

Even inside a single function with region r, a local channel could only auto-close safely if it never escaped to another task or actor — defeating the main purpose of channels. And unlike a single-threaded File (which belongs to one region and returns FileError.NotOpen once that region exits), closing or freeing a channel mid-flight while another thread is still draining buffered items would cause lost messages or synchronization races.

This is also why Go, Rust (explicit close/drop), and Erlang do not tie channel lifetimes to lexical arenas: closing a channel is a semantic protocol decision ("the producer is done"), whereas memory reclamation waits for the last drained consumer.

⚖️ 3. Pros & Cons of Explicit .close()

Pros of Vela's Current Design Cons of Vela's Current Design
Zero handle refcount overhead: Handles are plain int64_t values packed with a slot index + generation, passed freely across threads without atomic increment/decrement traffic on every copy. Easy to leak on early returns: If a loop or server allocates per-request channels (chan_new) and exits early via <-, fail, or break without calling .close(), the C heap allocation, buffer, mutex, condvars, and table slot stay alive until process exit.
Safe double-close & stale handles: Destroying twice is a no-op, and stale copied handles fail generation lookup cleanly with zero use-after-free. Protocol deadlock if omitted: When a producer forgets .close(), consumers waiting on <<- ch or select without a timeout wait indefinitely instead of observing closed state.
Clean close + drain semantics: Buffered items remain readable after close(); only when empty does teardown free the runtime node. Manual audit burden: Every code path that creates short-lived reply channels must manually remember .close().

🔍 4. Is Forgetting .close() Actually As Problematic As It Sounds?

Honest answer: only in certain patterns — it is much less scary in Go-style long-lived pipelines, and genuinely dangerous in per-request loops.

Low Risk Long-Lived App / Worker Channels

If your program creates 3 work queues or spawns 10 actors once in main, omitting .close() when exiting usually costs almost nothing: the OS reclaims process heap memory and kernel resources immediately on exit (just as Go programs often leave immortal worker channels unclosed until shutdown).

Caveat: strict AddressSanitizer / LeakSanitizer test runs (cargo test) and library code that runs repeatedly in one process do expect channels to be closed and drained cleanly so LSan sees zero leaked allocations.

High Risk Dynamic Per-Request Channels & Shutdown Loops

In an HTTP server or actor system that calls fixed reply = chan_new<Resp>(1) on every incoming request:

  • Forgetting reply.close() on even one error branch leaks a vela__rt__chan struct, ring buffer, pthread_mutex_t, 2 pthread_cond_ts, and a slot in vela__rt__global_chan_table on every failed request.
  • Forgetting to close an input feed channel hangs consumer loops waiting on <<- ch.

🛠️ 5. Alternatives to Guarantee Channels Are Never Forgotten

If manual .close() feels too error-prone as Vela programs grow, five clean designs exist (ordered from lightest to strongest compiler guarantees):

1. Lexical defer ch.close() Best Immediate Fit

Adding a defer statement (already proposed in Future Directions) solves per-request leaks immediately without changing channel handle semantics: 

; Conceptual future syntax: closes on EVERY exit path (normal return, ?, break, fail)
task query_actor(acc: Actor[Account]) -> int ~ TimeoutError
    fixed reply = chan_new<int>(1)
    defer reply.close()
    GetBalance(reply) ->> acc
    <- <<- reply
fi

Why it works well: The developer still chooses where closing happens (no premature close when returning a channel from a factory helper), while preventing leaked reply channels on error paths.

2. Split Endpoints: Sender[T] + Receiver[T] with Auto-Drop Strongest Design

Splitting creation into paired handles (like Rust's std::sync::mpsc or crossbeam) solves both closing and freeing automatically:

  • Each Sender[T] holds an atomic sender refcount; when the final Sender[T] goes out of scope (or is explicitly dropped), the channel automatically marks itself closed = true and wakes receivers.
  • Each Receiver[T] holds a receiver refcount; when the final receiver drops (or once closed & drained), the channel frees its buffer.

Tradeoff: Requires explicit lifetime/drop destructors on channel handles and splitting one type into two (Sender[T], Receiver[T]), adding surface complexity that Vela avoided in v1.

3. Scoped Region Channels (chan_new<T>(cap) at r) Opt-In Local Channels

Only safe if the type system restricts the handle (Chan[T]@r) so it cannot escape r — meaning an actor or helper spawned inside an inner structured concurrency block that finishes before r closes could use it safely, while global/escaped threads could not. Works best paired with structured concurrency scopes.

4. Reference-Counted Handle Copies (Implicit Drop Free) GC-Like Lifecycle

Tracking how many copies of a Chan[T] handle exist across all stacks/structs and calling destroy when total handle refs hit zero prevents memory leaks even without .close().

Downside: Does not distinguish producer handles from consumer handles cleanly (a waiting consumer still holds a reference!), and adds atomic refcount updates whenever handles are copied or leave scope.

5. Debug / Guard Mode Leak Diagnostics (vela --guard) Zero Language Change

Keep current semantics in release builds, and record creation source locations (file:line) in vela__rt__global_chan_table under a guard/debug flag. At process exit, report any slots still open (channel created at server.vela:42 was never closed), turning silent leaks into instant actionable feedback.

Practical Summary Today: For global/main pipelines, keep channels explicit and call .close() during shutdown. For finite request/reply async calls, prefer rush & Commitment[T], whose handles auto-settle and clean up at scope exit with zero manual .close() bookkeeping.
