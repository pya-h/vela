Vela Web Architecture

Design, concurrency paradigms, and standard library specifications for std/web

1. Overview & Philosophy

Vela's standard web library, std/web, provides minimal yet complete building blocks for backend services, REST APIs, static file delivery, and HTTP client communications. Inspired by the ergonomics and clarity of Go's net/http and Rust's low-overhead networking, Vela combines straightforward abstractions with its own unique language capabilities:

  • Scoped Request Regions (@req): Memory allocated while processing an HTTP request lives in a dedicated per-request region. Once the response completes, the entire region is bulk-reclaimed instantly with zero garbage collection or pointer-chasing frees.
  • Typed Failure Channels (Response ~ WebError): Route handlers declare their errors explicitly using Vela's failure channel operator ~, allowing clean error propagation with the ? operator without exceptions.
  • Kind-Based Pattern Matching: HTTP methods are represented by first-class kind definitions (kind Method = GET | POST | PUT | DELETE | PATCH | HEAD | OPTIONS), allowing exhaustive compile-time checking.
  • Composable Decorator Middleware: Middleware layers wrap route handlers cleanly using Vela's wrapper syntax ($(logging), $(authenticate)).

2. Concurrency Architecture: Single Event Loop vs. Multi-Threaded Pool

Network servers face a fundamental architectural choice when orchestrating concurrent I/O: multiplexing connections onto an asynchronous event loop or distributing connections across an operating system thread pool.

Option A: Single Event Loop

Mechanism: A single coordinator thread multiplexes non-blocking socket descriptors using OS primitives (epoll on Linux, poll portability fallback).

Pros:

  • Zero Data Races: Handlers execute in a single cooperative execution thread; no locks, mutexes, or synchronization overhead needed for shared server state.
  • Minimal Footprint: Thousands of idle connections occupy only socket file descriptors and lightweight connection records (~few hundred bytes), unlike thread stacks (typically 1–8 MiB).
  • Region Safety: Seamlessly aligns with Vela's deterministic region-based memory lifecycle.

Cons:

  • A CPU-intensive handler computation can delay subsequent requests on the loop unless chunked or offloaded to background native tasks.

Option B: Multi-Threaded Pool

Mechanism: A pool of worker threads accepts connections or pulls pending requests from a shared queue.

Pros:

  • CPU Isolation: A long-running synchronous computation on one request does not stall socket readiness processing for other connections.
  • Simpler Sequential Code: Blocking socket reads can be used directly without connection state machines.

Cons:

  • Thread Overhead: High memory consumption and OS context-switching penalties under high concurrency.
  • Race Hazards: Shared caches or routing structures require synchronization locks and cross-thread memory barriers.

Vela's Decision

Vela adopts Option A (the Single Event Loop) as the core engine for std/web. Vela's design emphasizes predictability, deterministic execution, and ultra-low runtime overhead. By combining non-blocking I/O multiplexing with Vela's per-request memory regions, an HTTP server can handle thousands of concurrent connections with deterministic microsecond latency and zero lock contention.

3. Connection Lifecycle: HTTP/1.1 Keep-Alive vs. Close-Per-Request

Modern network stacks in industry-standard languages (such as Go's net/http, Node.js, and Rust's hyper / actix / axum) treat HTTP/1.1 persistent connections (Keep-Alive) as the standard default:

  • Handshake Elimination: Reusing established TCP connections avoids repeated 3-way handshakes (SYN → SYN-ACK → ACK) and TLS negotiation roundtrips.
  • TCP Slow-Start Avoidance: Established sockets maintain optimal congestion window sizes (cwnd), yielding significantly higher throughput and lower latency for bursty API traffic.
  • In-Order Sequential Processing: While keep-alive keeps the connection open, requests on that connection are processed sequentially in arrival order. HTTP/1.1 pipelining is intentionally disabled due to well-known Head-of-Line blocking and intermediate proxy bugs.

Dual-Mode Configuration in std/web

Because supporting both persistent connections and one-shot connections is straightforward in the event loop, std/web supports both paradigms with minimal complexity:

Mode Default Behavior Configuration Knob Use Case
Keep-Alive (Default) Maintains persistent socket until idle timeout or connection cap is reached server.keep_alive(true) (enabled by default) High-performance APIs, web clients, microservices, SPA backends
Close-Per-Request Sends Connection: close and terminates socket immediately after response flush server.keep_alive(false) or client header Connection: close Constrained memory targets, short-lived one-off health checks, legacy proxies

4. API Specification & Decorator-Driven Routing

Vela's two decorator modes work seamlessly with std/web to provide both declarative endpoint registration and composable request middleware with zero wiring boilerplate in main:

Declarative Endpoint Registration & Middleware

Startup decorators ($get(...), $post(...), $router.get(...)) register routes automatically at program startup before main begins. Wrapper decorators ($(auth, logged)) intercept requests at call time as per-endpoint middleware. 

include std/web { serve, get, post, text, json, Request, Response, WebError }
include middleware { authenticated, logged }

; Middleware runs on every request; $get registers route at startup
$(authenticated, logged)
$get("/api/greeting/\{name\}")
$(auth)
task handle_greeting(req: Request@r, r: region default) -> Response@r ~ WebError@r
  fixed name = req.param("name") { "world" }
  <- text_response("Hello, {name}!" at r, r)
fi

$post("/api/echo")
task handle_echo(req: Request@r, r: region default) -> Response@r ~ WebError@r
  <- text_response(req.body(), r)
fi

task main()
  ; All decorated endpoints are automatically served:
  serve("127.0.0.1:8080") { failure _ }
fi

Programmatic & Modular Routers

Applications can also instantiate explicit Router instances for modular sub-trees, mounted prefixes, or static asset directories: 

include std/web { router, Request, Response, WebError, text_response, serve }

task health_check(req: Request@r, r: region default) -> Response@r ~ WebError@r
  <- text_response("ok", r)
fi

task main()
  flex app = router()
  app.get("/health", health_check)
  app.files("/static/*", "public")

  serve("127.0.0.1:8080", app.route) { failure _ }
fi

5. Security & Path Confinement

Serving static assets via web.files(folder) applies the same strict path confinement discipline proven in Vela Studio:

  • Relative path traversal sequences (..) are rejected immediately with WebError.BadRequest.
  • Absolute path escapes are stripped and trapped.
  • Symbolic links resolving outside the root directory are refused, guaranteeing zero path traversal vulnerabilities out of the box.

6. Real-Time WebSockets (RFC 6455)

For bidirectional, low-latency streaming applications (live metrics, collaborative tools, terminal connections), std/web provides native RFC 6455 WebSockets integrated directly with Vela's region-scoped memory discipline.

Handshake & WebSocket Upgrades

Incoming HTTP/1.1 requests can be inspected and upgraded into a persistent WebSocket shape. The handshake validates Upgrade: websocket, calculates the RFC 6455 Sec-WebSocket-Accept key via SHA-1 and Base64, and returns HTTP 101 Switching Protocols: 

include std/web { router, WebSocket, WebSocketMessage, Request, Response, serve }

task main()
  flex app = router()

  ; Register a WebSocket route handler:
  app.ws("/live", task (ws: WebSocket@r, req: Request@r, r: region default)
    loop ws.is_open()
      region msg_r default
      fixed msg = ws.recv(msg_r) { failure _ break }
      match msg
      case WebSocketMessage.Text payload
        ws.send_text("Echo: {payload}" at msg_r) { failure _ break }
      case WebSocketMessage.Close code reason
        ws.close(code, "bye", msg_r) { failure _ }
        break
      case _
        ; Automatic ping/pong handling
      fi
    fi
  )

  serve("127.0.0.1:8080", app.route) { failure _ }
fi

Frame Framing, Masking & Region Discipline

  • Client-to-server masking: RFC 6455 requires all frames sent from client to server to be masked with a 4-byte key; WebSocket automatically applies and validates masks.
  • Zero-copy per-message regions: In accordance with Vela's region architecture, message payloads are allocated in the caller's active frame/message region (region msg_r default) and instantly reclaimed upon loop iteration with zero GC pauses.
  • Ping / Pong keep-alive: Heartbeat ping/pong frames are encoded and decoded natively.
