1Executive Summary from Vela's Perspective

Vela compiles readable, region-checked source code to standard ISO C11 built with gcc -O3 -march=native -s. 2Vela's Power Points vs. Weak Points

Power Points (Where Vela Shines)

  • Zero-Pause Bulk Region Reclamation: On allocation-heavy workloads (02_binary_trees), Vela beats Go's GC by 8.59x, manual C malloc/free by 2.84x, and Rust Box RAII by 2.98x, while recording the lowest Peak RSS (7.7 MB).
  • Register-Tight Scalar Compute: When operating on local float / int variables without slice indexing inside the innermost loop (01_mandelbrot), Vela achieves 175.2 ms — edging out C, Rust, Go, and Zig alike.
  • Competitive Flat Buffers & Maps: In 05_prime_sieve (120.6 ms) and 06_hashmap (82.3 ms), Vela matches C/Zig memory footprints on byte arrays and outperforms Rust's SipHash-1-3 map and Go's map on 5M integer lookups.
  • Tiny Binaries & Rapid Builds: Stripped batch executables weigh 14.1–30.2 KB (50–100x smaller than Go's 1.52 MB and 15–23x smaller than Rust's 331–395 KB), and full builds finish in 137–210 ms (vs rustc at 1.65–1.98 s).
  • Lean Standard-Library Web Server: Full std/web with HTTP parsing, routing, and per-request region cleanup hits 37,450 req/s at just 2.2 MB RSS (vs Go 29,017 req/s at 14.6 MB).

Weak Points (Where Vela Lags Today)

  • Channel Latency & OS-Thread Contention (03_concurrency): At 482.4 ms vs Go's 29.2 ms, Vela pays OS kernel futex() context switches and global table mutex locking on every single message pass.
  • Blocked SIMD Auto-Vectorization (09_matmul, 04_quicksort): Even though GCC runs with -O3 -march=native, per-iteration bounds-check and integer-overflow trap branches sit inside inner loops, preventing AVX2 vectorization (720.1 ms vs C's 148.1 ms).
  • Missing sqrt Lowering (08_nbody): Writing dist2 ** 0.5 emits software pow(dist2, 0.5) instead of hardware sqrt(dist2), paying a ~500 ms library-call penalty across 50M inner-pair iterations (677.9 ms vs Rust 141.5 ms).
  • Single-Acceptor Funnel in serve_concurrent (07_web_server): All incoming sockets route through a single poll(1, 20) acceptor loop into a bounded Chan[int] with blocking reads/drains, trailing Zig/Rust/C (~43–44k req/s) and limiting high-connection C10K concurrency.
  • Hash Map Memory Density (06_hashmap): Vela's map uses 16.1 MB Peak RSS vs Rust/Go/Zig at 8.3–8.7 MB due to larger bucket/order entries instead of dense power-of-two open-addressing control bytes.

3Root-Cause Forensics (Verified Against Source & --emit-c)

Every finding below is grounded directly in Vela's C runtime (runtime/vela_rt.h), web standard library (std/web.vela), and generated C11 inspected via ./target/release/vela --emit-c.

Why Vela Leads 02_binary_trees (93.6 ms vs 803.7 ms Go, 265.7 ms C) Architecture Advantage

In tree.vela, each iteration opens a lexical region (region pass). Building the depth-16 tree invokes vela__rt__region_alloc(), bumping a pointer inside pre-allocated 4 KB–1 MB slab chunks. Exiting the loop pass frees the chunk list in O(chunks) via vela__rt__region_free() without walking millions of individual pointers.

  • Why Go lags (803.7 ms, 17.8 MB): Every node allocates on a traced heap, activates GC write barriers, and forces concurrent mark-sweep cycles (1.930s CPU user+sys vs Vela's 0.110s).
  • Why un-arenad C & Rust lag (265.7 ms & 279.3 ms): Individual free() / recursive Drop calls must walk every node pointer back to general allocator bins.
Why 03_concurrency Takes 482.4 ms vs Go's 29.2 ms Critical Runtime Bottleneck

Inspecting runtime/vela_rt.h shows why Vela tracks OS-thread timings (C 573 ms, Rust mpsc 427 ms, Zig 437 ms) instead of Go's 29 ms:

Current Path Global chan_table.lock → seq_cst ops++ → chan->lock → pthread_cond_wait (kernel futex ~4.5µs) → seq_cst ops--
C1–C4 Goal Lock-free tagged slot (acquire/release) → Direct sudog handoff → User-space M:N fiber swap (~20 ns) → LIFO next-run slot
  1. OS Pthreads Instead of User-Space Coroutines: Tasks execute synchronously on worker pthreads (plus detached helper threads). Blocked chan_recv / chan_send calls pthread_cond_wait(), parking the OS kernel thread via Linux futex().
  2. Global Mutex + Double seq_cst Barrier per Hop: Every message pass locks vela__rt__global_chan_table.lock, bumps chan->ops with memory_order_seq_cst, locks chan->lock, copies and signals, and decrements ops with another full fence.
  3. Per-Spawn malloc/free: vela__rt__sched_submit allocates a heap task node on every spawn under the global scheduler lock.

Why 07_web_server Hits 37,450 req/s (Beats Go, ~15% Behind Zig/Rust/C) Stdlib Networking Architecture
Current Stdlib 1 Acceptor poll(1, 20) → Chan[int] + select wakeup → Blocking read + string concat → keep_alive: false + drain(5s)
W1–W3 Goal N SO_REUSEPORT listeners → Per-worker epoll/io_uring reactor → Zero-copy header views + Keep-Alive → Single writev() flush

In std/web.vela (run_concurrent_server), one central serve_accept_loop wakes via poll(1, 20), accepts every socket, and dispatches FDs over Chan[int] into 4 blocking workers with keep_alive_enabled: false and synchronous drain(). Removing that cross-thread channel funnel and combining per-worker SO_REUSEPORT with non-blocking Poll/epoll unlocks both higher peak RPS and 50,000+ concurrent keep-alive sockets in tiny RAM.

4Engineering Optimization Catalog (Concurrency, Web, Loops & Memory)

Twelve targeted improvements across Vela's C runtime, std/web, and compiler codegen. Every card preserves Vela's region isolation and safety checks without unsafe global toggles.

Track A: Concurrency & Channels (Closing the 16.5x Gap vs. Go)

C1Runtime • Medium
Lock-Free Channel Slot Table (Remove Global Mutex)

How & Why: Store channel pointers in a flat cache-aligned table indexed by handle bits with atomic generation/refcounts (memory_order_acquire/release instead of seq_cst). Removes the process-wide global_chan_table.lock bottleneck on every send/recv/select.

Est. Impact: -20% to -30% latencyZero ABA safety change
C2Runtime • Medium
Vyukov Bounded Ring Buffer + Adaptive Spin Before futex

How & Why: Replace per-channel pthread_mutex_t + 3 condition variables with an atomic slot-sequence ring buffer and brief _mm_pause() spinning (~64–128 cycles) before falling back to a single futex wake word.

Est. Impact: 2.5x–3.5x faster Token Ring482 ms → ~135 ms
C3Runtime • Major Milestone
True M:N User-Space Fibers + Work-Stealing Deques

How & Why: Run rush tasks and actors on lightweight fibers (4–8 KB stacks swapped in ~20 ns) scheduled over Chase-Lev per-core deques with slab-pooled task descriptors (no malloc per spawn). Blocked channel ops yield in user space instead of sleeping an OS thread.

Est. Impact: 10x–15x faster Token RingReaches ~28–38 ms (Go tier)
C4Runtime • Incremental
Direct Sender-to-Receiver sudog Stack Handoff

How & Why: When a waiting receiver fiber is already parked on an empty channel, the sender writes the payload directly into the waiter's destination slot and schedules it LIFO on the current core's run-next slot, skipping ring writes and deque steals.

Est. Impact: +20%–25% throughputIdeal for unbuffered / cap=1 ping-pong

Track B: Web Servers & std/web (Passing C/Rust/Zig & Unlocking C10K)

W1std/web • High ROI
SO_REUSEPORT Per-Worker Listeners

How & Why: Let each serve_concurrent worker bind and accept on its own kernel-load-balanced listening socket, deleting the central 20 ms poll() loop and Chan[int] handoff per TCP connection.

Est. Impact: +15%–22% RPS~37.4k → ~44.5k+ req/s
W2std/web + RT • C10K
Per-Worker epoll / io_uring Fiber Reactor

How & Why: Multiplex non-blocking read/write events per worker thread (reusing std/web's existing Poll architecture across N cores) instead of tying one OS thread to blocking reads and synchronous socket drains.

Est. Impact: 10x C10K scale+18%–30% under high concurrency
W3std/web • Quick Win
Zero-Copy Parser Views, Keep-Alive & writev()

How & Why: Enable HTTP/1.1 keep-alive inside serve_concurrent, slice request paths/headers in place without string concatenation copies, pre-format common headers, and flush response status + headers + body in one writev() syscall.

Est. Impact: +14% close / 3x+ keep-alive-35% request region bytes

Track C: Compiler Loop Codegen & Math (Fixing N-Body & Matmul)

L1Codegen • Quick Win
Lower x ** 0.5 to sqrt(x) + std/math.sqrt

How & Why: Detect literal exponent 0.5 on float power in src/codegen.rs and emit C sqrt((double)x) → single x86-64 sqrtsd hardware instruction instead of calling libm pow() 50M times.

Est. Impact: ~3.3x–4.0x faster N-Body678 ms → ~195 ms
L2Compiler • High Impact
Loop-Header Range & Bounds Check Hoisting

How & Why: For bounded each i in 0..n loops, verify induction range limits once in the pre-header (trapping upfront if out of bounds) and omit per-element inner traps. Immediately unlocks GCC AVX2 vectorization!

Est. Impact: 3.5x–4.5x Matmul, +25% Qsort720 ms → ~165 ms (100% safe!)
L3Codegen • Quick Win
Single-Check += & __restrict Slice Pointers

How & Why: Cache &b[i] once during compound updates instead of bounds-checking both read and write, emit __restrict on disjoint slice buffers, and tag cold trap branches __builtin_expect(..., 0).

Est. Impact: +15%–25% N-Body/MatmulEnables register FMA unrolling

Track D: Memory, Regions & Hash Maps (Boosting Existing Strengths)

M1Runtime • Medium
Power-of-Two SwissTable Control-Byte Map

How & Why: Replace modulo node tables in vela__rt__map with dense open-addressing metadata control bytes (hash & (cap - 1) masking + cache-line 16-slot group probing) so 200k integer keys pack into half the memory.

6Architectural Innovations & Strategic Route

Vela's Core Principle: Keep Safety Zero-Cost at Compile Time
Never chase benchmark numbers by disabling bounds/overflow traps globally or introducing tracing GC. As 02_binary_trees proves, lexical regions already defeat Go GC and un-arenad C/Rust by wide margins. The right path combines compile-time proof hoisting with a modern user-space fiber & epoll runtime under the unchanged Vela surface language.

Shipped Compiler Foundations: First-class bitwise operations (&, |, ^^, ~&, ~|, ~^, <<, >>, ~) with checked C11 helpers, zero-cost inlined assert/!assert statements, UB-free stepped integer ranges (start..step..end), and in-place adaptive introsort (collections.sort) have now landed in the compiler and standard library.

1. Interval & Induction Proof Hoisting (Zero-Cost Safety)

Teach src/check.rs → src/codegen.rs to emit one pre-loop guard (if (end > arr.len) trap() and i + off range check) for bounded each loops. Preserves 100% panic safety while stripping every branch out of inner loops so GCC auto-vectorizes to AVX2.

2. Region-Backed Fiber Stacks (rush + Regions Synergy)

Unlike Go (GC-scanned heap escapes) or Rust (self-referential Pin<Future> futures), every Vela rush worker already owns an isolated region that splices in O(1) into the caller's region! Allocating each fiber's 4 KB stack from a slab pool turns M:N concurrency into zero-GC green threads.

3. Zero-Copy Chan[own region] Arena Handoff

Pair linear move checks with region slab lists: transfer ownership of an entire parsed HTTP payload or AST tree across threads over a channel by moving one vela__rt__region chunk head pointer in O(1), invalidating sender bindings at compile time.

4. Cold-Trap Branch Hints & Interned Diagnostic Sites

Wrap remaining runtime trap checks in __builtin_expect(..., 0), annotate disjoint region slices with __restrict, and replace inline per-site literal strings with an interned site index table — keeping executables tiny and instruction caches hot.

Recommended 3-Phase Engineering Roadmap

Phase 1 • Immediate (1–2 Weeks)

Fix Vector Loops & Accept Path

  • Lower ** 0.5 to hardware sqrt() (L1)
  • Loop-header bounds/overflow hoisting + += single-check & __restrict (L2, L3)
  • SO_REUSEPORT listeners + zero-copy Keep-Alive / writev() (W1, W3)
  • Result: Matches C/Rust on N-Body & Matmul, hits ~50k req/s HTTP.
Phase 2 • Medium Term (3–6 Weeks)

Lock-Free Channels & Compact Maps

  • Lock-free atomic channel table replacing global mutex (C1)
  • Vyukov atomic ring buffer + adaptive spin before futex (C2)
  • SwissTable open-addressing map + stack-first region slab (M1, M2)
  • Result: ~3–4x faster channels, -45% HashMap RSS, faster Binary Trees.
Phase 3 • Architectural Milestone

Full M:N Fibers & Epoll/io_uring Reactor

  • Work-stealing user-space fibers + direct sudog handoff (C3, C4)
  • Per-worker epoll/io_uring reactor integrated with fibers (W2)
  • Result: Go-tier concurrency (~30 ms Token Ring), C/Rust compute, C10K web scale, and 20–160 KB binaries.
