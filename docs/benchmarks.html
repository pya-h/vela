1. Executive Summary from Vela's Perspective

Vela compiles readable, region-checked source code to standard C11 and builds with gcc -O3 -march=native -s. Because it carries no garbage collector and no heavy language runtime, its performance profile already looks much closer to C, Rust, and Zig than to managed languages — with two sharp architectural exceptions revealed by the 9-workload suite in benchmarks/RESULTS.html.

2. Vela's Power Points vs. Weak Points

Power Points (Where Vela Shines)

  • Zero-Pause Bulk Region Reclamation: On allocation-heavy workloads (02_binary_trees), Vela beats Go's GC by 8.59x and even beats manual C malloc`/`free by 2.84x and Rust Box RAII by 2.98x, while using the lowest Peak RSS (7.7 MB).
  • Register-Tight Scalar Compute: When operating on local float / int variables without slice indexing inside the innermost loop (01_mandelbrot), Vela achieves 175.2 ms — edging out C, Rust, Go, and Zig alike.
  • Competitive Flat Buffers & Maps: In 05_prime_sieve (120.6 ms) and 06_hashmap (82.3 ms), Vela matches C/Zig memory footprints and beats Rust's default SipHash-1-3 map and Go's map in raw lookup throughput.
  • Tiny Binaries & Rapid Builds: Stripped batch binaries weigh 14–30 KB (up to 100x smaller than Go's 1.5 MB and 15–20x smaller than Rust's 332 KB), and full compiles finish in 137–210 ms (vs rustc's 1.7–2.0 s).
  • Lean Standard-Library Web Server: Full std/web with HTTP parsing, routing, and per-request region cleanup reaches 37,450 req/s at just 2.2 MB RSS (vs Go's 29,017 req/s at 14.6 MB).

Weak Points (Where Vela Lags Today)

  • Channel Latency & OS-Thread Contention (03_concurrency): At 482.4 ms vs Go's 29.2 ms, Vela pays OS kernel futex context switches and global table mutex locking on every single message pass.
  • Blocking SIMD Auto-Vectorization (09_matmul, 04_quicksort): Even though Vela emits C compiled with GCC -O3 -march=native, runtime bounds-check and integer-overflow trap branches sit inside inner loops, preventing AVX2 vectorization (720 ms vs C's 148 ms).
  • Missing sqrt Lowering (08_nbody): Writing dist2 ** 0.5 currently emits pow(dist2, 0.5) instead of hardware sqrt(dist2), paying a ~4.2x library-call tax across 50M calls (678 ms vs Rust's 141.5 ms).
  • Web Server Single-Acceptor Handoff (07_web_server): All incoming sockets in serve_concurrent pass through a single poll(1, 20) loop into a bounded Chan[int] with blocking request reads/drains, capping throughput ~15% below direct C/Rust/Zig socket servers and limiting high-concurrency C10K scaling.
  • Hash Map Memory Density (06_hashmap): Vela's map uses 16.1 MB RSS vs Rust/Go/Zig's 8.3–8.7 MB due to larger bucket/node structures rather than compact SwissTable control-byte arrays.

3. Root-Cause Forensics (Verified Against Source & --emit-c)

Every explanation below comes directly from inspecting Vela's C runtime (runtime/vela_rt.h), web standard library (std/web.vela), and actual compiler output via vela --emit-c.

Why Vela Crushes 02_binary_trees (93.6 ms vs 803.7 ms Go) Architecture Advantage

In tree.vela, each pass creates a short-lived lexical region (region pass). Building the binary tree calls vela__rt__region_alloc(), which performs a fast pointer bump inside a pre-allocated slab page — far cheaper than glibc malloc() bin searches. At the end of the loop iteration, vela__rt__region_free(pass) discards or recycles the entire slab list in O(chunks) without walking the tree nodes.

  • Why Go loses (803.7 ms, 17.8 MB): Every node allocates on a traced heap, triggers write barriers, and forces the multi-threaded mark-sweep GC to traverse millions of live pointers repeatedly (burning 1.930s of CPU user+sys time vs Vela's 0.110s).
  • Why C & Rust lose (265.7 ms & 279.3 ms): Without a custom arena, C's free() and Rust's recursive Drop must traverse every single node pointer individually to return blocks to the general allocator.
Why 03_concurrency Takes 482.4 ms vs Go's 29.2 ms Critical Bottleneck

Inspecting runtime/vela_rt.h (lines 4430–4905) reveals why Vela matches C/Rust/Zig OS-thread timings (427–573 ms) rather than Go (29 ms):

  1. OS Pthreads, Not User-Space Coroutines: Although the runtime section is named M:N Task Scheduler & Worker Pool, tasks run synchronously on OS worker threads (plus up to 128 detached helper pthreads). When vela__rt__chan_recv or chan_send blocks, it calls pthread_cond_wait(), putting the entire OS kernel thread to sleep via Linux futex() (~4–5 µs kernel context switch per token pass).
  2. Double-Lock + seq_cst Pinning on Every Message: Every single vela__rt__chan_send and vela__rt__chan_recv calls vela__rt__chan_of(handle), which locks a process-wide global mutex (vela__rt__global_chan_table.lock), executes an atomic_fetch_add_explicit(..., memory_order_seq_cst) full barrier on chan->ops, unlocks the global lock, acquires chan->lock, copies the item and signals a condition variable, unlocks chan->lock, and finally executes another seq_cst decrement in vela__rt__chan_unpin.
  3. Per-Task malloc`/`free: vela__rt__sched_submit allocates a heap vela__rt__sched_task node for each spawned task under the global scheduler lock.
// Actual hot path on EVERY send/recv in runtime/vela_rt.h:
vela__rt__chan* chan = vela__rt__chan_of(handle); // 1. Acquires GLOBAL chan_table.lock + seq_cst++
pthread_mutex_lock(&chan->lock);                  // 2. Acquires per-channel mutex
while (chan->count == 0 && !chan->closed)
    pthread_cond_wait(&chan->not_empty, &chan->lock); // 3. Parks OS pthread in kernel futex()!
vela__rt__chan_pop_locked(chan, out_item, &drained);
pthread_mutex_unlock(&chan->lock);
vela__rt__chan_unpin(chan);                       // 4. seq_cst-- memory barrier
Why 08_nbody (677.9 ms) & 09_matmul (720.1 ms) Are ~4.8x Slower Than C/Rust Codegen / Compiler Optimization Gap

Running ./target/release/vela --emit-c immediately exposed two concrete codegen reasons inside GCC's inner loops:

  • 1. dist2 ** 0.5 Emits Software pow() Instead of sqrt(): In nbody.vela, computing Euclidean distance emitted double dist = (pow((double)dist2, (double)(0.5)));. Without -ffast-math, GCC cannot lower general pow(x, 0.5) to the 1-instruction hardware sqrtsd due to IEEE-754 signed-zero/Inf corner rules. Calling libm pow() 50 million times adds ~500 ms by itself.
  • 2. Inner-Loop Overflow & Bounds Traps Block AVX2 SIMD: In matmul.vela's 1-billion-iteration j loop, every read and write emits checked arithmetic and index helpers:
// Actual emitted C inside matmul's innermost loop (runs 1,000,000,000 times):
double* vela__place__23 = &(*vela__at__slice__float(
    c, (vela__rt__add(in_offset, j, "25:29 in task 'matmul'")), "25:18 in task 'matmul'"));
*vela__place__23 = ((*vela__place__23) + (a_val * (*vela__at__slice__float(
    b, (vela__rt__add(kn_offset, j, "25:57 in task 'matmul'")), "25:46 in task 'matmul'"))));

Every FMA executes 2 vela__rt__add_overflows checks, 2 vela__rt__index bounds traps (fprintf + abort()), and aliases c.items against b.items (no __restrict). GCC cannot vectorize a loop containing potential trapping exits on every element, turning a 4-wide AVX2 vectorized multiply-add (~148 ms in C) into scalar trap-checked code (~720 ms). Likewise, nbody's b[i].vx -= ... calls vela__rt__index(i, 5) twice per statement (write address + value read), and 04_quicksort's swap executes 4 bounds checks.

Why 07_web_server Hits 37,450 req/s vs C/Rust/Zig ~43–44k req/s (and C10K Limits) Stdlib Networking Architecture

Inspecting std/web.vela (run_concurrent_server, lines 1292–1383) explains both why Vela already beats Go (29k req/s, 14.6 MB RSS vs Vela's 37.4k req/s, 2.2 MB RSS) and where the remaining ~15% throughput + scalability bottlenecks lie:

  • Single-Acceptor Funnel Through Chan[int]: A single task (serve_accept_loop) polls the listening socket (server_sock.poll(1, 20)), calls accept, and forwards each client FD through a bounded channel (chan_new<int>(count * 4)) using a select timeout loop. Every single HTTP request incurs cross-thread channel locking + condvar signaling before a worker wakes up.
  • Blocking Worker Per Active Connection: Each worker uses blocking read_http_request (which builds header/body strings via "{chunk}{more}" concatenation on partial reads), runs dispatch_connection_request(..., keep_alive_enabled: false, ...), and calls synchronous drain(client, 5000) before closing. Under 2,000 localhost requests, the 4 threads stay busy; under 10,000+ slow or keep-alive WAN clients, 4 OS worker threads cannot multiplex idle sockets simultaneously.
  • Note: Notice std/web.vela already includes a single-threaded Poll-based run_event_loop (serve()), while multi-core serve_concurrent() does not yet combine SO_REUSEPORT with per-worker epoll/Poll event loops!

4. Engineering Improvements Catalog (Focus on Concurrency, Web & Loops)

Below is every high-impact engineering change across Vela's runtime, standard library, and C codegen—prioritizing Concurrency & Channels and Web Servers, alongside fast compiler wins that fix N-Body/Matmul and strengthen Vela's region/map advantages.

Track A: Concurrency & Channels (Closing the 16.5x Gap vs. Go)

C1Runtime / Medium Effort
Eliminate Global chan_table.lock via Lock-Free Epoch/Tagged Slots

How & Why: Store channel pointers in a flat lock-free array indexed by handle bits with atomic generation/refcount packed in an _Atomic uint64_t (acquire/release, not seq_cst). Removes the process-wide vela__rt__global_chan_table.lock acquisition on every single send/recv/select.

Est. Impact: -20% to -30% channel latency Safety: Identical generation checks
C2Runtime / Medium Effort
Lock-Free Ring Buffer + Adaptive Spin-Wait Before futex

How & Why: Replace pthread_mutex_t + 3 pthread_cond_t per channel with an atomic Vyukov bounded ring buffer and brief CPU _mm_pause() spinning (~64–128 spins) before falling back to a single futex sleep word. Prevents expensive kernel context switches on fast ping-pong hops.

Est. Impact: 2.5x–3.5x faster Token Ring Drops ~482 ms → ~135 ms
C3Runtime / Major Architecture
True User-Space M:N Fibers + Work-Stealing Deques

How & Why: Execute rush tasks on lightweight user-space stacks (4–8 KB initial stack, x86-64/ARM64 assembly swap or minicoro-style fiber switch in ~15–25 ns) scheduled across Chase-Lev per-core work-stealing deques with slab-pooled task structs (no malloc per spawn). Blocked <<- / ->> parks the fiber in user space instead of calling pthread_cond_wait.

Est. Impact: 10x–15x faster Token Ring Reaches ~30–40 ms (Go territory)
C4Runtime / Incremental
Direct Sender-to-Receiver sudog Handoff & Batching

How & Why: When a receiver fiber is already parked waiting on an empty channel, the sender copies the item directly into the receiver's stack slot and resumes it immediately on the current worker (LIFO next-slot), bypassing ring buffer writes and wakeup queue contention.

Est. Impact: +20% extra channel throughput Ideal for cap=1 / unbuffered sync

Track B: Web Servers & std/web (Passing C/Rust/Zig & Unlocking C10K)

W1std/web / High ROI
SO_REUSEPORT Per-Worker Listeners (Remove Channel Handoff)

How & Why: Let each of the 4+ serve_concurrent workers bind/accept on its own SO_REUSEPORT socket FD. Eliminates the single serve_accept_loop 20ms poll bottleneck and removes the Chan[int] + select hop for every single TCP connection.

Est. Impact: +15% to +22% RPS ~37.4k → ~44.5k+ req/s, lower P95
W2std/web + RT / High Scale
Multi-Core epoll / io_uring Event Reactor Per Worker

How & Why: Combine SO_REUSEPORT with per-worker edge-triggered epoll (or io_uring) integrated with user-space fibers or non-blocking state machines. Replaces blocking read_chunk_blocking + drain so 4 threads can hold 50,000 concurrent keep-alive sockets at minimal RAM.

Est. Impact: 10x C10K scale, +18–30% RPS Zero thread explosion on slow clients
W3std/web / Quick Win
Zero-Copy HTTP Header Views, Keep-Alive & writev() Serialization

How & Why: Turn on HTTP/1.1 keep_alive_enabled in serve_concurrent, slice request targets in place without string re-concatenation, cache static header lines, and emit response status + headers + body in one writev() syscall instead of native_socket_queue + string builder loops.

Est. Impact: +12%–25% close / 3x+ keep-alive -35% per-request region churn

Track C: Compiler Loop Codegen & Numerical Math (Fixing N-Body & Matmul)

L1Codegen / 1-Hour Fix
Lower x ** 0.5 to Hardware sqrt(x) + Add std/math.sqrt

How & Why: Detect literal exponent 0.5 in src/codegen.rs (BinaryOp::Pow on float) and emit C sqrt((double)x), compiling directly to a single x86-64 sqrtsd instruction instead of a libm pow() function call.

Est. Impact: ~3.5x–4.0x faster N-Body 678 ms → ~185 ms
L2Compiler / High Impact
Loop Range Induction Check Hoisting (Slice Bounds & Overflow)

How & Why: For bounded loops (each i in 0..n, each j in 0..n), prove 0 ≤ i < n and emit a single pre-loop guard (if (end > arr.len) trap() and i + off range check) instead of per-element vela__rt__index & vela__rt__add traps. Immediately unlocks GCC AVX2 SIMD auto-vectorization!

Est. Impact: 3.5x–4.5x Matmul, +25% Qsort 720 ms → ~165 ms (100% safe!)
L3Codegen / Quick Win
Single-Check Compound Assignment (+=) & __restrict Slice Buffers

How & Why: Evaluate b[i].vx -= val by indexing b[i] once into a local pointer rather than bounds-checking for read and write separately, and mark disjoint region-backed slice inputs __restrict so GCC keeps inner accumulators in vector registers.

Est. Impact: +15%–25% N-Body, Matmul & Qsort Unlocks full GCC register/FMA unrolling

Track D: Memory, Regions & Hash Map (Boosting Existing Power Points)

M1Runtime / Medium Effort
Power-of-Two SwissTable Map + Stack-First Small Region Slab

How & Why: Switch vela__rt__map from modulo bucket nodes to cache-dense open addressing with SIMD/bitmask control bytes (power-of-two capacity hash & (cap - 1)), and back lexical region variables with a 4 KB inline stack slab before calling malloc for larger pages.

Est. Impact: +18% HashMap, -45% Map RSS Also cuts Binary Trees & Web alloc cost

6. Safety Synergy, Extra Ideas & Vela's Strategic Route

Vela's Core Superpower: Zero-Cost Memory Isolation Meets Readable Systems Code
Do not trade Vela's safety for speed by turning off bounds/overflow checks globally or adding a garbage collector. As 02_binary_trees proves, lexical regions already beat C malloc and Rust Box. The right route is eliminating redundant checks at compile time via range/region proofs while upgrading the concurrency & networking runtime underneath the unchanged surface syntax.

Why Vela's Design Fits M:N Fibers Better Than Almost Any Language

  • Deterministic Fiber Memory Splicing: In Go, any variable captured by a goroutine can escape to the global GC heap. In Rust, async futures struggle with self-referential lifetimes and 'static + Send bounds. In Vela, every rush worker already owns an isolated worker_region that splices cleanly into the caller's region on join! Pairing per-task regions with user-space fibers means fibers execute with zero GC scanning and zero lifetime gymnastics.
  • Compiler-Driven Safety Hoisting ("Pay Zero for Proved Invariants"): Keep vela__rt__index and integer overflow traps enabled as the semantic contract, while teaching the compiler's checker/codegen to hoist proofs to loop headers (each i in 0..arr.len → 0 inner checks). You keep 100% memory & integer safety while unlocking C/Rust AVX2 speeds.
  • Compile-to-C Pragmatic Hints: Emit __builtin_expect(..., 0) (unlikely) on every remaining cold runtime trap, emit __restrict on disjoint slice buffers, and preserve a fast C compilation path (avoiding LLVM bloat so compile times stay ~150–250 ms).
  • Benchmark Suite & Hardware Counter Integration: Add optional Linux perf stat capture (cycles, instructions, L1-dcache-load-misses, context-switches) and a multi-connection C10K keep-alive stress profile to benchmarks/run.py so every compiler or runtime PR verifies both raw throughput and IPC/cache efficiency.

Recommended 3-Phase Route Forward

Phase 1 • Immediate (Days–2 Weeks)

Erase Loop & Accept Bottlenecks

  • Lower ** 0.5 to sqrt() (L1)
  • Hoist loop-header bounds/overflow checks & single-index += + __restrict (L2, L3)
  • Use SO_REUSEPORT per-worker listeners + keep-alive in std/web (W1, W3)
  • Outcome: Matches C/Rust on N-Body & Matmul, reaches ~45k+ req/s on Web Server.
Phase 2 • Medium Term (3–6 Weeks)

Lock-Free Channels & Cache Maps

  • Replace global chan_table.lock with atomic slot refcounts (C1)
  • Atomic bounded ring buffer + adaptive spin before futex (C2)
  • SwissTable open-addressing map + stack-slab small regions (M1)
  • Outcome: ~3–4x faster channels, ~45% lower HashMap RSS, faster web request parsing.
Phase 3 • Architectural Milestone

True M:N Fiber + Epoll/io_uring Runtime

  • Work-stealing user-space fibers replacing OS-thread blocking on channels (C3, C4)
  • Per-worker epoll/io_uring reactor driving fiber sockets (W2)
  • Outcome: Go-tier concurrency (~30ms Token Ring) + C/Rust-tier compute + O(1) region safety in 20–160 KB binaries.
