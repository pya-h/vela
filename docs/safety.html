Safety

Where one name can see a change made through another: what the compiler checks today, and the concerns still open.

Language Regions Library Studio Comparison Future Future (Kimi) Safety May Waste Events

In Vela a value behaves as a copy: giving it to a task, binding it to another name, or putting it in a shape never lets two names change one thing. Three features give that up on purpose, since they are how two names share one place: a reference (hold&, bind&), a pointer (^T), and a shared field. This page lists what the compiler checks about them today, and the concerns it doesn't settle yet, to come back to. Nothing here changes the language.

How to read the marks. checked is refused by the compiler today; warned builds, with a warning; by design is how the feature is meant to work, written down so it is known; open is a concern the compiler doesn't catch; later waits for a feature Vela doesn't have yet.

What the compiler checks

RuleWhat it prevents
A place a call changes is given once: two hold& parameters, or a hold& and a bind& or a plain parameter, never name one place, and nor do &xs[i] and &xs[j], which may. A method that alters the value it is called on counts as changing it. A task changing a value through one parameter while it reads it through another. See Parameters.
A large plain parameter, x: T, is read where the caller keeps it only when nothing can change it while the task runs: a local variable, or a field or an array item of one, with no later argument that calls a task. Anything else is copied first. A value given as a copy changing under the task. See Large values.
A reference names a place: never an item of a slice, which moves when the slice grows, a part taken of a value, a call's value, or a result. A reference to memory that has moved, or to a value that is gone. See References.
A pointer always points to something (a missing one is a maybe ^T), and lives in a region that outlives it. Null pointers, and pointers into memory that was freed. See Regions.
A tuple's items never change, and hold nothing that changes through a pointer, a slice, or an array. A value that looks fixed changing through another name. See Tuples.

Concerns

A reference parameter changed through a pointer open

The rule that a call gives a place it changes once compares the places written at the call. A pointer reaches a place the call doesn't write, so a task given &p^ as a bind& and p itself can change what the reference reads: 

shape Box
    v: int
fi

task f(bind& x: Box, p: ^Box@r)
    p^.v = 99
    show(x.v)                      ; 99: x is where p points
fi

task main()
    region r
    bind p = new Box(Box { v: 1 }) at r
    f(&p^, p)
fi

Two pointers that hold one address slip past the same rule, since the compiler can't tell they do: 

task two(hold& a: int, hold& b: int)
    a = 1
    b = 2
    show(a, " ", b)                ; 2 2
fi

bind q = p
two(&p^.v, &q^.v)
Why it is hard
Whether two pointers hold one address is known only when the program runs. A rule written for the compiler has to be cautious: it would refuse or warn about every call that gives a place behind a pointer together with another pointer of that type, or into the same region, most of which are fine.
Ways it could go
A warning where a call gives &p^ (or a part of it) to a reference parameter and also gives a pointer of the same type, or a place behind another pointer of it. Or, in a build for finding mistakes, a check that the two addresses differ when the call starts, trapping when they don't.

A reference to a shared field the task changes open

A shared field that changes (shared hold) is one place for the whole program, and every task can reach it by name. A task given it as a bind& reads it where it is, so its own change to the field shows through the reference: 

shape Tally
    shared hold count: int = 0
fi

task report(bind& seen: int)
    Tally.count = Tally.count + 1
    show(seen)                     ; 1, not the 0 it was given
fi

report(&Tally.count)

A plain parameter given a shared field is copied first, so it never sees the change.

Why it is hard
The change may come from a task the body calls, or one that task calls, so the compiler would have to know every shared field each task can change.
Ways it could go
The checker could learn, for each task, which shared fields it or the tasks it calls may change, and refuse a call that gives one of them to a reference parameter, as it refuses a place given twice. A shared read field, which only its shape's methods change, narrows where to look.

A reference reads the place as it is now by design

bind& y = &x can't change x, but it reads x as it is each time it is read, and x may change between two reads: 

hold x = 1
bind& y = &x
show(y)                            ; 1
x = 2
show(y)                            ; 2

That is what a reference is for, and a bind& parameter is the same inside the task. What the word promises is that the reader doesn't change the place, not that nothing does. A reader who needs the value to stay as it was keeps a copy: bind v = y, or a bind x parameter.

Where a plain parameter is warned

A plain parameter, x: T, is a copy, or for a value larger than 64 bytes, the caller's own place. Its value is the same either way, but what reads where the value is sees the difference: &x, and == on a shape, an array, or a tuple, which compare by where the value is. Such a read is a warning that says which way the compiler went; bind x and bind& x say which is meant.

Threads later

Vela has no threads, so every change above happens at a point the program's own order decides. Once two tasks can run at once, each reference, pointer, and shared field is memory two threads may change together, and the rule that a place is given once would have to hold between threads as well as within one call. Whatever Vela adds for running work at once (see Events for one idea) will need its own answer here before it is built.
