Vela Future Directions

A design notebook of weak points, safe improvements, and bold ideas for where Vela could go next.

Language Regions Studio Comparison Future

Vela is intentionally small today, but every small language has a horizon. This document collects honest weak points, practical improvements, and deeper design questions — especially around memory safety — that could shape the next version of Vela.

⚠️ Current Weak Points

These are not failures; they are the natural limits of a first compiler. Naming them is the first step toward fixing them.

Poor error locations Done

Fixed: every syntax node now carries a source span, and errors are reported as file:line:col with the offending line and a caret.

Manual memory risks Done

Fixed: new/free allowed leaks and use-after-free, just like C. Regions replaced them: memory is freed a region at a time, and pointer types name their region, so no pointer outlives its memory. Details below, and the full guide in Vela Regions.

No standard library High

Only show and scan (which reads a line of input) exist. No text operations, conversions, files, networking, or math utilities.

No module system Done

All code had to live in one file. Now a file includes another with include; there is still no way to share packages between programs. Details below.

Limited types Medium

No generics yet. Tuples ((text, int), whose items never change) are done (Tuples), and so are arrays ([int; 4]) and slices ([int]@r, which grow with xs.add(v) and shrink with xs.del(i)) are done (details below), and missing values and errors have types: maybe T and T or E, and a pointer can't be none.

No methods Medium

Behavior lives in free tasks such as area(s). All tasks in a file share one namespace, so two shapes of one file can't both have an area, and a task can only change a shape through a ^ pointer.

No concurrency Medium

No threads, channels, async, or actors. Vela is strictly single-threaded today.

Text is a C string Medium

text is currently const char*. == compares contents, but there is no length, no safe concatenation, and a \0 ends the text early. Text now has a lifetime in its type: text lasts as long as the program, text@r is in a region (Text in a region), which reading input (scan) uses, and building text will need.

Undefined integer edge cases Done

Integer overflow and division by zero behaved as in C: undefined. They now stop the program with a message, the same under every C compiler (the language guide).

One error at a time Low

The compiler stops at the first error, so fixing a file can take several rounds.

C backend dependency Low

Generating C is simple but requires a C compiler. An LLVM or native backend would be cleaner long-term.

✅ Safe & High-Impact Improvements

These changes improve Vela without radically changing its character. They are the lowest-risk next steps.

Source spans Done

Attach line/column info to every AST node so errors point to the real problem.

A complete checker Done

Block scopes, declaration order, unknown types, none, unit, and a send on every path are all checked by Vela, so mistakes no longer surface as C compiler errors.

Portable C output Done

Generated C is ISO C11, tested warning-free with gcc and clang on every test program and example, and any name that means something in C still works in Vela. (Code the C compiler finds suspicious, such as x == x, or text longer than C's 4,095-byte limit for a literal, can still draw a warning in its strictest modes.)

Vela Studio Done

A small editor for Vela with highlighting, completion, live errors, one-key run, and a terminal, built on the compiler itself. See Vela Studio.

Multiple results Done

A task sends several values, -> int, int and <- a / b, a % b, received with bind q, r = divmod(17, 5). The language guide describes it; the reasoning is below.

Named results Done

Results with names, -> total: int, set along the way with total <- value; a bare <- or the end of the task sends them. The language guide describes it; the reasoning is below.

Built-in arrays & slices Done

Arrays [int; 4] held in place, and slices [int]@r that view items in a region, with every index checked. The language guide describes them; the reasoning is below.

Real string type Idea

Replace C strings with a (ptr, len) struct and safe operations.

Regions Done

region r, new T(v) at r, and pointer types ^T@r that can't outlive their region, instead of free. Details below; ideas for making them easier to use are in Vela Regions.

Maybe & errors Done

maybe T and T or E, read with match, is, or a plan B (x { 0.0 }); pointers can no longer be none. Details below.

Pattern match expressions Idea

Let match produce a value, not just execute statements.

Module system Done

A file is a module: include shapes/geometry, then geometry.area(…), or include shapes/geometry (area), or only the names with braces; => renames a module or a name; everything is public unless marked priv. The language guide describes it; the reasoning is below.

Built-in testing Idea

A lightweight test block or assertion syntax for confidence.

Move-only pointers Idea

An own ^T@r that moves instead of being copied, so a single value can be dropped from its region early. Details.

🎁 Multiple and Named Results Done

A task used to send at most one value. A task that has two things to report, such as a quotient and a remainder, or a value and whether it was found, had to declare a shape only to carry them, or be split into two tasks that repeat the same work. Two small, related features fix that, and they came first among the language ideas because they are the cheapest: neither needs a new type, a runtime, or a change to existing programs. -> int and <- value keep their meaning.

Step 1: Multiple Results Done

Implemented; Several Results in the language guide is the reference, and what follows is the design it was built from. The return type after -> is a list of types, and <- sends one value per type:

task divmod(a: int, b: int) -> int, int
    <- a / b, a % b
fi

task main()
    bind q, r = divmod(17, 5)
    show(q)                      # 3
    show(r)                      # 2

    bind whole, _ = divmod(9, 4)  # _ skips a result
    show(whole)                  # 2
fi
  • Sending: <- a, b must list exactly as many values as the header has types, each of its type. A bare <- stayed reserved for tasks with no results, until step 2 gave it a second meaning: sending named results as they are.
  • Receiving: bind, hold, and assignment take a list of names: hold q, r = divmod(17, 5) or q, r = divmod(20, 6). Types can be written per name, bind q: int, r: int = …. _ receives a result and drops it; no Vela name can start with _, so it's free for this.
  • Results aren't one value. show(divmod(17, 5)) and bind pair = divmod(17, 5) are errors: 'divmod' sends 2 values; receive them with 'bind a, b = …'. A task with several results can only be called as the whole right side of a list. Tuples came later as a type of their own (-> (int, int) sends one tuple; see Tuples), and several results stay separate from them.
  • Regions: each result type follows today's rule, so -> ^Node@r, int needs a parameter that names r, and the results' regions are inferred at the call like a single result's.
  • Plain lists too: the same form works with ordinary values, and the right side is evaluated completely before anything is assigned, so a, b = b, a swaps two variables.
  • Generated C: results become a struct returned by value, struct vela__results__2__int__int { int64_t r0; int64_t r1; }; the call site copies its members into the new variables. One struct per list of types, not per task, so a task that sends another's values on is a plain return. No pointers, no allocation.

Step 2: Named Results Done

Implemented; Named Results in the language guide is the reference, and what follows is the design it was built from. Each result can have a name, written like a parameter: name: type. A named result is a variable of the task, and it is set with the same arrow that sends results. What stands before the arrow says what happens:

HeaderLineMeaning
-> int<- valueSend the value and end the task (today's Vela)
-> int, int<- a, bSend both values and end the task
-> total: inttotal <- valueSet the result and keep going
-> total: int<- valueSend that value and end the task
-> total: int<-Send the result as it is and end the task
-> total: intthe closing fiReaching the end sends the result

So an empty left side means "send and stop", and a name on the left means "this is the result so far":

task score(hits: int, misses: int) -> total: int
    total <- hits * 10
    when misses == 0
        <- total + 50            # a perfect round: send the bonus score and end here
    fi
    total <- total - misses * 5  # otherwise keep going
    when total < 0
        total <- 0
    fi
fi                              # reaching the end sends total

When misses isn't zero, score runs to its last line, updating total each time it reaches a total <- line, and the end sends whatever total holds. A perfect round stops at the inner <- instead, and total + 50 is sent. Setting a named result never ends the task. With several names: 

task collatz(start: int) -> steps: int, peak: int
    hold n = start
    steps, peak <- 0, start
    loop n != 1
        when n % 2 == 0
            n = n / 2
        else
            n = 3 * n + 1
        fi
        steps <- steps + 1
        when n > peak
            peak <- n
        fi
        when steps == 1000
            <-                  # give up and send what we have
        fi
    fi
fi

task main()
    bind steps, peak = collatz(27)
    show(steps)                 # 111
    show(peak)                  # 9232
fi

Named results follow Go's, with Vela's arrows and Vela's rule that every variable has a value:

GoVela
Declarefunc score(…) (total int)task score(…) -> total: int
Set and keep goingtotal = xtotal <- x
Set and endreturn x<- x
End with the current valuesreturn<-
Reach the endNot allowed: a return is requiredSends the named results
A result never setSends the zero valueCompile error

The rules:

  • All or none. Either every result has a name or none does: -> q: int, int is an error.
  • Names live in the task's scope. A result can't share a parameter's name, and the body can't declare another variable with it. After it is set, it reads like any variable: total <- total - 1.
  • Only <- changes a result. total = 0 is an error ('total' is a result; set it with 'total <- …'), and so is count <- 1 on an ordinary variable ('count' isn't a result of this task; assign it with 'count = …'). Every line that changes what a task sends starts with a result's name and an arrow, so those lines stand out when reading, and an editor can color them.
  • No zero values. Vela has no uninitialized variables, and results are no exception. The checker requires each named result to be set before it is read, and before every bare <- and the end of the task, on every path. This is the same path analysis that checks "a send on every path" today: 'peak' might not be set here. A <- values line sets them all, so it counts as a send on its path.
  • Whole values only, at first. best <- Point { x: 0.0, y: 0.0 } sets a shape result; setting one field, best.x <- 0.0, can come later if it's needed.

💡 Why the arrow, and what it costs

Setting a result with = would work too, but total <- value keeps one symbol for "this is what the task sends", with the name telling whether it stops there. It also costs the parser almost nothing:

  • Parser: the lexer already reads <- as one token. A line that starts with a name, or names separated by commas, followed by <- is a result update; an <- anywhere else in a line is still an error. That is a few tokens of lookahead in parse_stmt, the same as telling x = 1 from x + 1. The header's -> list reads names the way parameter lists already do.
  • Checker: result names join the task's scope; "set on every path" reuses the existing send-on-every-path analysis; the mid-line error for a <-1 keeps its hint to write < - when a isn't a result.
  • Generated C: named results are locals declared at the top of the function; every <- that ends the task, and the end itself, returns them (in the result shape when there are several).
  • Vela Studio: hover on a result name shows result total: int, completion at the start of a line offers total <- , and the outline shows the names in the signature. (All three are in place.)

Multiple results came first, since named results reuse their header list, send list, and C result struct; names went on top of them. What step 1 settled: a call that sends several values can only be the whole right side of a list (bind a, b = f(), a, b = f(), <- f()), and those values are taken as they are, since there is no single expression to wrap; every value of a list is computed before the first is stored, so a, b = b, a swaps; and all the tasks whose results have the same types share one C struct, whose members are r0, r1, …, so sending them on is a plain return.

What step 2 settled: a line-start name(, name)* <- is a result update, and the parser reads it without knowing the task's results, so the checker gives the message ('count' isn't a result of this task; assign it with 'count = …'); a <- anywhere else in a line is still an error with its < - hint. "Set on every path" is a walk over the body that keeps the results not yet set: a branch that leaves the task contributes nothing to the join, a loop's body sets nothing for certain since it might not run, and the same state answers reads, bare <-s, and the end of the task. A named result is a C local, zero-initialized so that a gap in that analysis would still read a defined value, and reaching the end of the task returns them. A unit or E task succeeds by reaching its end, so its result has no value to name.

📦 Modules Done

A program used to be one file. Now each file is a module, and a file includes another with include (see Modules in the language guide): 

include shapes/geometry           # shapes/geometry.vela, named geometry
include shapes/palette (Color, describe)
include fuel/prices => fuel        # another prices.vela, under another name
include shop/prices {Item => Product, price_of}   # only these names

task main()
    show(geometry.area(geometry.Square(3.0)))
    show(describe(Color.Red))         # a variant through its kind
    show(price_of(Product.Apple))
fi

# in shapes/geometry.vela
priv task pi() -> float           # only this file can call it
    <- 3.14159
fi
  • A file is a module. A folder of files as one module (Go's packages) splits a big module across files, but then no file alone says what it declares, and every name needs a search. A module path names folders with / and the file last, relative to the file with the include.
  • The word include. Vela compiles to C, and include is the word a C reader already knows for "this file needs that one". It isn't C's #include, which pastes text: the included file stays a module with names of its own, read once however many files include it. (The keyword was use at first; use and import are now errors that name include.)
  • Both m.name and include m (name). Qualified names say at every use where a name comes from and never collide; a list of names keeps code that uses a few names often short. This is the one place where Vela gives two ways to write the same thing, on purpose: a file chooses per name, and the list at the top says which. Braces list names without the module's name, for a file that wants only those.
  • Aliases with =>, and the old name gone. An alias hides the name it replaces, in that file, both Item and prices.Item, so each thing has one spelling per file and nothing needs a search to know which name is meant. The arrow points from the real name to the new one, and doesn't read as a type (:) or an assignment (=). A variant or a field can't be renamed: they are parts of a declaration, and renaming them would redefine it. Instead any variant can be written through its kind (Size.Small, shop.Size.Small), so two kinds with variants of the same name never clash, with no second kind of include.
  • Public unless priv. Most of what a file declares is meant to be used, so the rare private helper is the one marked, the reverse of Rust's pub. Fields follow the same rule, which is what lets a module keep an invariant: another file can't read, assign, or build a private field, so it goes through the module's tasks.

What building it settled. Names. Every task, shape, kind, and variant gets one name in the program: its own in the main file, and its module's path from the main file's folder with the name in any other (shapes/geometry.Point), so two util modules in different folders are two modules. (At first a module was named by the path's last part, and two utils were an error; aliases made that rule unnecessary, and the path made it wrong.) A message is spelled for the file it is in: each of the program's names in it is written as that file writes it (expected type Product, got int), or by its path when the file can't write it. In C, the . becomes __0__, each / __1__, and each .. __2__ (vela_shapes__1__geometry__0__area), none of which a Vela name can contain. Patterns. A case names a variant alone even for another module's kind, since the matched value's type says whose it is, or through its kind (case Size.Large extra), which must be the value's; case geometry.Square (a module, then a variant) is an error that says so. A kind listed in include m (…) doesn't bring its variants; they are listed on their own or written through the kind. Because Size.Small reads like a field, a variable can't be named like a kind, as it can't be named like a variant or a module. Visibility. A module sees only what it declares and includes, never the main file's names. What other files see of a public item (a task's parameters and results, a shape's public fields, a kind's values) can't mention a private type, since they couldn't name it. Errors. Include cycles, a missing file, a module included twice, two modules under one name, a module or alias named like a builtin, an alias of a variant, and a name that clashes with a name the file declares, brings in, or binds are all errors at the include or the name; a name hidden by an alias or by braces is an error that says what the file writes instead; an error in another module names that file. Studio. Vela Studio follows include lines as you type: the page gives the analysis the text of the files a program includes (an open file as edited), and the analysis says which it still needs; an error in a module is shown at the include that leads to it. The server builds a program's modules from the workspace only, so an include can't read a file outside it. Hover, completion, and highlighting follow aliases, braces, and Kind.Variant, and name things as the file does. Packages shared between programs are left for later.

🧮 Arrays and Slices Done

The first step out of the limited types; tuples came next (Tuples), and generics follow, each a step of its own. An array is a fixed number of values held in place, and a slice is a view of values in a region (see Arrays and Slices in the language guide): 

bind scores: [int; 4] = [90, 72, 85, 60]
each score in scores
    show(score)
fi
region r
bind all = new [int]([0; n]) at r     # [int]@r: n zeros, n known as the program runs
bind part = all[1..3]                 # the same memory, not a copy
part[0] = scores.len
hold names = new [text]() at r        # no items yet
names.add("b")                        # last
names.add(0, "a")                     # before item 0
show(names.del(1))                    # takes item 1 out: b
  • [type; count] and [type]. The item's type comes first, as the type is read (an array of int, four of them), rather than Go's [4]int or C's int a[4]; a slice is the same brackets without a count.
  • A slice lives in a region. In C, an array is another form of pointer, and a slice is that pointer with a length, so it follows the pointer rules: its type names its region, it is never none, and it can't outlive its region or move to another. A slice of a local array would point at the stack, so that is an error, and copying into a region is written out (new [T](xs) at r, or xs.copy() at r, which also copies what the items hold).
  • new [T](…) at r. The same form as new T(v) at r: the value in parentheses gives the items ([v; n], an array, or a slice, copied), and the result is the slice itself rather than a pointer to one. A count known only as the program runs is allowed only there, since an array's count is part of its type.
  • xs.len, not len(xs). The length reads as part of the value, costs nothing (a constant for an array, a stored count for a slice), and takes no name away from tasks.
  • A slice's length changes; an array's doesn't. First there were no growable lists: a list that grows copies itself into bigger memory, and without free every old copy stays in the region until it closes. Then (2026-09-17) the length that can change became what sets a slice apart from an array, so a slice grows and shrinks itself, with no separate list type: xs.add(v), xs.add(i, v), xs.del(i), and xs.del(), one word for each direction and the form chosen by how many arguments are given (rather than push, insert, remove, and pop). new [T]() at r makes an empty one. They read like methods, but they are built-in changes, as len is a built-in member: add takes its region from the slice's type, so nothing is passed for it.

What building it settled. Values. Arrays are copied whole, like shapes, and each goes through an array as it was when the loop started (a slice's items as they are, up to the count it had then). A literal's values join into one type: none and a value make a maybe, fail e and a value a T or E, and a literal of only none takes its type from where it goes (bind slots: [maybe int; 4] = [none; 4]). Checks. Every index and slice is checked as the program runs and stops it with a message saying where, as integer overflow does (vela: index 4 is out of range 0..4 at 7:12 in task 'main'). A constant index or bound out of range, a count below 1, and a type whose values would take more than 1 TiB are errors when compiling, the last so that every program the compiler accepts also compiles as C. Places. An array's item can be assigned where a field could be (in a hold, or behind a pointer); a slice's items can always be written, as through a pointer; neither's len can. An array behind a pointer, or an item of a slice, is in a region, so it can be sliced. C. An array is a struct holding a C array, which C can copy and return; a slice is a struct of a pointer, an int64_t length, and its room. Reading a slice's item, slicing, copying, and filling go through small generated functions, so each array or slice is evaluated once. Studio. Hover shows the types ([int; 4], [int]@r, and an each item's), and completion offers len after a . (and add and del on a slice) and types inside a type's brackets, as the file is typed.

What growing settled. Where. A change is written to the slice where it is kept, so the slice must be in a place that can be assigned (a hold variable, a field of one, anything behind a pointer, an item of another slice), and add needs the slice's region itself (declared, or an r: region parameter), as new does. Room. A slice carries a pointer to its room: a block of its region holding its items and free space after them. A full block is replaced by one twice as large, or grows in place when it ends where the region hands out memory next, so adding is amortized constant time, and a slice of n items has taken at most about 4n items of memory in its region. Only a slice whose items end where the room's free space begins adds in place, so adding to a copy or a part of a slice doesn't write over items another one counts; taking out the last item gives its space back, to the next add of that slice, even when an older copy still counts that item (as moving items in the middle is seen by the copies). Order. A change inside an expression happens in order with the rest, left to right, since xs.del() - xs.del() must mean one thing. Speed. In a test of 20 million adds (gcc -O2), one into room took about 2 nanoseconds, close to a hand-written C array; the whole run took about 5 times as long as C with realloc, because doubling copies the items into new memory that must be touched, where realloc of a large block can move pages instead. Hand-written C that doubles by copying, as regions must, took about as long as Vela.

Left for later: comparing arrays with ==, showing them whole, slices with a bound left out (xs[1..]), and making a slice with room reserved ahead for a count known in advance. A slice that never reuses the space del gives back is a lower-priority idea. When generics come, other collections whose size changes will get the same add and del.

🛟 Maybe, Plan B, and Errors Done

A value that might be missing, and a task that might fail, are the two most common sources of bugs that a type checker can rule out. C spells both with conventions (NULL, -1, errno) that nothing enforces. Vela now spells them with types, and gives three ways to get a value out, from the most explicit to the most compact. This is implemented; the language guide describes it in Maybe and Errors. This section keeps the reasoning behind the design.

maybe

maybe T holds a T or nothing. A plain value becomes one wherever a maybe is expected (a typed binding, an assignment, an argument, a field, a send), and none is the empty one. There is no Some(…) to write. 

task find(names: ^Names@r, wanted: text) -> maybe int
    …
    <- index                  # found: the int becomes a maybe int
    …
    <- none                   # not found
fi

bind x: maybe float = 2.1
hold y: maybe float = none
  • The word is maybe, never Option: the type reads as what it is, a value that is maybe there.
  • The type is a prefix, like ^: maybe int, maybe ^Node@r, ^maybe int@r. A brace form (maybe{int}) was considered and rejected: braces would mean a type argument, a pattern, a plan B, and a shape literal at once, and generics written with braces would collide with plan B in expressions.
  • A maybe can't hold another maybe, or unit.
  • A plain value never becomes a maybe in arithmetic or comparisons: m + 1 is an error that says to extract it first, and == compares a maybe only with none.
  • show(m) prints the value, or none.

No more null pointers

maybe exists to remove null mistakes, so none no longer fits a pointer type. A ^T always points to something: new already stops the program when memory runs out, every binding needs a value, and every shape literal gives every field. A pointer that may be empty is a maybe ^T, and like any maybe it must be checked before use: p^ on a maybe ^T is a compile error. 

shape Item
    title: text
    next: maybe ^Item        # the last item has no next
fi
  • A maybe ^T compiles to a plain C pointer, with NULL for none, so the safety costs nothing.
  • A shape that reaches itself only through ^ pointers could never be created (the first one would need another to exist already), so the checker rejects it and suggests maybe ^T.
  • This removes null dereferences. Freed memory and double frees were a separate question, since answered by the region model below: pointers there can't outlive their memory, and there is no free.

Getting the value out

1. match, when both outcomes need real work:

match find(names, "vela")
case {index}
    show(index)
case none
    show("not found")
fi

{index} matches a value and names it; none matches nothing; _ matches whatever the earlier cases didn't, and works for kinds too. Cases stay exhaustive.

2. is, for "only when there is one", and for walking linked structures:

when find(names, "vela") is {index}
    show(index)
fi

hold current = first
loop current is {item}
    show(item^.title)
    current = item^.next
fi

is takes the same patterns as case, including a kind's variants (when light is Dimmed level), and its names are visible only in the block it guards. It is the whole condition of a when or loop: combining it with and or or would make it unclear where the names exist, so that is an error that suggests nesting. Without is, removing null pointers would make every list walk check twice.

3. Plan B, the compact form: a block after a value runs only when there is no value, and its last line is the value to use instead.

bind y = x { 0.0 }                 # x's value, or 0.0
bind z: float = y * 5.2

bind port = config_port() {
    show("no port set, using 8080")
    8080
}

bind scaled = x { 1.0 } * 2.2      # works inside expressions

bind first = head {
    <-                             # nothing to do: leave the task
}
  • The value before the block is evaluated once. A plan B binds like . and ^, so x { 0.0 } * 2.2 and -x { 1 } mean what they look like.
  • The last line gives the value, and must have the wrapped type. A <- inside a plan B sends from the task, as anywhere else; only a line that isn't a send gives the value. When every path through the block ends in <-, no value line is needed.
  • Names declared in a plan B stay inside it. Plan Bs nest: a { b { 0 } } falls back to a second maybe.
  • An empty block is an error, except where there's no value to replace (below).

Errors: T or E

A task that can fail sends T or E: a T when it works, an E when it doesn't. The name Result was avoided because "result" already means what a task sends. 

kind ParseError
    Empty
    BadDigit(position: int)
fi

task parse(digits: text) -> int or ParseError
    when digits == ""
        <- fail Empty
    fi
    …
    <- value
fi

task main()
    bind n = parse("42") { 0 }            # the error is ignored: use 0

    bind m = parse("4x") {
        fail e                            # names the error for this block
        match e
        case Empty
            show("empty")
        case BadDigit position
            show(position)
        fi
        -1
    }

    match parse("7")
    case {value}
        show(value)
    case fail e
        show("failed")
    fi
fi
  • fail e makes an error value. It is always written, even where the types would tell, so text or text and future generic code stay unambiguous; the error type must differ from the value type anyway.
  • case fail e and is fail e match an error; case {v} a success.
  • In a plan B, a first line fail e names the error. The form { err: ErrorType was considered and rejected: after a variable, res { err: Problem } is already a shape literal, and the error's type is known anyway.
  • unit or E is a task that sends nothing when it works: a bare <-, or reaching the end, succeeds.
  • A call written as a statement can't drop an error by accident: when its or result is unused, that is an error (a variable holding one isn't checked for being used, yet); save(file) { } ignores the error on purpose.

How it fits the grammar

  • Braces: Name { followed by field: or } is a shape literal; any other brace after a value is a plan B. No statement starts with name:, so nothing is lost. If shape literals may later span lines, the check skips line breaks.
  • Sends: <- may follow { (x { <- 0 }), and } ends a bare <-. The hint for a <-1 is unaffected, since { is not a value.
  • New words: maybe, is, and fail are reserved, and _ is a symbol. In types, or separates the value type from the error type.
  • Generated C: a maybe T is a small struct { bool has; T value; } (a plain pointer for maybe ^T), and T or E is { bool ok; T value; E error; }. An expression containing a plan B is generated as statements: its operands are evaluated left to right into temporaries, and/or still skip their right side, and a loop condition runs its plan B on every pass.

💡 Next steps on top of this

  • Forwarding errors: a plan B that only sends the error on, fail e then <- fail e, will be common; a shorthand can come once real code shows its shape.
  • Match expressions can reuse plan B's rule, "the last line is the value", instead of a separate = value form per case.
  • Named results work inside plan B unchanged: total <- v updates, a bare <- ends.
  • Calling C: pointers coming from C functions should arrive as maybe ^T.
  • Dangling pointers and double free: the remaining pointer bugs, for the memory model. Done: regions.

🧠 Memory Management: The Big Question Decided

Vela's biggest open question was memory safety. There are several credible paths, each with trade-offs. Below are the main candidates.

Decided and implemented: Option B, regions, with named regions in types (^Node@r), the design sketched in the second notebook. free is gone: region r declares an arena freed when its block closes, new T(v) at r (or new@r T(v)) allocates in it, a task allocates only in a r: region parameter and can name any region its parameters' types show, and a shape holding pointers lives in one region (Node@r). The checker keeps every pointer from outliving its region. The reference is in Memory and Regions, and the long guide, with the model's limitations, workarounds, and ideas, in Vela Regions. The other options stay below, each with a note on how it could still grow the region model.

🔒 Option A: Rust-Style Borrow Checker

Track ownership, lifetimes, and borrows at compile time. Values have one owner; references are temporary and cannot outlive the data they point to.

Pros
  • Eliminates use-after-free, double-free, and data races
  • Zero runtime overhead
  • Proven at scale (Rust)
Cons
  • Massive implementation complexity
  • Steep learning curve for users
  • Fights against Vela's minimalism
Verdict: Probably too heavy for Vela. A full borrow checker would double or triple the compiler's size and change the language's feel.
With regions: a small part of it still fits. Read-only borrowed references would let younger data point at data in an older region, which regions alone can't allow (writing through such a pointer would not be safe), and let a task take a view it can't change. See Lifting today's limitations.

📦 Option B: Region / Arena Allocation

Allocate everything into a region (arena) and free the whole region at once. Objects never outlive their region. The compiler checks that references never escape their region.

Pros
  • Very fast allocation and deallocation
  • Simpler than borrowing: just region scoping
  • Excellent for compilers, games, and request handlers
Cons
  • Objects cannot live longer than their region
  • Requires discipline about region boundaries
  • Long-lived data needs special treatment
Verdict: A strong fit for Vela. It is simpler than full borrowing and aligns with the language's explicit, minimal philosophy. Chosen and implemented; see Memory and Regions.

🔄 Option C: Automatic Reference Counting (ARC)

Every shared object carries a reference count. The compiler inserts retain/release calls, or the runtime does it. Swift uses this model successfully.

Pros
  • Easier to reason about than borrowing
  • Handles shared ownership naturally
  • Deterministic destruction
Cons
  • Runtime overhead from counting
  • Reference cycles need weak references
  • Not as zero-cost as borrowing or arenas
Verdict: Viable, but it adds runtime complexity. Less "systems-y" than arenas or ownership.
With regions: counting could be kept for the few values shared across a whole program, in a region of their own, so ordinary pointers never pay for it.

➡️ Option D: Linear / Move-Only Ownership

Every value has exactly one owner. You can move it, but you cannot copy or alias it unless you explicitly clone. There are no borrows at all — only moves.

Pros
  • Much simpler than a borrow checker
  • No aliasing means no use-after-free or double-free
  • Easy to implement and explain
Cons
  • Can be awkward: reading a field consumes the whole value
  • Need explicit clone for shared read access
  • Limited compared to full borrowing
Verdict: An excellent stepping stone. Start here, then add limited borrowing later if needed.
With regions: the most natural next step. A move-only own ^T@r can be dropped early, which is the one thing regions can't do, and could move between threads. See Freeing one value early.

💡 Recommended Path for Vela

The first step, regions, is done. Growing it into a hybrid of linear ownership and regions remains the direction, where real programs show the need:

  • Owned pointers ^T could be move-only, letting a single value be freed early without dangling copies.
  • Borrowed references &T are temporary and cannot be stored. They are valid only within the current scope/region.
  • Regions (explicit arenas) group allocations and free them in bulk. References cannot escape their region. (Done, and text has regions too: text@r.) Next for them, from Vela Regions: copies into another region (done: value.copy()), moving a whole region into another, easier region passing (push[nodes](…), with inferred region arguments), shapes with several regions (and text fields of their own region), tasks that take text of any region without naming it, and fixes for the cases the rules reject today.
  • No shared mutable state by default: either you own it mutably, or you borrow it immutably.

This gives Vela a memory model that is simpler than Rust, safer than C, and more flexible than pure arenas. It also keeps the compiler small and the syntax minimal.

🧩 Methods: Behavior for Shapes and Kinds

Vela keeps data and behavior apart: shapes and kinds hold data, and tasks act on it. That separation is a good default, but today it has real costs:

  • One namespace for a file's tasks. A Circle and a Rect declared in one file can't both have a task called area; programs end up with circle_area and rect_area, and the second area is rejected with 'area' is already defined.
  • No way to change a value in place. Vela has no address-of operator, so a task can only modify a shape that was allocated with new in a region and passed as ^Point@r. A hold variable on the stack can't be updated by a helper task.
  • Nothing to discover. After p., an editor can offer fields but not the operations that belong to Point.

Whatever design Vela picks has to answer the same questions: where methods are declared, how they are called, how a method changes its receiver, how names are scoped, whether kinds get methods too, and how this leaves room for interfaces later. Below are the main candidates, each shown with the same example.

🐹 Option A: Go-Style Receiver Tasks

A task names its receiver before its own name. Methods can be declared anywhere, next to any other task. A pointer receiver lets the method change the value. 

task (p: Point) length_squared() -> float
    <- p.x * p.x + p.y * p.y
fi

task (p: ^Point@r) shift(dx: float)
    p^.x = p^.x + dx
fi

bind size = p.length_squared()
Pros
  • No new block or keyword: methods are still just tasks
  • Methods can live anywhere, and later in other modules
  • Proven and easy to explain (Go)
Cons
  • The receiver syntax task (p: Point) length_squared() is the most punctuation-heavy option
  • Pointer receivers need ^ values, or a new address-of operator that Vela avoids
  • A type's methods can be scattered across a file
Verdict: The right idea (methods are ordinary tasks attached to a type) with a syntax and a receiver model that fit Go better than Vela.

🦀 Option B: Rust-Style Implementation Blocks

A separate block gathers a type's tasks, with an explicit self whose mode says whether the method can change it. In Vela's words-first style the block could be extend Point. 

extend Point
    task origin() -> Point
        <- Point { x: 0.0, y: 0.0 }
    fi

    task length_squared(self) -> float
        <- self.x * self.x + self.y * self.y
    fi

    task shift(hold self, dx: float)
        self.x = self.x + dx
    fi
fi
Pros
  • All of a type's behavior is in one place
  • A natural home for tasks without self, such as constructors (Point.origin())
  • Extends cleanly to interfaces later (extend Point as Printable)
Cons
  • A new keyword and block kind, and one more level of fi nesting
  • A type is now described in two places: its shape and its extend
  • More machinery than a small language strictly needs
Verdict: Well organized and future-proof, but heavier than Vela needs today. Its self / hold self receiver modes are worth keeping whichever syntax wins.

🏛️ Option C: Methods Inside the Shape

Tasks are declared in the shape's own block, as in Swift structs, Kotlin, or C++ classes. Fields are in scope inside them. 

shape Point
    x: float
    y: float

    task length_squared() -> float
        <- x * x + y * y
    fi
fi
Pros
  • Maximum discoverability: data and behavior side by side
  • Short method bodies, with fields in scope
  • Familiar to most programmers
Cons
  • Shapes become classes, against Vela's "no classes and structs" philosophy
  • Implicit field scope makes it unclear whether x is a field or a variable
  • Types can't gain methods from elsewhere, such as another module
Verdict: Convenient, but it changes what a shape is. Not a good fit.

🔗 Option D: Uniform Call Syntax

No new declarations at all: p.length_squared() is simply another way to write length_squared(p), as in D and Nim. Every existing task becomes callable with a dot. 

task length_squared(p: Point) -> float
    <- p.x * p.x + p.y * p.y
fi

bind a = length_squared(p)
bind b = p.length_squared()     # the same call
Pros
  • The smallest change: only the checker learns to rewrite the call
  • Existing programs gain dot calls for free
  • Chains read left to right: list.first().title
Cons
  • Doesn't solve the shared namespace: there is still only one area
  • Solving that requires overloading by first parameter, which complicates name lookup
  • Doesn't solve changing a value in place
Verdict: Nice sugar, but it fixes the least important of the three problems.

🎯 Option E: Qualified Tasks

A task declared with its type's name in front, task Point.length_squared, belongs to that type. It reads exactly like the call, needs no new keyword or block, and takes Rust's explicit receiver modes. 

task Point.origin() -> Point
    <- Point { x: 0.0, y: 0.0 }
fi

task Point.length_squared(self) -> float
    <- self.x * self.x + self.y * self.y
fi

task Point.shift(hold self, dx: float)
    self.x = self.x + dx
fi

hold p = Point.origin()
p.shift(2.5)
show(p.length_squared())
Pros
  • Methods stay ordinary tasks; the only new syntax is Type. before the name
  • Each type gets its own namespace: Circle.area and Rect.area coexist
  • hold self changes a hold variable in place without an address-of operator
Cons
  • Like Go, a type's methods can be spread across a file (a formatter or outline can group them)
  • No block to hang interface implementations on; those need their own design
  • Needs a rule for a method and a field with the same name
Verdict: The best fit. It keeps Go's "methods are just tasks", borrows Rust's receiver modes, and reads the way it is called.

💡 Recommended Path for Vela

Adopt qualified tasks (option E), with these rules:

  • Receivers are explicit. self is an immutable copy, like any parameter; hold self may change the receiver, and its call must be on something assignable (a hold variable, one of its fields, or p^). The compiler passes that place's address in the generated C, but Vela code never sees a pointer, so it can't dangle.
  • No self means a type-level task, called as Point.origin(): constructors without a new concept.
  • Kinds get methods too: task Shape.area(self) -> float with match self inside, which replaces today's free area(s).
  • Names: a type's methods and fields share its namespace, so a method can't reuse a field name; method names don't clash with top-level tasks or with other types' methods.
  • No automatic dereference, as with fields: a method on a pointer's target is called as p^.length_squared().
  • Regions: a method of a shape that holds pointers is generic over its receiver's region, as tasks are today: task Node.length(self) -> int works on a Node@r in any region, and a method that allocates takes a region parameter. Settle this design before any region shortcut that uses a dot, such as nodes.push(list, 1) (see Easier region passing), since both would give meaning to value.name(…). A slice's built-in changes, xs.add(…) and xs.del(…), already do, and methods must keep them.
  • Generated C stays collision-free: vela_Point__method_length_squared(vela_Point self) and vela_Point__method_shift(vela_Point* self, double dx).
  • Later, interfaces can be satisfied implicitly, as in Go: a type that has the right qualified tasks fits a contract, with no extra declaration.

The work is contained: the parser accepts task Type.name and value.name(…) calls, the checker keeps a method table per type and checks receiver modes, and codegen mangles names and passes hold self by address. In Vela Studio, completion after p. would list fields and methods together.

🚀 Other Design Directions

Memory is not the only place Vela can grow. Here are ideas across the whole language.

Syntax & Ergonomics

  • Match expressions: bind area = match s case Circle r = 3.14 * r * r … fi (not ->, which names a task's result type)
  • Guards in patterns: case Circle r when r > 0.0
  • Else-if chains: when ... else when ... else ... fi
  • Inclusive ranges: 0..=10 or 0...10
  • Tuples: (int, text) as values that can be stored and passed, beyond multiple results (done: Tuples, including patterns that take them apart, when found is {(name, age)} and when pair is (x, y), and hold names in any pattern)
  • Named arguments: resize(width: 2.0, height: 3.0) for task calls, as shape literals already name their fields (Point { x: 1, y: 2 })
  • Statements end at a line break: today show(1) show(2) on one line is accepted; requiring the break, and allowing one inside ( ) and { }, would make long calls and literals splittable

Defined Behavior

  • Integer traps: overflow and division by zero stop the program with a message instead of being C's undefined behavior, identical under every C compiler (done: Numbers). Trapping won over wrapping and saturating, which would both turn the bug into a wrong number. The location in the message (vela: integer overflow at 7:15 in task 'main') costs one string per operation; the checks use the C compiler's overflow builtins where it has them. Two cases never reach the program: arithmetic written with literals only is computed by the compiler, which rejects a result that doesn't fit, and a division by a zero written that way is an error. The smallest int % -1 is 0, its exact value, rather than a trap.
  • Left-to-right evaluation: arguments and operands that call tasks are evaluated in order (codegen stores them in temporaries first), so output never depends on the C compiler. Expressions that contain a plan B already work this way; the rest would follow. (A null check on p^ is no longer needed: a pointer can't be none.)
  • Lints: warn about code that can't run (after a <- in the same block), a value compared with itself, and x = x; these fit naturally with reporting many errors at once

Type System

  • Generics: parameterize shapes, kinds, and tasks over types. Tasks are already generic over regions (list: maybe ^Node@r); a bracket syntax could hold both, task find[T, r](…) (see region brackets)
  • Type inference: let the compiler infer more types without annotations
  • Sum-type exhaustiveness: already present; keep it mandatory
  • Compile-time constants: const MaxSize: int = 1024
  • Compile-time use of tuples: a tuple's items never change, so a tuple built from constants (bind limits = (0, 100)) is itself a constant: the compiler could compute limits.1 - limits.0 when compiling, pass small tuples in registers, and share one copy of a constant tuple, with no check that it changed
  • Type conversions (casting): Vela can't convert a value from one type to another yet: not an int to a float (except where 1 + 2.5 promotes it), not a float to an int, and not text to a number or a number to text. See Type conversions below.
  • Type aliases: alias UserId = int

Type conversions (casting)

Every conversion between types is missing today, and reading input makes it pressing: scan reads text, and a program asking for a number has no way to turn "42" into 42. (The typed form scan("Age: ", int) waits for this.) The syntax is to be chosen; the questions each spelling must answer are the same: 

bind x = float(n)                  # a call named by the type
bind y = n as float                # a keyword, as in Rust and Swift
bind age = int("42")               # text to a number can fail: int or ParseError
bind shown = text(3.5) at r        # a number to text makes text, in a region
  • Which conversions. int ↔ float, bool → int, numbers ↔ text. Shapes, kinds, pointers, and slices don't convert; a task does that.
  • What can fail. Text to a number can fail ("4x2"), and so can a float to an int (nan, or 1e300, which doesn't fit). Vela's own ways apply: a T or E for input that may be wrong (int("42") gives int or ParseError), and stopping the program with a message, as integer overflow does, for a conversion that is a bug when it fails (int(1e300)).
  • Rounding. A float to an int truncates toward zero, as C does, or rounds; separate conversions (round, floor) keep that explicit.
  • Text needs memory. A number written as text is new text, so it goes in a region (text@r), written … at r as new and scan are.
  • Promotion. With conversions, 1 + 2.5 could become an error that asks for float(1) + 2.5, so that no int becomes a float quietly.

Tooling & Ecosystem

  • Package manager: simple dependency fetching and project builds
  • Formatter: consistent, opinionated code formatting
  • LSP: Vela Studio's language layer already answers completion, hover, go-to-definition, and errors; a small language server built on it would bring the same support to VS Code, Neovim, Helix, and Zed
  • Playground: the compiler's front end already runs in the browser as WebAssembly; with an interpreter or a WebAssembly back end, the docs could run every example in the page
  • Docs generator: extract docs from comments automatically
  • Test runner: built into the compiler
  • vela run file.vela: build into a temporary folder and run, with no -o and no stray executables
  • Standalone C output: --emit-c -o out.c could write vela_rt.h beside it, and VELA_CFLAGS could pass options such as -O0 -g for debugging
  • Source mapping: #line directives in the generated C, so C compiler errors and debuggers point at Vela lines, and Vela Studio could show the C a line produced
  • A stability promise: a short page saying which syntax is settled (<-, fi, bind/hold) and which may still change before 1.0

Concurrency

  • Message-passing actors: no shared mutable state by default
  • Channels: pass values between tasks (<- already sends a task's result, so channel operations would need a spelling that can't be confused with it)
  • Async/await: only if it fits the minimal philosophy
  • Data-race freedom: enforce through ownership rules from day one
  • Regions per thread: a region belongs to the thread that declared it, and handing a whole region to another thread is safe, since every pointer into it names it

Compilation Targets

  • LLVM IR: finer control over optimization and more targets, without a C compiler
  • WebAssembly: run Vela in browsers and edge environments
  • Embedded targets: bare-metal output with no runtime

Lower priority Low

Ideas kept for later, each waiting for a decision on whether Vela wants it at all, and on its syntax.

  • Slices that don't reuse taken-out space: today, taking the last item out of a slice with del gives its space back, and the next add of that slice goes there, which keeps memory use low; a copy made before the del sees the new item (see Adding and taking out items). A second kind of slice could never reuse that space and always grow into new room in its region, so no older copy ever sees another's items, at the cost of memory. That behavior stays as it is; this would be a separate kind of slice, with syntax still to be chosen.

🗺️ Suggested Roadmap

Now — Foundations Low Risk

  • Source spans and good error messages (done)
  • Complete type checking and portable C output (done)
  • Vela Studio: an editor with language support and a terminal (done: Vela Studio)
  • Multiple results, then named results (-> total: int, set with total <- value) (done: Several Results, Named Results)
  • Defined integer overflow and division by zero (done: they stop the program with a message)
  • Fixed-size arrays and slices, which grow and shrink (done: arrays and slices), and a real text type
  • Text in regions (done: text@r), reading input (done: scan), copies into another region (done: .copy()), then type conversions
  • Small region improvements: result-only regions, typed patterns, a lint for regions that grow in loops, and a chunk cache (ideas)
  • Move-only owned pointers, on top of regions
  • Basic standard library (math, strings, files)

Next — Growth Medium Risk

  • Module system (done: modules, with aliases and Kind.Variant), then a package manager
  • Methods on shapes and kinds (qualified tasks with self / hold self)
  • Tuples (done: tuples), then generics
  • Missing values and error handling (done: maybe T, plan B, T or E)
  • Pattern-match expressions
  • Region-based allocation (done: regions)
  • Region brackets with inferred region arguments (generated copies between regions: done, .copy())

Later — Ambition High Risk

  • Limited borrow checking on top of regions
  • Concurrency model (actors or channels)
  • LLVM or native backend
  • WebAssembly target
  • Self-hosting compiler

🎯 Conclusion

Vela's strength is its smallness. The best next steps preserve that smallness while filling the obvious gaps: a real string type and generics, now that arrays, slices, and tuples are in place. The memory model's first step, scoped regions, is in place (Vela Regions); move-only ownership and optional temporary borrows can grow it while keeping Vela fast, simple, and far safer than C without becoming Rust.

Beyond memory, Vela should grow carefully: methods as qualified tasks, generics, and packages built on its modules before concurrency or a self-hosted compiler. The goal is not to be everything; it is to be a small, beautiful, fast language that proves you do not need a massive toolchain to write safe systems code.

Vela — designed small, with room to grow.
