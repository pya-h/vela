What is Vela?

Vela is a small systems programming language designed to be minimal like Go, strictly typed with exhaustive matching, and expressive like modern functional languages — without the bloat. It has one clear way to do things: one kind of function, one kind of record, one kind of sum type, and memory managed through regions, without a garbage collector.

Vela compiles to C through a Rust-based compiler, so it runs anywhere C runs and inherits its performance while keeping the source language tidy and opinionated.

Philosophy

  • Minimal surface. No classes and structs. No interfaces and traits. Just shapes, kinds, and tasks.
  • One way to do it. Immutability by default with bind; mutation explicitly opt-in with hold.
  • Safe by design. Static typing, exhaustive pattern matching, no uninitialized variables, no null pointers, and pointers that can never outlive their memory.
  • Beautiful syntax. Words for control flow and logic (when, and, not), blocks closed with fi, no semicolons, and a symbol only where it reads as a picture: -> names what a task gives back, and <- gives it back.
  • No GC, no free. Values live on the stack, and new allocates in a region, which frees everything in it at once when its block closes (see Memory and Regions).

Types

  • int — 64-bit signed integer
  • float — 64-bit floating point
  • bool — true or false
  • text — UTF-8 text that knows its length, t.len, in bytes; == compares contents. text lasts as long as the program, as a literal does, and text@r is in region r (see Text in a region)
  • unit — the return type of a task that returns nothing; it has no values, so it can't be the type of a variable, parameter, or field
  • ^T@r — pointer to a T in region r; it always points to something (see Memory and Regions)
  • [T; n] — an array: n values of type T, held in place (see Arrays)
  • [T]@r — a slice: a view of values of type T in region r (see Slices)
  • (T, U) — a tuple: two or more values held together, whose items never change (see Tuples)
  • maybe T — a T, or none (see Maybe and Errors)
  • T ~ E — a T, or an error E, sent by a task that can fail; ~ holds the whole type before it, so maybe int ~ text is (maybe int) ~ text, and parentheses group the other nesting, maybe (int ~ text) (see Becoming a wider type)
  • region — the type of a task's region parameter, r: region
  • T — a type a task or shape takes, standing for the type each use gives it (see Types a declaration takes)
  • Box<int> — a shape with the types it is given, in the region its values live in when it holds anything there (Box<text>@r)
  • User-defined shapes and kinds, with methods of their own (see Methods)

Syntax Overview

Every block — a task, shape, kind, when, loop, each, or match — closes with fi. Write each statement on its own line, without a semicolon after it (a ; only separates an array's type or value from its count, as in [int; 4]). (The compiler doesn't insist on the line break yet; see Current Limits.) Files may use LF or CRLF line endings.

A statement is a binding, an assignment, a block, a send (<-), a result update (total <- value, see Named Results), a region, or a task call, which may have a plan B (see Maybe and Errors). Any other expression on its own line would do nothing, so it is an error: x == 1 alone reports the result of '==' is unused; use '=' to assign. A when and a match are blocks, and so statements, but they are also values where one is expected (see A match or a when as a value). Comments start with #.

Tasks

Functions are called tasks. -> T in the header says a task sends back a value of type T, and <- sends it: one arrow points out of the header to the result, the other brings the result back. A task that sends nothing back has no arrow in its header. 

task add(a: int, b: int) -> int
    <- a + b
fi

task greet(name: text)
    show(name)
fi

A task that returns a value must send one on every path: the compiler rejects a task that could reach its end without sending. A when counts only if both branches send, a match only if every case does, and a loop never counts, since its body might not run. A task without a return type uses a bare <- to return early. A task whose results are named sets them instead, and reaching its end sends them; the same paths are walked, to make sure each one is set (see Named Results). 

task sign(x: int) -> int
    when x < 0
        <- -1
    fi
    <- 1                 # without this line: task 'sign' can finish without sending a value
fi

task report(x: int)
    when x == 0
        <-                  # nothing to send: just leave
    fi
    show(x)
fi

A send starts its line. <- is always one symbol, so a comparison with a negative number needs a space: a < -1 compares, and a <-1 is an error. In the middle of a line the error says so — '<-' sends a value and must start a line; to compare with a negative number, write '< -' — and at the start of a line, where name <- value sets a named result, it reports that a isn't a result of the task.

Tasks can be called before they are declared, and can call themselves. Parameters are immutable, and arguments are copies, so a task can't change a shape it was given; pass a pointer to let it change the caller's value.

Every program starts at task main(), which takes no parameters and returns nothing.

Several Results

A task can send more than one value: its header lists the types after ->, and <- sends one value for each. A list of names receives them. 

task divmod(a: int, b: int) -> int, int
    <- a / b, a % b
fi

task main()
    bind q, r = divmod(17, 5)
    show(q)                      # 3
    show(r)                      # 2

    bind whole, _ = divmod(9, 4)  # _ drops a result
    show(whole)                  # 2
fi

The results are separate values, not one value, and not a tuple: show(divmod(17, 5)) and bind pair = divmod(17, 5) are errors that say 'divmod' sends 2 values; receive them with 'bind a, b = …'. A task that sends one tuple says so in its header, -> (int, int) (see Tuples). A task with several results can only be called as the whole right side of a list, which includes a <- that sends them on: 

task halves(n: int) -> int, int
    <- divmod(n, 2)         # sends both of divmod's values
fi

Each result follows the rules of a single one: -> maybe int, bool and -> ^Node@r, int work as they read, and the regions of a call's results are settled at the call (see Memory and Regions). One value can't be unit, since unit means no value at all. A value sent on from a call, as in halves above, goes as it is: it doesn't become a maybe or a T ~ E on the way, which a single sent value would, and the error says so. Results fail one at a time, not together: -> int, int ~ Bad is two results, the second of which may fail, and its receiver gives that one a plan B. A task that fails as a whole sends a single T ~ E.

bind, hold, and assignment take the same lists with plain values too, and every value is computed before the first of them is stored, so two variables can be swapped in one line: 

hold a = 1
hold b = 2
a, b = b, a                  # a is 2, b is 1
bind x: int, y: float = 3, 0.5

A name can appear once on the left of an assignment, and the names of a bind or hold must all be new, as any binding's must. A _ on the left takes a value and drops it, except a T ~ E, whose error must be handled.

Named Results

A result can have a name, written like a parameter. The name is a variable of the task, and the same arrow that sends results sets it. What stands before the arrow says what happens:

HeaderLineMeaning
-> int<- valueSend the value and end the task
-> int, int<- a, bSend both values and end the task
-> total: inttotal <- valueSet the result and keep going
-> total: int<- valueSend that value and end the task
-> total: int<-Send the results as they are and end the task
-> total: intthe closing fiReaching the end sends the results

So an empty left side means "send and stop", and a name on the left means "this is the result so far":

task score(hits: int, misses: int) -> total: int
    total <- hits * 10
    when misses == 0
        <- total + 50            # a perfect round: send the bonus score and end here
    fi
    total <- total - misses * 5  # otherwise keep going
    when total < 0
        total <- 0
    fi
fi                               # reaching the end sends total

Setting a result never ends the task. With several names, one line can set them all, and a bare <- sends what they hold: 

task collatz(start: int) -> steps: int, peak: int
    hold n = start
    steps, peak <- 0, start
    loop n != 1
        when n % 2 == 0
            n = n / 2
        else
            n = 3 * n + 1
        fi
        steps <- steps + 1
        when n > peak
            peak <- n
        fi
        when steps == 1000
            <-                  # give up and send what we have
        fi
    fi
fi

The rules:

  • All or none. Either every result has a name or none does: -> q: int, int is an error.
  • The names are the task's. A result can't share a parameter's name, and the body can't declare another variable with it. After it is set it reads like any variable, total <- total - 1.
  • Only <- changes a result. total = 0 reports 'total' is a result; set it with 'total <- …', and count <- 1 on an ordinary variable reports 'count' isn't a result of this task; assign it with 'count = …'. So every line that changes what a task sends starts with a result's name and an arrow.
  • No zero values. Vela has no uninitialized variables, and results are no exception: each must be set before it is read, before every bare <-, and before the end of the task, on every path. Reading one too early reports 'peak' might not be set here, and a path that reaches the end without setting one reports task 'collatz' can finish without setting 'peak'. A <- values line sends its own values, so nothing after it runs and nothing else need be set.
  • Whole values. best <- Point { x: 0, y: 0 } sets a shape result; setting one field of it, best.x <- 0, isn't part of this.
  • A task that sends unit ~ E succeeds by reaching its end, so its result has no value to name.

Bindings

bind creates an immutable binding. hold creates a mutable variable.

bind pi = 3.14
hold count = 0
count = count + 1
hold total: float = 0.0     # the type can be written out

Assigning copies the value. Shapes are copied whole, so after hold b = a, changing b.x leaves a alone.

A variable lives until the block that declares it closes. Vela has no shadowing: inside a task, a name cannot be declared again while another variable with that name is visible (including parameters). Separate blocks, such as the two branches of a when, may reuse a name. 

when ready
    bind label = "go"
    show(label)
else
    bind label = "wait"   # fine: a different block
    show(label)
fi
show(label)                # error: unknown variable 'label'

Numbers

Arithmetic (+ - * / %) works on int and float, on two numbers of the same type: two ints give an int, with division truncating toward zero, and two floats give a float. An int and a float don't mix, so n + 2.5 is an error that asks for float(n) + 2.5 (or n + int(2.5), which truncates); no int becomes a float quietly, as a binding (bind x: float = 3), an argument, and a field already ask for one. % on floats keeps the sign of the dividend. On ints too, % keeps the sign of the dividend (-7 % 3 is -1). Comparisons (< <= > >=) work on numbers of the same type. Number literals are decimal digits with an optional fraction (42, 3.14), and _ may separate digits (1_000_000); there are no exponent or hex forms, so 1e5 is an invalid number. An int literal can be at most 9223372036854775807, so the smallest int is written -9223372036854775807 - 1. 

show(7 / 2)              # 3, two ints
show(float(7) / 2.0)     # 3.5, two floats
show(5.5 % 2.0)          # 1.5
show(7 / 2.0)            # error: an int and a float don't mix in arithmetic …

An int never wraps around. An operation whose result doesn't fit in an int, and a division or remainder by zero, stop the program with a message saying where, on every C compiler: 

task average(total: int, count: int) -> int
    <- total / count
fi

task main()
    show(average(10, 4))     # 2
    show(average(10, 0))     # stops: vela: division by zero at 2:14 in task 'average'
fi

The one quotient that doesn't fit is the smallest int divided by -1, and -x overflows only when x is the smallest int. A remainder always fits: the smallest int % -1 is 0. Arithmetic on floats never stops the program: 1.0 / 0.0 is infinity. Arithmetic written with literals only (60 * 60 * 24) gives the same result every time, so the compiler computes it and rejects one whose result doesn't fit (integer overflow: the result, 9223372036854775808, is more than an int holds (at most 9223372036854775807)), and a division or remainder by a zero written that way, as in n / 0 (division by zero).

float(n) and int(x) turn a value into a number, called by the name of the type they give, as text(x) at r is. They make no memory, so they name no region. float(n) turns an int into a float exactly, and never fails. int(x) takes a float or a bool: a float becomes its whole part, toward zero, so it rounds neither way (int(2.9) is 2 and int(-2.9) is -2), and a bool becomes 1 or 0, which counts (int(n > 3)). A float with no whole part to give stops the program, as arithmetic that doesn't fit does: int(0.0 / 0.0) says nan cannot become an int, and a float too large to hold says inf does not fit in an int. A number turned into its own type, int(n), is the value itself. A bool reaches float through int, float(int(ok)), and rounding another way waits for conversions of its own.

Reading a number from text. int(t) and float(t) on text may fail, since the text comes from outside the program, so they send int ~ ParseError and float ~ ParseError, read with a plan B, match, or is like any error result. ParseError is a kind no program declares, with two variants and no values in them: NotANumber, when the text is no number at all, and TooLarge, when it is a number the type can't hold ("9223372036854775808" as an int). A program may send one itself, written through its kind (fail ParseError.TooLarge) or as a bare variant (fail TooLarge), and no declaration may take the three names.

The text is the number and nothing else: digits, an optional leading -, and for a float one . with digits on both sides. A space (" 4"), a +, a _ (which a written number may hold), an exponent ("1e5"), a fraction read as an int ("4.0"), and text with nothing in it are all NotANumber. Leading zeros are fine ("007" is 7). A float is read to the nearest one it can hold, from at most 400 significant digits, and one too large to hold is TooLarge; one too small is 0, as arithmetic gives.

A number read straight from input is scan(prompt, int), which sends an InputError instead, since reading input can also end. 

task main()
    region r
    show(int("42") { 0 })               # 42
    show(int("4x2") { -1 })             # -1, the plan B's value
    bind line = scan("Age: ") at r { "" }
    match int(line)
    case {age}
        show("next year: ", age + 1)
    case failure why
        match why
        case NotANumber
            show("that is no number")
        case TooLarge
            show("that number is too large")
        fi
    fi
fi
task main()
    bind n = 7
    show(float(n) / 2.0)                 # 3.5
    show(int(2.9), " ", int(-2.9))       # 2 -2
    show("over three: ", int(n > 3))    # over three: 1
    show(int(1.0 / 0.0))               # stops: vela: inf does not fit in an int at 6:10 in task 'main'
fi

Text, Output, Input, and Logic

Text literals use double quotes and support the escapes \n, \t, \r, \\, \", \0, and \{ and \} for braces, since a brace in text holds a value (see Text holding values). A # starts a comment that runs to the end of the line. A text literal ends on the line it starts (a line break in it is written \n). Text holds any UTF-8 and knows how long it is: t.len is how many bytes it has, read without counting them. A character outside ASCII takes more than one byte ("é".len is 2, "Ada".len is 3), and a \0 is a byte like any other ("ab\0cd".len is 5, and it shows all five). Floats print with up to 6 significant digits, switching to exponent form for very large or small values (123456789.0 shows as 1.23457e+08), and 0.0 / 0.0 and 1.0 / 0.0 show as nan and inf.

show takes any number of values and writes them one after another, with nothing between them, then ends the line: show("n = ", n) prints n = 5, and any space between the values is one you write. Each value is an int, a float, a bool, or text, or a maybe of one, which writes its value or none. A shape or kind with a method str of its own is a value too: show(card) writes what card.str() gives. The text that takes goes in a region show makes for the line and frees once the line ends, so printing a value of your own names no region at all; a maybe of such a shape or kind has no value to call str on until it is opened, so it is an error. show() writes an empty line. The values are written, and anything they ask for happens, left to right, so show("a:", f(), " b:", g()) calls f before g however the C compiler orders a call's arguments (see the limits). A sentence with values in the middle of it reads better as text holding values, which keeps the text to use again; show is for printing it once. 

shape Card
    name: text
    wins: int
    str(r: region) -> text@r
        <- "{.name} ({.wins})" at r
    fi
fi

task main()
    bind n = 5
    show("n = ", n)                      # n = 5
    show(n, " and ", n * 2, "!")        # 5 and 10!
    show()                                # an empty line
    bind missing: maybe int = none
    show("missing: ", missing)            # missing: none
    bind card = Card { name: "Ada", wins: 3 }
    show("top: ", card)                   # top: Ada (3), from Card's str
fi

t[a..b] is a part of text: its bytes from a up to, but not including, b. A part is the same bytes, not a copy, so it lives where the text does: a part of text is text, and a part of text@r is text@r. Its bounds are checked as a slice's are, and each must fall between two characters: "café"[0..4] would end inside the two bytes of é, so it stops the program (vela: text 0..4 cuts through a character at byte 4). Text has no items to read one at a time, so t[i] is an error; the byte at i is the part t[i..i + 1]. Text never changes, so a part can't be assigned either.

<, >, <=, and >= order text by its bytes, which is the order of Unicode: capitals come before small letters ("B" < "a"), and text that starts other text comes before it ("app" < "apple"). Text of any regions compares. 

task first_word(line: text@r) -> text@r
    hold i = 0
    loop i < line.len
        when line[i..i + 1] == " "
            <- line[0..i]              # a part: text@r, like the line
        fi
        i = i + 1
    fi
    <- line
fi

task main()
    bind name = "Ada Lovelace"
    show(name.len)                        # 12
    show(name[4..name.len])               # Lovelace
    show(first_word(name))                # Ada
    show("café".len)                      # 5: é takes two bytes
    show("café"[3..5])                   # é
    show("apple" < "banana")            # true
fi

scan(prompt) at r, or scan(prompt)@r, reads input: it shows the prompt (as it is, with no newline added; "" shows nothing), then reads one line into region r, without its line break (a Windows \r\n too). The line is new text, so it goes in a region, as new's values do (see Text in a region), and the task needs that region itself. It gives a maybe text@r: none once the input has ended (Ctrl-D, or the end of a file given as input), so reading every line is a loop … is {line}. A last line without a line break is still a line, a line can be as long as memory allows, and a \0 in it is one of its bytes. As a statement, scan("Press Enter")@r reads a line and drops it. 

task main()
    region r
    bind name = scan("Your name: ") at r { "stranger" }   # text@r; "stranger" when input has ended
    show(name)
    hold count = 0
    loop scan("")@r is {line}                              # every line left
        count = count + 1
    fi
    show(count)
fi

scan(prompt, int) and scan(prompt, float) read a number from that line instead of the line itself. A number needs no memory, so this form names no region, and it gives int ~ InputError: the number, or why there is none. InputError is a kind no file declares, with two variants — Ended, the input is over, and NoNumber, which holds the ParseError that reading the line gave (see Reading a number from text), read with a match of its own. A program reads one with a plan B, match, or is, passes on one it was given, and may send one itself (fail Ended); no declaration may take those names. 

task main()
    hold total = 0
    hold reading = true
    loop reading
        match scan("n: ", int)                # int ~ InputError; no region
        case {value}
            total = total + value
        case failure e
            match e
            case Ended                        # nothing more to read
                reading = false
            case NoNumber why                 # the line was no number
                match why
                case NotANumber
                    show("that is no number")
                case TooLarge
                    show("that does not fit in an int")
                fi
            fi
        fi
    fi
    show("total ", total)
    bind age = scan("Age: ", int) { 0 }        # a plan B where any trouble means the same
    show(age)
fi

Which form to use: scan(prompt, int) where a number is all the program wants, and scan(prompt) at r with int(line) where it also wants the line — to print what it refused, to accept "quit" beside numbers, or to read two numbers from one line. A loop that reads for a long time can keep each line in a region declared inside it, which is freed on every pass; a loop that reads numbers keeps nothing.

Logic uses words: and, or, and not work on bool, and and/or skip the right side when the left side decides the result. Conditions in when and loop must be bool: when count is an error. == and != work on numbers, bool, text (by contents), and pointers (by address); both sides must have the same type, except that pointers into different regions can be compared (they are never equal). A maybe compares only with none. <, >, <=, and >= work on numbers and text.

a + b at r joins text: new text holding the bytes of a and then of b. It is new text, so it goes in a region, as a line scan reads does, and its type is text@r. The region comes after the last part of a chain, first + " " + last at r, or after parentheses, (first + " " + last)@r; the parts may be text of any regions, or text that lasts. + on text without a region is an error that says to name one (joining text makes new text, which goes in a region …), and + joins only text: "n = " + 5 at r is an error. Text that mixes in values reads better written as text holding values, "n = {n}" at r. 

task full_name(first: text, last: text, r: region) -> text@r
    <- first + " " + last at r
fi

task main()
    region r
    bind name = full_name("Ada", "Lovelace", r)   # text@r
    show(("<" + name + ">")@r)                  # <Ada Lovelace>
    hold line = "".copy() at r
    each word in ["one", "two"]
        line = line + word + ";" at r                 # one;two; — each join is new text in r
    fi
    show(line)
    show("Ada" + "!")                           # error: joining text makes new text, which goes in a region …
fi

Each join makes new text in its region, and a region only frees memory when its block closes, so a loop that joins again and again keeps every step until then. A loop that runs long can build in a region declared inside it, and copy what it keeps out (see Copying into another region).

x.str() at r turns a value into text: new text in region r, written as show writes the value (2.5, 1e+20, true). The region can also follow as x.str()@r, or be given in the parentheses, x.str(r), and text(x) at r (or text(x)@r) is the same, named by the type the value becomes. Numbers, bools, and text have str built in; text turned into text is a copy of it in r. A shape or a kind gives its own with a method written str(r: region) -> text@r, and every one of these forms calls it, as show(x) does when it writes the value. A value without str (a slice, a maybe, a pointer, a shape without the method) is an error saying what can be turned into text, and so is a str without a region. + never turns a value into text by itself: "n = " + 5 at r is an error that says to turn it into text first. 

shape Point
    x: int
    y: int
    str(r: region) -> text@r
        <- "(" + .x.str() at r + ", " + .y.str(r) + ")" at r
    fi
fi

task main()
    region r
    show(42.str() at r)                          # 42
    show(text(2.5) at r)                         # 2.5, as show writes it
    bind p = Point { x: 3, y: -4 }
    show("p = " + p.str(r) at r)                  # p = (3, -4)
    show("p = ", p)                            # the same line, with no region to name
    show("n = " + 5 at r)                        # error: '+' joins text, but this value is int; turn it into text first …
fi

Text holding values. A value in braces inside text, "n = {n}" at r, is turned into text as n.str() does and put in its place: "{name} is {age}" at r is new text in r, so it names its region as a join does, after the text ("…" at r) or with @ ("…"@r). The braces may hold any value that has str: a name, a call with text of its own ("{f("x")}"), arithmetic, a field, a plan B, even text holding values ("{"{n}"}", which takes the region of the text around it); spaces inside them don't count. A value without str is the same error as its str would be. Text holding no value is a literal as always and needs no region, and \{ and \} write braces. In a join the text takes the join's region: "Dear " + "{name}," at r. Written without a region, it is an error that says to name one (text holding values is new text, so it names the region it goes in …); so are an unclosed {, a } alone, and empty braces, each saying how to write a brace instead. 

shape Point
    x: int
    y: int
    str(r: region) -> text@r
        <- "({.x}, {.y})" at r
    fi
fi

task main()
    region r
    bind name = "Ada"
    bind n = 3
    show("{name} has {n} cats" at r)             # Ada has 3 cats
    show("{n} * 2 = {n * 2}, big: {n > 2}"@r)     # 3 * 2 = 6, big: true
    show("at {Point { x: n, y: -n }}" at r)       # at (3, -3), from Point's str
    show("\{name\} is {name[0..1]}…" at r)          # {name} is A…
    show("n = {n}")                             # error: text holding values is new text, so it names the region it goes in …
fi
# greet the user
show("say \"hi\"")       # say "hi"
show(2.0 / 3.0)            # 0.666667
show(1 < 2 and not false)  # true
show(1 == 1.0)             # error: expected type int, got float

Shapes

Shapes group named fields, like C's structs. (Several values of one type are an array; see Arrays.)

shape Point
    x: int
    y: int
fi

bind p = Point { x: 10, y: 20 }
show(p.x)

A shape literal must give every field exactly once, in any order: Point { y: 20, x: 10 } is the same value. A shape may also have no fields (Marker {}).

A field can name the value a literal that leaves it out gives it, written after its type. It is a value the compiler works out without running the program — a number, text, true, false, none, a variant, or a tuple, an array, or a literal of those — so a literal that leaves the field out costs no more than one that writes it. The value is read where the literal is, so each value made gets its own. A literal may still write the field, and a shape whose every field names one is written Job {}. 

kind State
    Idle
    Busy
fi

shape Job
    name: text                   # every literal gives this one
    tries: int = 0
    note: maybe text = none
    state: State = State.Idle
fi

bind sweep = Job { name: "sweep" }              # tries 0, note none, state Idle
bind again = Job { name: "scrub", tries: 3 }    # what it writes, and the rest
Job { tries: 1 }                                # error: missing field 'name' in 'Job'

This is what lets a shape keep a field of its own and still be built anywhere: a priv field with no value to fall back on can only be given inside its own module, so only that module can build the shape at all, while one that names a value is left out elsewhere and starts there.

Shapes and kinds can be used before they are declared. A type cannot contain itself by value, since its values would be infinitely large, but it can point to itself. A pointer always points to something, so the pointer to the next one must be a maybe: the last node has none. (A field's pointer names no region: a shape that holds pointers lives in one, written Node@r; see Memory and Regions.) 

shape Node
    value: int
    next: maybe ^Node      # ok: a pointer that can be none
fi

shape Loop
    inner: Loop            # error: 'Loop' contains itself by value
fi

shape Chain
    next: ^Chain           # error: 'Chain' can never be created: field 'next' needs an existing ^Chain
fi

Assigning to a field requires the variable to be a hold; task parameters are immutable.

hold q = Point { x: 1, y: 2 }
q.x = 5                    # ok
p.x = 5                    # error: cannot assign to a field of immutable variable 'p'

Kinds

Kinds are tagged unions with exhaustive pattern matching. Each case binds the variant's payload fields in order; the bindings are visible only inside that case, so different cases may reuse names. A kind value has no fields of its own (s.radius is an error): match is the way to read a payload. 

kind Shape
    Circle(radius: float)
    Rectangle(width: float, height: float)
fi

task area(s: Shape) -> float
    match s
    case Circle r
        <- 3.14 * r * r
    case Rectangle w h
        <- w * h
    fi
fi

A match must have a case for every variant, each once; leaving one out is an error that names it. A last case _ covers every variant not matched above (it is an error when there are none left), and _ in place of a binding leaves that payload field unnamed. 

match s
case Rectangle w _
    show(w)
case _
    show("not a rectangle")
fi

A variant can have no payload. Write its value as just its name, with or without parentheses; its case binds nothing. 

kind Light
    Red
    Green
    Dimmed(level: int)
fi

bind a = Red
bind b = Green()          # same as Green
bind c = Dimmed(3)

A variant can also be named through its kind: Light.Red and Light.Dimmed(3) are the same values as Red and Dimmed(3), and a pattern may be written the same way, case Light.Dimmed level (the kind it names must be the value's). It is how another module's variants are named when only their kind is brought in (see Modules). Since Light.Red reads like a field, no variable can be named like a kind.

A kind can have methods too, below its variants, which read the value as .this (see Methods). A match can also be the value itself, with each case giving one (see A match or a when as a value).

Methods

A shape or a kind can have methods: tasks of its own, written inside its block, below every field or variant, with no task before them. A method is called on a value, c.total(), and reads what that value holds with a dot: .count is its field and .cap() another of its methods. A name without a dot still means a variable or a task, so a field and a variable never clash. 

shape Counter
    label: text
    count: int

    total() -> int
        <- .count
    fi

    alters step()
        .count = .count + 1
        .cap()
    fi

    priv alters cap()
        when .count > 3
            .count = 3
        fi
    fi
fi

hold c = Counter { label: "clicks", count: 0 }
c.step()
c.step()
show(c.total())            # 2

A method that changes the value it is called on says alters before its name; one that assigns a member without it is refused, with the fix named. Only a place that can change may call it: a hold variable, a field or item of one, an item of a slice, or what a pointer points to (p^.step()). The compiler gives the method that place, so the change lands where the caller keeps the value. A bind, a parameter, a result, and a value made on the spot never change: 

bind fixed = Counter { label: "once", count: 1 }
show(fixed.total())        # fine: total changes nothing
fixed.step()               # error: 'Counter.step' changes the value it is called on, so it needs a place
                           #   that can change, and 'fixed' never does (declared at 1:6); a value declared
                           #   with 'hold' can

task bump(c: Counter)
    c.step()               # error: ... and 'c' is a parameter, which never does; take a pointer to it,
fi                         #   as in 'c: ^Counter@r', and call the method on 'c^'

The whole value is .this. A kind has no fields, so its methods read .this and take it apart with match, and an alters method moves the value to another variant with .this = Other. (A shape's methods have .this too.) 

kind Light
    Red
    Green
    Blinking(times: int)

    label() -> text
        match .this
        case Red
            <- "red"
        case Green
            <- "green"
        case Blinking _
            <- "blinking"
        fi
    fi

    alters flip()
        match .this
        case Red
            .this = Green
        case _
            .this = Red
        fi
    fi

    tell(prefix: text) -> unit
        show(prefix)
        show(.label())
    fi
fi

hold light = Red
light.flip()
light.tell("now:")         # now:, then green

Inside a kind, a variant's values and a method's parameters are written alike: Blinking(times: int) and tell(prefix: text). A member is a method when it says alters, names what it sends (-> text), takes nothing (label()), or comes after another method. That leaves one case, a kind's first method that takes values and sends nothing, which writes -> unit, as tell would if it came first; the error for a method read as a variant says so.

  • Fields first. Every field or variant goes above the methods: every field of a shape goes above its methods, and method 'total' is declared at 5:5.
  • Names. A field and a method are both written .name, so they can't share a name, and neither can be called this. No method can be called add, del, copy, or len, which every value or slice already answers to. A method called str turns the value into text for x.str() at r and text(x) at r, so it is written str(r: region) -> text@r (see Values as text). A method's name clashes with nothing outside its type, so two shapes can each have a total. alters and this are not reserved words: a variable can be called either, as it can be called default (see A block's default region).
  • priv marks a method only its own file may call, as it marks a field.
  • No automatic dereference, as with fields: a method of what a pointer points to is called p^.total(). A value of a type without methods says so: type int has no methods.
  • Shapes that take types. A method of shape Box<T> uses T as its fields do, and one is made for each set of types the shape is given (see Shapes that take types). A method takes no types of its own yet (an idea for later).
  • Regions. The region the value lives in is @this, so a method can send what the value holds, nameOf() -> text@this (see Methods and regions).
  • A message or a runtime trap inside a method names it as the program writes it: in task 'Counter.step'.

Arrays

An array holds a fixed number of values of one type, written [type; count]. A literal lists the values, or repeats one: [0; 8] is eight zeros, the value computed once and copied. xs[i] is an item, counting from 0, and xs.len is how many items there are. An array is a value, like a shape: assigning or passing it copies every item, and an item can be assigned where a field could be, as in a hold. 

bind scores: [int; 4] = [90, 72, 85, 60]
show(scores[2])             # 85
show(scores.len)            # 4
hold grid = [[0; 3]; 2]     # [[int; 3]; 2]
grid[1][2] = 5
hold copy = scores          # a copy: changing it leaves scores as it was
copy[0] = 0
scores[0] = 0               # error: cannot assign to an item of immutable variable 'scores'
each score in scores
    show(score)
fi
  • Items. A literal's values have one type, except that none and a value make a maybe ([none, 7] is a [maybe int; 2]), and fail e and a value make a T ~ E. A literal of only none needs a written type, as in bind slots: [maybe text; 4] = [none; 4]. Arrays go anywhere a type does: fields, payloads, parameters, results, maybe [int; 2], and arrays of shapes (points[1].x = 4). An array holds its items by value, so a shape can't hold an array of itself, and an array of pointers lives in a region like a shape holding them ([^Node; 3]@r). An array keeps no region of its own, so the one written on it is its items' ([text; 2]@r and [text@r; 2] are one type, and so is [text@r; 2]@r); writing two different ones is an error.
  • Count. A count is at least 1 and known before the program runs: a number in a type, and a number or arithmetic on numbers ([0; 2 * 8]) in a literal. For a count known only while the program runs, make a slice in a region (see Slices). A type whose values would take more than 1 TiB of memory is an error.
  • Index. An index out of range stops the program with a message saying where, on every C compiler (vela: index 4 is out of range 0..4 at 7:12 in task 'main'); a constant index out of range is an error when compiling.
  • each. each v in xs goes through the items in order. An array is gone through as it was when the loop started, even if the loop changes it; a slice, as many items as it had then, each read as it is.
  • Not yet. Arrays can't be compared with == or shown whole (show their items one at a time), and a part of an array is a slice, which points into a region.

Tuples

A tuple holds two or more values together, each of its own type: (text, int), written as a value ("Ada", 36). t.0, t.1, … read its items by position, from 0. A tuple is a value, like a shape, and its items never change: a hold tuple takes a whole new tuple, but no item can be assigned. Names take a tuple apart, as a list of names takes a task's several results. 

task divide(a: int, b: int) -> (int, int)
    <- (a / b, a % b)
fi

task main()
    bind pair: (text, int) = ("Ada", 36)
    show(pair.0)                         # Ada
    show(pair.1)                         # 36
    hold point = (1, (2.5, "deep"))      # (int, (float, text))
    show(point.1.1)                      # deep
    point = (2, (3.5, "other"))          # a hold tuple takes a whole new tuple
    bind q, r = divide(17, 5)            # unpacks the tuple: 3 and 2
    bind (whole, left) = divide(9, 4)    # the same, in parentheses
    bind first, (half, label) = point    # a nested part, in parentheses
    hold x = 0
    hold y = 0
    x, y = divide(20, 6)                 # into hold variables of the items' types
    (y, x) = (x, y)                      # swapped
    point.0 = 5                          # error: a tuple's items never change; …
    show(pair == ("Ada", 36))            # true
fi
  • Items. Only values that can't change: numbers, bools, text, other tuples, maybe and T ~ E of those, and shapes and kinds whose fields are all such. A pointer, a slice, or an array (or a shape holding one) is an error, since what it holds could change. (x) is only parentheses, so a tuple has at least two items, and a tuple is written on one line. The same holds for types: (int) is int, which is how a type is grouped (Becoming a wider type), and () and (int,) are errors.
  • Taking apart. bind a, b = t and bind (a, b) = t declare copies of the items; a nested part is written in parentheses (bind a, (b, c) = t), a name may have a type (bind n: int, (f: float, s: text) = t), and _ drops an item. Changing a later leaves the tuple as it was. An assignment (x, y = t, (x, y) = t) writes into existing hold variables, whose types must be the items'.
  • Several results are not a tuple. -> int, int sends two values, and -> (int, int) one tuple: bind qr = divmod(17, 5) stays an error for the first, and <- a, b is an error for the second, which says to write <- (a, b). Values received from several results can be put in a tuple: bind qr = (q, r).
  • Regions. An item of text names its own region, (int, text@r), or the tuple names one for all of them, (int, text)@r; the same one written on both is the same type, and a different one is an error. Two items may be text of two regions, (text@r, text@s). In a field, a slice, or after new, items name none: they are in that value's region.
  • Comparing. == and != compare item by item (text by its characters) when every item is a number, a bool, text, or a tuple of them. < and the other order comparisons are for numbers, so compare items (t.0 < u.0). show takes one item at a time.
  • Where they go. Anywhere a type does: parameters, results, fields, payloads, arrays and slices ([(text, int)]@r, whose items are replaced whole, xs[i] = ("Cy", 80)), maybe, and after new.
  • Patterns. In is and case, braces take the value out of a maybe or a T ~ E and parentheses take a tuple apart, so when found is {(name, age)} does both, as do case {(a, b)} and case failure (line, message). A plain tuple has no other case, so when t is (x, y) always matches: its block runs with the items named, so a <- in it sends for certain, and an else on it, a loop of it, or a match on a tuple, is an error that says to use bind. hold before a name makes it a variable the block can assign (is hold (x, y), {hold v}, case Circle hold r); assigning it leaves the value matched as it was.

Types a declaration takes

A task can take types as well as values: task first<T>(xs: [T]@r) -> maybe T works for a slice of anything. The names in < > after the task's name are the types it takes, and T in its header and body means the type each call gives it. The body is checked once, with T standing for that type, and the compiler then makes one task for each set of types the program uses it with, so a call costs nothing more than an ordinary one. A shape takes types the same way (Shapes that take types); a kind can't yet.

A word after a type's : says what every type given for it must allow, and so what the body may do with its values. Without a word, values of that type can only be stored, passed, and sent.

WordWhat the body may doTypes that fit
fixedput a value in a tuple, whose items never changenumbers, bools, text, tuples of them, and shapes and kinds whose fields are all such
same== and !=numbers, bools, text, and tuples of them
shownshownumbers, bools, and text
ordered<, >, <=, >=numbers and text

Each word allows everything the words above it do, since fewer types have an order than can be shown, fewer can be shown than compared, and fewer can be compared than never change: <T: ordered> may compare and show its values too. & joins words (<T: same & shown>), which is read today but never needed yet: every pair of these four is an error saying which one to keep, since each already means the wider ones. It is there for words that may come. No word asks a type for arithmetic: a task that adds its values takes numbers. shown allows the types show writes by itself; a shape or kind with its own str can be shown, but doesn't fit shown yet, so a task that prints one takes it by its own type. 

task first<T>(xs: [T]@r) -> maybe T
    each v in xs
        <- v
    fi
    <- none
fi

task biggest<T: ordered>(a: T, b: T) -> T
    when a > b
        <- a
    fi
    <- b
fi

task nothing<T>() -> maybe T
    <- none
fi

task main()
    region r
    bind ns: [int]@r = new [int]([4, 5]) at r
    hold names: [text@r]@r = new [text]() at r
    names.add("Ada".copy() at r)
    show(first(ns))                      # 4 — the argument says T is int
    show(first<text@r>(names))            # Ada — or the call writes it out
    show(biggest(2, 5))                   # 5
    show(biggest(1.5, 0.5))               # 1.5 — the same task, made for float too
    bind empty: maybe int = nothing()    # the place the value goes says T is int
    bind fallback: text = nothing() { "none" }
    show(biggest("fig", "pear"))          # pear — text has an order too
    show(biggest(true, false))            # error: task 'biggest' takes a type that is 'ordered' …
fi
  • Which type a call is for. From its arguments, from the place its value goes (a binding's written type, a parameter, a field, a <-, or a plan B's value), or written in < > after the name, as in the header. Writing them is all or nothing: a task that takes two types is given both. When nothing says which type it is, the compiler asks for it: can't tell which type 'T' is for this call of 'nothing' ….
  • Reading <. A < after a name starts the types of a call only when the matching > is followed by (, so a < b is still a comparison. (a < b > (c) was never valid Vela: > doesn't compare bools.)
  • Regions. A type a task takes names no region of its own: what a T holds is in the region of the type given for it, so T@r is an error. A slice or pointer around it names one as usual ([T]@r), and then the type given must live in that region — a call that would keep a value of one region inside a value of another is an error that says to copy it first. A written type names its regions, as a written type does everywhere else: first<text@r>(names), not first<text>(names).
  • Copies. v.copy() at r works on a T, whatever it turns out to be. A copy lives where it is made, so it is a T only where the header already keeps a T in that region — as a parameter xs: [T]@r or p: ^T@r does, since a use must then give a type of that region. A copy into any other region (one the task declares itself, or one nothing ties to T) is only the value itself, so every use must give a type that holds no text, slice, or pointer; otherwise the compiler says so, naming the copy.
  • Shapes, kinds, and modules. Any type fits a T: numbers, text, tuples, arrays, slices, pointers, maybe, shapes, and kinds. A task that takes types can be public or priv, used from another module (numbers.larger(3, 8)), and can use another such task, giving it the type it was given itself. A name in < > can't be a builtin type or a type the file already names, and main takes no types.
  • Not kinds, for now. A kind can't take types yet, so there is no kind Result<T>; maybe T and T ~ E cover what most such kinds would be for. A call that gives a type built from its own (f<(T, int)> inside f<T>) would never stop, so a type built up more than 24 types deep, or a task used with more than 500 sets of types, is an error.

Shapes that take types

A shape takes types in the same < >, with the same words: shape Box<T>, shape Pair<A: fixed, B: fixed>. Its fields are read once, with T standing for the type each value of it is given, and the compiler makes one shape for each set of types the program uses, so Box<int> is a struct holding an int64_t and nothing more.

The types given name no region, as a shape's fields don't: they are in the region of the value holding them, which the whole type names. So Box<text>@r is a box whose text is in r, one shape serves every region, and Box<int> names no region at all, since it holds nothing in one. 

shape Box<T>
    value: T
fi

# A field may name the shape again, with the types it takes, behind a pointer.
shape Node<T>
    value: T
    next: maybe ^Node<T>
fi

task valueOf<T>(b: Box<T>@r) -> T
    <- b.value
fi

task main()
    region r
    bind count = Box { value: 1 }          # Box<int>: the value says which type
    bind empty = Box<maybe int> { value: none }  # written, since none says nothing
    bind kept: Box<text>@r = Box { value: "ada".copy() at r }
    show(valueOf(count))                   # 1
    show(kept.value)                       # ada
    bind tail: ^Node<int>@r = new Node<int>(Node { value: 3, next: none }) at r
    bind head: ^Node<int>@r = new Node<int>(Node { value: 2, next: tail }) at r
    show(head^.value)                      # 2
fi
  • Literals. Box { value: 1 } works out the types from the values it gives, as a call does from its arguments; Box<int> { value: none } writes them, for when a value says nothing (none, fail e). Writing them is all or nothing, and a shape that takes no types has none to name.
  • Where they go. Anywhere a type does: a field, a parameter, a result, an array or slice ([Box<int>]@r), a tuple, a maybe, a kind's payload, after new (new Box<int>(Box { value: 1 }) at r), and inside another shape's types (Box<Box<int>>, Pair<Box<text>, int>@r). A declaration that takes no types of its own may name one, as a task textOf(b: Box<text>@r) -> text@r does, since the shape made for a set of types is one type with the shape given them. A shape that takes types is not a type on its own: Box alone is an error that says to name them.
  • Regions. A type given names no region (Box<text>@r, not Box<text@r>), and a shape given types names one exactly when its values hold something there: Box<text>@r and Box<int>. Inside a task that takes types, where the type given isn't known yet, that can't be told apart, so Box<T> names a region (b: Box<T>@r) and the region is dropped for the uses that don't need one, which leaves a task sending one back taking a region some of its uses have no use for (an open question).
  • Recursion. A field may name the shape again with the types it takes, behind a pointer (next: maybe ^Node<T>), as a shape may name itself. One that gives it a type built from its own (^Grow<Grow<T>>) would need an endless line of shapes, so that is an error after 24 of them, as is a shape containing itself by value.
  • Words. The same four words, meaning the same things: shape Shown<T: shown> may only be given a type that word allows. A task passing its own type on must ask for at least as much: a task tell<T>(b: Shown<T>@r) is an error that says to require shown too.

Names

A name starts with an ASCII letter and continues with ASCII letters, digits, and _, but cannot contain __ (two underscores), which the compiler keeps for its own C names. Words that mean something in C, such as int, default, or stdout, are ordinary names in Vela.

Tasks, shapes, kinds, and variants share one namespace in a file: no two of them can have the same name, even across different kinds, and none can be named like a builtin: the types (int, float, bool, text, unit), the tasks (show, scan), or the kinds no file declares and their variants (ParseError with NotANumber and TooLarge, InputError with Ended and NoNumber). Another module has names of its own (see Modules). Every type you write must be a builtin, a shape, or a kind. A variable can't take the name of a variant, a kind, or a module the file includes, so a bare Red always means the variant, and Light.Red a variant of Light.

Control Flow

when x > 0
    show("positive")
else
    show("non-positive")
fi

loop count < 10
    show(count)
    count = count + 1
fi

each i in 0..5
    show(i)
fi

each counts from the start of the range up to, but not including, the end. Both ends are evaluated once, before the first iteration; the loop variable is immutable. A range such as 0..5 is not a value: it can only appear in each and in a slice. each also goes through the items of an array or slice, as in each score in scores (see Arrays).

loop repeats while its condition holds. There is no break or continue: end a loop through its condition, or leave the task with <-. The condition follows loop directly: loop when count < 10 says a 'loop' takes its condition directly, without 'when'.

A when or a match can be a value as well as a statement, giving one from each branch (see A match or a when as a value).

else when chains conditions: each is tried in turn, the first that holds runs its block, and one fi closes the whole chain. A chain is the same statement as a when written inside the else on its own lines, so it may end with an else, or with nothing when no condition need hold. else if is an error that says so. 

task grade(score: int) -> text
    when score >= 90
        <- "top"
    else when score >= 60
        <- "pass"
    else
        <- "fail"
    fi
fi

task main()
    show(grade(72))       # pass
fi

A condition can also test a pattern with is, the same patterns a case takes. The names it binds are visible only in the block it guards (not in the else), and is must be the whole condition: combining it with and or or is an error. A name is a bind unless the pattern writes hold before it, and parentheses take a tuple apart (see Tuples). 

when light is Dimmed level
    show(level)
fi

loop current is {node}      # while current holds a node
    show(node^.value)
    current = node^.next
fi
bind found: maybe (text, int) = ("Ada", 36)
when found is {(name, age)}       # the value, then its items
    show(name)
    show(age)
fi
bind pair = (1, "one")
when pair is (number, word)       # always matches: a tuple has no other case
    show(number)
    show(word)
fi
when pair is hold (n, w)          # hold: the names can be assigned
    n = n + 1
    show(n)
    show(w)
fi

A match or a when as a value

A match or a when can be the value itself, wherever a value goes: the right side of a bind, an argument, part of a larger expression, or what a task sends. Every branch then gives the value. A case gives it on one line with =, or on the last line of its block, as a plan B's block does; a when uses blocks only, and needs its else, since without one nothing gives the value when the condition doesn't hold. 

# The same `area` as in Kinds, with the match as the value it sends.
kind Shape
    Circle(radius: float)
    Rectangle(width: float, height: float)
fi

task area(s: Shape) -> float
    <- match s
    case Circle r = 3.14 * r * r
    case Rectangle w h = w * h
    fi
fi

# Shapes come from here, so `main` reads them as any program would.
task made(wide: bool) -> Shape
    <- when wide
        Circle(2.0)
    else
        Rectangle(1.0, 2.0)
    fi
fi

task main()
    bind s = made(true)
    show(area(s))                      # 12.56

    # A case may work first, and give the value on its last line.
    bind name = match s
    case Circle r
        bind wide = r > 1.0
        when wide
            "a wide circle"
        else
            "a circle"
        fi
    case Rectangle w h = "a rectangle"
    fi
    show(name)                         # a wide circle

    # A `when` used as a value, with a chain of conditions.
    bind size = when area(s) > 100.0
        "huge"
    else when area(s) > 1.0
        "middling"
    else
        "tiny"
    fi
    show(size)                         # middling
fi

The rules are the ones the pieces already have:

  • Every branch gives one type. The types the branches give are joined, by the rule the items of an array follow: a branch that gives none makes the whole a maybe, and one that gives fail e makes it a T ~ E, exactly as a value becomes one anywhere else, with the wrapper outside whatever a branch already gives (see Becoming a wider type). Where every branch gives one of those, the place the value goes says what it is part of, as it does for a bare none.
  • A branch may leave the task instead with <-. It gives no value then, and the other branches settle the type. If every branch sends, nothing gives a value, which is an error.
  • The last line may be a when or a match, which gives the value through its own branches. That is how a chain of conditions gives one, and how a branch chooses again inside itself.
  • A match still covers every case, and case _ still covers the rest: a value must come from somewhere for every outcome.
  • A region declared inside a branch is freed when it ends, so the value can't be in it; a value in a region declared outside is fine (see Memory and Regions).
  • = belongs to a case that gives a value. The cases of a match written on its own hold statements, so case p = value there is an error that says so.

Maybe and Errors

A value that might be missing has type maybe T. Wherever a maybe is expected (a typed binding, an assignment, an argument, a field, or a send), a plain value becomes one, and none is the empty one. A maybe can't be used as its value directly: m + 1 is an error, and == compares it only with none. A maybe can't hold another maybe. 

task half(n: int) -> maybe int
    when n % 2 == 0
        <- n / 2               # the int becomes a maybe int
    fi
    <- none
fi

bind m = half(7)
show(m)                    # none
show(m == none)            # true
show(m + 1)                # error: arithmetic requires numeric operands; the value in this maybe int must be extracted first

There are three ways to get the value out. match handles both outcomes:

match half(8)
case {n}
    show(n)                # 4
case none
    show("odd")
fi

is runs a block only when there is a value (see Control Flow): when half(8) is {n}. And a plan B, a block after the value, gives the value to use when there is none: 

bind a = half(7) { 0 }            # 0
bind b = half(7) { 1 } * 10       # 10: a plan B works inside expressions
bind c = half(7) {
    show("odd, using 3")
    3                              # the last line is the value
}
bind d = half(7) {
    <-                             # or leave the task instead
}

The value before the block is evaluated once, and the block runs only when it is empty. Its last line gives the value, of the type inside the maybe, and may be a when or a match, which gives it through their branches (see A match or a when as a value); a <- in the block sends from the task as usual, and when every path through the block sends, it needs no value line. Names declared in the block stay in it, and an empty block is an error. A call with a plan B can be a statement of its own: half(7) { <- } leaves the task when there is no value, and drops the value otherwise. A { after a shape's name followed, on the same line, by field: or } is a shape literal; any other { after a value starts a plan B, and a <- may follow it on the same line: m { <- 0 }.

A task that can fail sends T ~ E: its value when it works, or an error of type E, sent with <- fail error. The error type must differ from the value type, and can be any type but unit, a maybe, or another T ~ E: a type has one error side, so (int ~ text) ~ text is refused, as maybe maybe int is. Two words keep the two jobs apart: fail is the verb that makes a failure, and failure is the noun that names one where it is matched. So case {v} matches a success, case failure e a failure, and a plan B's first line failure e names the failure it handles — the name of the error value, not a type; the type is the one after ~: 

kind SizeError
    Negative(value: int)
    TooBig
fi

task checked(size: int) -> int ~ SizeError
    when size < 0
        <- fail Negative(size)
    fi
    when size > 100
        <- fail TooBig
    fi
    <- size
fi

task main()
    bind a = checked(500) { 100 }       # ignore the error: use 100
    bind b = checked(-1) {
        failure e
        match e
        case Negative value
            show(value)            # -1
        case TooBig
            show("too big")
        fi
        0
    }
    match checked(7)
    case {size}
        show(size)                 # 7
    case failure e
        show("failed")
    fi
fi

unit ~ E is a task that sends nothing when it works: a bare <-, or reaching the end, succeeds, and case {_} matches that success. A call written as a statement can't drop an error by accident: when its ~ result goes unused, that is an error. (A result kept with bind stays a T ~ E that only a match or a plan B opens, but nothing yet checks that such a variable is ever used.) An empty plan B, save(file) { }, ignores the error on purpose. fail binds like - and not, so an error computed with operators needs parentheses. 

task save(size: int) -> unit ~ text
    when size > 100
        <- fail "too big"
    fi
    show("saved")
fi

save(500)                  # error: the error 'save' may send is ignored
save(500) {
    failure reason
    show(reason)           # too big
}

Becoming a wider type

A plain value becomes a maybe or a T ~ E by being wrapped: the value is kept as it is, and the emptiness, or the error side, is added around it. That is all of it, and it has one consequence worth knowing: a value already made is never changed inside. A value written out is built part by part, so each part becomes what that part's type is; a value that comes back from a task is already made, and nothing reaches into it. 

bind pair: (int, maybe int) = (2, 3)      # written out, so built item by item
bind made = divide(17, 5)                 # (int, int), already made
bind taken: (int, maybe int) = (made.0, made.1)  # its items, built into the type wanted
bind same: (int, maybe int) = made
# error: expected type (int, maybe int), got (int, int); a value already made is never changed inside, …

Where several values must have one type — the items of an array, the branches of a match or a when used as a value — the same rule decides what that type is: the types are joined, and a wrapper goes outside whatever is already wrapped. 

bind m: maybe int = 3
bind xs = [1, none]                # [maybe int; 2]
bind ys = [m, fail "no"]           # [maybe int ~ text; 2]: the maybe kept, an error side added
bind zs = [risky(1), none]         # risky sends int ~ text: [maybe (int ~ text); 2]
bind ws = [risky(1), m]            # error: an array's values have one type, but this one is maybe int …

The middle two are the two nestings, and which one comes out follows from what was wrapped already: a maybe int beside a failure keeps its maybe and gains an error side, and an int ~ text beside none keeps its error side and goes inside a maybe. Two values that would each need the other remade, like int ~ text beside maybe int, have no type in common: which one is meant is the program's to say.

Writing the two apart. ~ holds the whole type before it, so maybe int ~ text means (maybe int) ~ text: a text failure, or a success holding maybe an int. Parentheses group a type, so the other nesting is maybe (int ~ text): nothing, or a result that may have failed. One type in parentheses is only that type, and a tuple still needs two or more items. A maybe and an error side nest either way round, but neither nests inside itself: maybe maybe int and (int ~ text) ~ text are both refused.

Memory and Regions

Vela has no garbage collector and no free. Values are copied and live where they are declared; a value that needs to be shared or linked, like the nodes of a list, is allocated with new in a region: an arena that gives out memory until the block declaring it closes, and then frees everything in it at once. Every pointer's type names its region, and the compiler makes sure no pointer is ever stored where it could outlive that region. So a Vela program can't use freed memory, free anything twice, or leak memory past the block that owns it, and the compiler does this with a handful of rules rather than a borrow checker.

This section is the reference. Vela Regions is the longer guide: why Vela has regions, their pros and cons, which types need a region and which don't, a step-by-step tutorial, the current limitations with a workaround for each, and ideas for where regions could go next.

The rules in short.
  • region r declares a region; new T(v) at r (or new@r T(v)) copies a value into it.
  • A pointer into r has type ^T@r, and a type can only name regions visible where it is written.
  • When the block declaring r closes, however it closes, everything in r is freed.
  • A task allocates only in a region it is given as a parameter, r: region; it can read and link pointers in any region its parameters' types name.
  • region r default (and r: region default) makes r the block's default region: what allocates there needs no at r.
  • A pointer is never stored in a different region than the one its type names.

Allocating in a region

shape Point
    x: int
    y: int
fi

task main()
    region scratch                          # a new, empty region
    bind n = new int(42) at scratch         # n is a ^int@scratch
    bind p = new@scratch Point(Point { x: 1, y: 2 })
    n^ = n^ + 1                             # read and write through ^
    p^.x = 5
    show(n^ + p^.x)                         # 48
fi                                          # scratch, and all in it, is freed here

new T(value) at r and new@r T(value) are the same: both copy the value into region r and give back a ^T@r. The type after new names no region, since what it makes lives in the region it allocates in. A pointer to a shape has no fields of its own: read and write them through ^, as in p^.x (p.x is an error that says so). Writing through a pointer is allowed even from a bind, which holds the address, not the value.

Pointer types name their region

A pointer type is written ^T@r. The @r comes after ^ and maybe and before ~, so maybe ^Node@r is a maybe pointer into r, and ^Node@r ~ text is such a pointer or a text error. A type without pointers lives in no region: int@r and Point@r are errors. A pointer always points to something: one that may be missing is a maybe ^T@r, which must be checked before it is used (see Maybe and Errors), and costs nothing extra, since the C it becomes is a plain pointer. 

region r
hold next: maybe ^int@r = none
when next == none
    next = new int(1) at r
fi
when next is {p}
    show(p^)                               # 1
fi
show(next^)                                # error: this pointer is a maybe ^int@r, which may be none
bind bad: ^int@r = none                    # error: expected type ^int@r, got none; a pointer can't be none, so use 'maybe ^int@r'
bind lost: ^int = new int(2) at r         # error: a pointer lives in a region, so its type names one

A region lives until its block closes

A region can be used from its region statement to the end of the block that declares it, like a variable, and shares the variables' names (no shadowing). Since a type can only name a region visible where the type is written, no variable, field, or result outside the block can hold a pointer into the region, so nothing is left pointing into it when it is freed. And a pointer is never stored in another region, which might live longer: 

hold saved: maybe ^int@inner = none     # error: unknown region 'inner'; declare it with 'region inner'

region outer
hold p = new int(0) at outer
when ready
    region inner
    p = new int(1) at inner                # error: expected type ^int@outer, got ^int@inner;
fi                                         #   a value can't move to another region

The region is freed however the block ends: at its fi, at the end of a plan B's block (after its last line has given its value), or by a send (<-) from anywhere inside it, which frees every region the task has declared before it returns (after computing the value it sends). A region in a loop's body is a new region on every pass, freed at the end of the pass, which is how a loop allocates without growing: 

each line in 0..1000
    region work                            # empty again on every pass
    bind temporary = new int(line) at work
    show(temporary^)
fi

There is no way to free one value early: free p is an error that explains this. Memory a region hands out stays in use until the region is freed, so a value replaced in a long-lived region (a hold pointer given a new new) keeps the old one's memory until then.

Tasks and regions

A task that allocates takes the region to allocate in as a parameter of type region, and the caller passes one of its regions by name. Its result can be a pointer into that region: 

shape Node
    value: int
    next: maybe ^Node
fi

task push(r: region, list: maybe ^Node@r, value: int) -> ^Node@r
    <- new Node(Node { value: value, next: list }) at r
fi

task sum(list: maybe ^Node@r) -> int         # only reads, so r is just a name
    hold total = 0
    hold current = list
    loop current is {node}
        total = total + node^.value
        current = node^.next
    fi
    <- total
fi

task main()
    region nodes
    hold list: maybe ^Node@nodes = none
    each i in 1..4
        list = push(nodes, list, i)
    fi
    show(sum(list))                        # 6
fi

A region named in a task's header without a region parameter, like r in sum, stands for whichever region the caller's arguments are in: sum(list) reads a list in nodes, and the same task reads lists in any other region. It costs nothing at run time, but the task can't allocate there (new … at r is an error that suggests the parameter). Two parameters with the same region name must be in the same region, and a result can only name regions the header's parameters name: 

task make() -> ^int@r                     # error: the result lives in region 'r', which the task isn't given
    region r
    <- new int(1) at r
fi

Regions aren't values: a region is only a region statement, a region parameter, an argument for one, or a name after @ or at. It can't be stored in a variable or a field, or sent from a task.

A block's default region

A block may name one of its regions its default, written after the region's name. Everything in the block that makes memory and names no region goes there, so at r is written only where memory goes somewhere else. A task takes one the same way, r: region default, which makes the region it is given the default of its body: 

task grow(r: region default, upto: int) -> [int]@r
    hold made = new [int]()            # in r
    each n in 1..upto
        made.add(n * n)
    fi
    <- made
fi

task main()
    region kept default
    bind squares = grow(kept, 4)         # a region is still passed by name
    bind greeting = "Hello, " + "Ada"   # text@kept
    bind p = new int(7)                 # ^int@kept
    each round in 0..3
        region pass default              # this block's own default
        show("pass " + round.str())      # text@pass, freed at the end of the pass
    fi
    region other
    bind elsewhere = new int(1) at other  # named, so it goes there
    show(squares.len, greeting, p^, elsewhere^)
fi
  • What it fills in. Everything that makes memory and would otherwise name a region: new, new [T](…), joining text (a + b), text holding values ("{n}"), a value written as text (x.str(), text(x)), and scan(prompt). A written region always wins, and nothing else changes: the value's type still names the region it lives in, which hover in Vela Studio shows.
  • A copy is the exception. x.copy() goes where the value it becomes goes (see Copies into a region), which is a better answer than a default, so a block's default doesn't settle one and a copy that nothing gives a region still says so.
  • One per block. A second default in the same block is an error: two lines that look alike would allocate in regions of different lifetimes. An inner block may name its own, which holds until that block closes; after it, the enclosing default is the one in force again.
  • It is opt-in. A block with no default is exactly as it always was: allocating there names a region, and the error that says so also mentions this, since making a region the default is often the shorter fix.
  • Only a region. n: int default is an error, and so is default on a shape's field or a variant's value. A task takes one default region at most, and a region the header only names (list: maybe ^Node@r) can't be one, since nothing can allocate there.

Shapes and kinds that hold pointers

A shape or kind whose fields hold pointers (directly, or in other shapes and kinds they hold by value) lives in a region too. Its declaration writes its pointers without a region, since they are in whatever region its value is, and a use names that region: Node@r. Everything one value holds lives in that one region, so reading a field of a Node@r gives a maybe ^Node@r. 

kind Tree
    Leaf(value: int)
    Branch(left: ^Tree, right: ^Tree)          # no region here: '^Tree@r' is an error
fi

task count(t: Tree@r) -> int
    match t
    case Leaf value
        <- value
    case Branch left right
        <- count(left^) + count(right^)
    fi
fi

task main()
    region trees
    bind one = new Tree(Leaf(1)) at trees
    bind two = new Tree(Leaf(2)) at trees
    show(count(Branch(one, two)))          # 3
    show(count(Leaf(5)))                   # 5
fi

A value built without any pointers, such as Leaf(5) or Node { value: 1, next: none }, takes the region of the place it goes: an argument, a field, or a variable with a written type. (So does the result of a task given only such values, as in first(none) for a task first(list: maybe ^Node@r) -> maybe ^Node@r, and a plan B on such a result takes the region of its fallback, which can't be a region declared in the plan B's own block, since that is freed when the block ends.) A binding without a type can't tell which region such a value should be in, so it asks for one: 

hold head = Node { value: 1, next: none }     # error: cannot tell which region 'head' lives in, ...;
                                              #   give it a type, such as 'head: Node@r'
hold first: Node@nodes = Node { value: 1, next: none }
first.next = push(nodes, none, 2)                # fine: first is in nodes

Text in a region

Text has a lifetime too. text lasts as long as the program, as a literal does, and text@r is in region r: text a value in r holds (an item of a [text]@r, a field of a Node@r, what a ^text@r points to) is in r, whatever it was made from. Text that lasts fits wherever text of a region is expected, and text of a region never goes where it could outlive its region: into a text, or text of another region.

A shape or kind holding text, but no pointers, may name a region or not. Person holds text that lasts, and Person@r may hold text in r; a literal takes the region of the text in it, and none when all of its text lasts. A shape holding pointers always names its region, and its text is in it. 

shape Person
    name: text
    age: int
fi

# Takes a Person whose text is in any region, or lasts.
task greet(p: Person@r)
    show(p.name)
fi

task main()
    region r
    hold names = new [text]() at r
    names.add("Ada")                               # a literal fits text@r
    bind first = names[0]                          # text@r
    bind plain = Person { name: "Bob", age: 7 }    # Person: its text lasts
    bind held = Person { name: first, age: 36 }    # Person@r: its text is in r
    greet(plain)                                   # Bob
    greet(held)                                    # Ada
    hold lasting = "none yet"
    lasting = first                                # error: expected type text, got text@r; …
fi
  • Tasks. A parameter of type text takes text that lasts. To take text of any region, a task names one in its header, as it does for pointers: name: text@r or p: Person@r takes text in r, or text that lasts, and a result of type text@r may send either back. Had greet taken a plain Person, greet(held) would be an error saying to name a region.
  • Comparing and showing. == compares text of any regions, and show prints any text.
  • Fields. A field or payload is written text: its text is in the region of the value holding it, when that value names one. A shape's text fields share that one region.
  • C. Text is its bytes' address and how many there are, either way; the region is only in the types, checked when compiling.

Slices

A slice, [type]@r, is a view of items in region r: in C, a pointer to the first and how many there are. It follows a pointer's rules: it is never none (a maybe [int]@r can be), its type names its region except in a field and after new, it can't be stored in another region, and a task sends one only into a region it is given. new [T](items) at r makes a slice by copying the items into r: [v; n] for n copies of v, where n may be known only as the program runs, an array, or another slice. new [T]() at r makes one with no items. 

task squares(r: region, n: int) -> [int]@r
    bind out = new [int]([0; n]) at r
    each i in 0..n
        out[i] = i * i
    fi
    <- out
fi

task main()
    region r
    bind all = squares(r, 5)            # 0 1 4 9 16
    bind middle = all[1..4]             # 1 4 9: the same memory, not a copy
    middle[0] = 100                     # a slice's items are written through it, even a bind's
    show(all[1])                        # 100
    show(middle.len)                    # 3
    bind copied = new [int](middle) at r  # its own items
fi
  • Slicing. xs[a..b] is the items from a up to, but not including, b, without copying. It works on a slice, and on an array in a region: one a pointer points to, as in p^[0..2] for p: ^[int; 4]@r, or an item of a slice. An array in a variable isn't in a region, so slicing it is an error; copy it with new [int](xs) at r, or keep it in a region with new [int; 4](xs) at r.
  • Checks. Every index and slice is checked as the program runs (vela: slice 2..7 is out of range 0..4, vela: slice 3..1 ends before it starts), and so is a count for new [T]([v; n]) (vela: count -2 is negative).
  • Writing. A slice's items can always be written, like what a pointer points to; its len can't be: it changes as items are added and taken out, or by slicing.
  • Regions. A slice's items live in its region, so new [^Node](nodes) at other is an error when the pointers are in another region, as copying a pointer there would be.

Adding and taking out items

A slice's length can change; an array's can't, since it is part of the array's type. Four changes are built in: 

task main()
    region r
    hold queue = new [text]() at r   # no items yet
    queue.add("b")                       # last: b
    queue.add("d")                       # b d
    queue.add(0, "a")                    # before item 0: a b d
    queue.add(2, "c")                    # a b c d
    show(queue.del(1))                  # b; now a c d
    show(queue.del())                   # d, the last; now a c
    show(queue.len)                     # 2
fi
  • The four changes. xs.add(v) puts v last and xs.add(i, v) before item i, where i may be the length (last). xs.del(i) takes item i out and xs.del() the last item; both give the item, which can also be dropped (xs.del(0) as a statement). The items after the change move to close or open the gap. They are built into every slice, as len is, so no method can take their names.
  • Where. The slice changes where it is kept, so it must be in a place that can be assigned: a hold variable, a field of one, anything behind a pointer (bag^.items.add(v)), or an item of another slice. A bind, a parameter, a result, a call's value, and a part taken with xs[a..b] can't change; keep them in a hold variable first. To change a caller's slice, a task takes a pointer to what holds it.
  • The region. add may need more room, which it takes from the slice's region, so the task needs that region itself: a region r it declares, or an r: region parameter (as new does). del needs no region.
  • Checks. An index out of range stops the program (vela: index 5 is out of range 0..3; for add, the range includes the length), and so does del() on a slice with no items (vela: del() on an empty slice).
  • Evaluation. The slice's place is found first, then the arguments, left to right; a change inside a larger expression happens in order with the rest (xs.del() - xs.del() takes the last item first).

How it runs. A slice also knows its room: after the first add, its items are in a block of the region with free space after them, and an add is a copy into that space. A full block is replaced by one twice as large, the items copied into it; when the block ends where the region hands out memory next, it grows in place instead, without copying. Old blocks stay in the region until it is freed, like any memory there, so a slice that grows to n items has used at most about four times their size in the region. del moves the items after the one taken out, and taking out the last item gives its space back to the room. To take the first item out without moving the rest, read it and slice: bind first = xs[0], then xs = xs[1..xs.len].

Copies and parts. A copy of a slice (hold ys = xs) and a part of one (xs[1..3]) are views of the same items. Adding to one doesn't write over an item another counts: only the slice whose items end where the room begins adds in place, and the others copy their items into a block of their own first. Writing an item, del, and add in the middle move items in that shared memory, which the other views then see, as they see xs[i] = v. So does del at the end: it gives the item's space back to the room, and the next add to that slice goes there, over the item a copy made before the del may still count. After changing a slice, use the slice you changed, and give a copy that must keep its items items of its own: new [T](xs) at r.

Copying into another region

A value can't move to a region that outlives its own, but a copy can go there. value.copy() copies what a value holds in regions (its text, its slices' items, and what its pointers point to, all the way down) into the region of the place the copy goes: the slice it is added to, the variable or field it is assigned to, the parameter it is passed as (when the call shows that parameter's region), or the result it is sent as. Where nothing names a region (a bind without a type, a comparison), the copy names one: value.copy() at r, or value.copy()@r. 

shape Note
    title: text
    tags: [text]
fi

task main()
    region kept
    hold titles = new [text]() at kept
    hold first: maybe ^Note@kept = none
    each pass in 0..2
        region work                                 # freed at the end of every pass
        bind line = scan("Title: ") at work { "none" }
        hold tags = new [text]() at work
        tags.add(line)
        bind note = new Note(Note { title: line, tags: tags }) at work
        titles.add(line.copy())                     # into kept, the slice's region
        when first is none
            first = note.copy()                     # the note, its title, its tags
        fi
        bind shout = line.copy() at kept            # nothing here names a region
        show(shout)
    fi
    show(titles[0])                                 # Ada
    bind kept_note = first { <- }
    show(kept_note^.tags[0])                        # Ada
fi
  • What it copies. Text, a shape or kind holding text, pointers, or slices, a slice, a pointer (with the value it points to), and a maybe, T ~ E, array, or tuple of those. Copying a value that holds none of them (an int, a Point of numbers) is an error: use the value as it is.
  • Shared values and cycles. Two pointers to one value give two pointers to one copy, so linked data keeps its shape, and a cycle is copied as a cycle. A copied slice gets items of its own, so changing it or adding to it leaves the original alone.
  • The region. The copy allocates, so the task needs its region as a region parameter or its own region, as for new. A copy can't go into text that lasts (hold kept: text = line.copy() is an error): lasting text is only a literal's.
  • Inside literals. A copy in a shape literal, a variant, or an array gets its region from where the whole value goes: people.add(Person { name: line.copy(), age: 36 }) copies into the slice's region.
  • Cost. Time and memory in proportion to what is copied. Text is copied with its characters, and a slice's items in one block. Pointers are followed with a list of the values still to copy rather than the C stack, so a list of a million nodes copies without running out of stack, and a table of the values already copied (freed when the copy is done) keeps shared values shared.

Methods and regions

A value of a shape or kind that holds pointers or text lives in a region, and inside its methods that region is @this. A method may send what the value holds there, and take more of it; each call works the region out from the value, so one method serves every region. 

shape Named
    name: text
    node: ^Node

    nameOf() -> text@this              # the value's own text, in its region
        <- .name
    fi

    alters point(to: ^Node@this)        # a pointer into the value's region
        .node = to
    fi

    made(r: region, value: int) -> ^Node@r
        <- new Node(Node { value: value + .node^.value }) at r
    fi
fi

region r
hold n: Named@r = Named { name: "ada".copy() at r, node: new Node(Node { value: 1 }) at r }
bind name: text@r = n.nameOf()
n.point(new Node(Node { value: 5 }) at r)
region s
n.point(new Node(Node { value: 9 }) at s)   # error: expected type ^Node@r, got ^Node@s; method
                                          #   'Named.point' takes 'to' in '@this', the region the
                                          #   value it is called on lives in, so it must be in that region too

What a method sends from @this is text or pointers of the caller's region, so it can't outlive that region: kept = n.nameOf() into a text that lasts as long as the program is refused, as any text of a region is. A method is given the value, never its region, so it can't allocate in @this: new … at this, and adding to a slice the value holds, are refused, and a region parameter doesn't help, since the value can't point into another region. Grow the value where it is kept (n.node = new Node(…) at r, bag.items.add(v)), or have the method make something in a region it takes and send it back, as made does (an idea for later).

How it runs

A region is a list of chunks of memory. new takes the next bytes of the newest chunk (aligned for the type), so allocating is a few instructions; when a chunk is full, the next is twice as large, starting at 4 KB and growing up to 1 MB, and an allocation too big for that gets a chunk of its own. Freeing a region frees its chunks, however many values they hold. A region that never allocates costs nothing. In the generated C, a region is a local vela__rt__region r[1] (so r is a pointer to it, like a region parameter) and a vela__rt__region_free(r) on every way out of its block; the allocator is in runtime/vela_rt.h. If the system runs out of memory, the program prints vela: out of memory and stops.

What regions don't do (yet)

  • One value can't be freed on its own: memory is released a whole region at a time. For data that changes a lot over a long run, use a region per iteration, and copy what survives into a longer-lived region (.copy()).
  • Everything one value holds lives in one region: a shape can't hold pointers into two different regions, or text in two, and a pointer can't be stored in a longer-lived region (store a copy instead: p.copy()). Text of a region can't be made to last.
  • A task that only names a region in its header can't allocate in it, and a region can't be returned.
  • A task can't send a pointer-free value of a type that holds pointers (-> Tree@r sending Leaf(1)) unless a parameter names that region, and a name bound from a value in no region (@_, as when first(none) is {n}) can't be given a pointer.
  • Each of these has a workaround in Vela Regions, which also collects ideas for going further: easier region passing, freeing one value early, shapes with several regions, and more. The other memory models (borrowed references, move-only pointers) are in Future Directions.

Modules

A program can be split into several files. Each file is a module, and a file includes another with include, naming its path without .vela. What the other file declares is then named through the module's name, the path's last part: 

# main.vela
include shapes/geometry
include shapes/palette (Color, describe)

task main()
    bind square = geometry.Square(3.0)
    show(geometry.area(square))              # 9
    bind corner: geometry.Point = geometry.Point { x: 3.0, y: 4.0 }
    show(corner.x)                           # 3
    match square                             # a case names the variant alone
    case Square side
        show(side)                           # 3
    case Circle radius
        show(radius)
    fi
    bind red: Color = palette.Red           # Color came in by name
    show(describe(red))                      # red
    show(describe(Color.Blue))               # blue: a variant through its kind
fi

# shapes/geometry.vela
shape Point
    x: float
    y: float
fi

kind Figure
    Circle(radius: float)
    Square(side: float)
fi

task area(figure: Figure) -> float
    match figure
    case Circle radius
        <- pi() * radius * radius
    case Square side
        <- side * side
    fi
fi

priv task pi() -> float                # only geometry.vela can call it
    <- 3.14159
fi
  • Where. include lines come first in a file, before any task, shape, or kind. A path is relative to the folder of the file that has the include: include geometry reads geometry.vela next to it, include shapes/geometry reads it from the folder shapes, and .. goes up one folder (include ../common/strings). The command is the same as for one file: vela main.vela -o program reads every file the program includes, and an error in any of them names that file. The word is C's, but an include doesn't paste the file in: the other file stays a module with names of its own, and is read once however many files include it. Writing use or import instead is an error that names include.
  • Names. geometry.area(…) calls a task, geometry.Point { … } builds a shape, geometry.Square(3.0) makes a variant, and geometry.Point is a type anywhere a type is written (^geometry.Node@r, maybe geometry.Point, new geometry.Point(p) at r). A variant can also be named through its kind, geometry.Figure.Square(3.0). A case or is names a variant alone, as in case Square side, since the value's kind already says which module it is from, or through its kind, as in case geometry.Figure.Square side.
  • Bringing names in. include shapes/palette (Color, describe) also lets the file write Color and describe without palette., which still works too. Each name listed must exist in the module. A kind's variants come in only when listed themselves; otherwise they are named through the kind, Color.Blue.
  • Only the names listed. With braces, include shapes/palette {Color, describe} brings in Color and describe but not the module's name: palette names nothing in this file, so nothing else of the module can be reached. The parentheses include the module and the names; the braces, only the names.
  • Other names. => gives an included module or name another name, the real name on its left: include shapes/geometry => geo, or include shapes/palette (Color => Hue, describe). From then on the file writes only the new name: geometry.area, Color, and palette.Color are errors that say what to write instead. That is how a file includes two modules whose files have the same name (include shop/prices => shop and include fuel/prices => fuel), or two names that would clash. A variant keeps its own name, as a field does, since it belongs to its kind; rename the kind and write its variants through it, as in Hue.Red. Braces can rename names too ({Color => Hue}), but not the module, which has no name there.
  • Private. Everything a file declares can be used by the files that include it, unless it is marked priv: a task, shape, or kind (whose variants are then private too), or a shape's field. Another file can't read or assign a private field, or give it in a literal, so a module can keep a value's invariants to itself through its tasks. A shape with a private field can be built elsewhere only when that field names the value it falls back on, which the literal leaves out; with no such value, only the field's own module can build the shape at all. What other files see of a public task (its parameters and results), a public shape (its public fields), or a public kind (its variants' values) can't mention a private type, since they couldn't name it.
  • Each module's own names. Tasks, shapes, kinds, and variants share one namespace within a file, but each module has its own: two modules can both have an area, and a program can have its own Red beside palette.Red. A module sees only what it declares and what it includes; the main file's names aren't visible to the modules it includes. Only the main file's main starts the program; a module's main is an ordinary task, called as tools.main(). The program knows a module by its path from the main file's folder, so shop/prices.vela and fuel/prices.vela can both be in one program.
  • Messages. A message names things as the file with the error writes them: expected type Hue, got int after (Color => Hue), expected type geometry.Point, got int through the module's name. Something the file has no way to write is named by its module's path, as in expected type shapes/palette.Color, got int, and starts with ./ when that path reads like the name the file gives another module (./c.Thing, in a file with include x => c).
  • Rules. Modules can't include one another in a circle (modules can't include one another in a circle: a -> b -> a). A file includes each module once, however its path is written (from the folder app, ../app/shapes is shapes), and can't include two modules under one name. A name is listed once on an include line. The name a module is included under can't also be the name of something the file declares, of a name it brings in, or of a variable, and can't be a builtin type, task, or kind, or a variant of one. A module or name can't be renamed to itself, or to a builtin.
# in main.vela, after include shapes/geometry
show(geometry.pi())            # error: 'pi' is private to module 'geometry'
show(area(square))             # error: unknown task 'area'; module 'geometry' has one: write 'geometry.area', …

examples/shop.vela is a program in three files. In the generated C, a module's names are prefixed with its path (vela_shapes__1__geometry__0__area), so every module's names stay apart.

task fib(n: int) -> int

        <- n
    else
        <- fib(n - 1) + fib(n - 2)
    fi
fi

task main()

        show(fib(i))
    fi
fi

Current Limits

Vela is young. These are known, and planned for (see Future Directions):

  • The compiler reports every mistake a program has, one after another, and at most 20 of them at a time; a mistake that stops a line from being read hides nothing else on that line, and the lexer and the parser still stop at the first thing they can't read.
  • Memory is freed a whole region at a time, and a value holds pointers into one region only (see Memory and Regions).
  • Text has ==, < and the other comparisons, .len, parts (t[a..b]), joining (a + b at r), values turned into it (n.str() at r), numbers read from it (int(t)), show, and scan. It has no search, no trimming, and no case changes yet.
  • Input is read a line of text at a time with scan, or a number at a time with scan("Age: ", int); there are no files, and nothing reads part of a line.
  • Arrays and slices can't be compared or shown whole, and an array's count is known before the program runs (see Arrays). Tuples can't be shown whole, and are taken apart in is and case only in parentheses, as in {(a, b)} (see Tuples).
  • Tasks and shapes take types; a kind can't yet, and no word asks a type for arithmetic (see Types a declaration takes).
  • A method takes no types of its own, can't allocate in the region its value lives in, and is written inside its shape or kind, never in another module (see Methods and the room left to grow).
  • There are no packages to share modules between programs (see Modules).
  • show prints floats with 6 significant digits. It writes a maybe of a number, a bool, or text as its value or none, but a maybe of a shape or kind with its own str has to be opened first, as in when m is {value}, since that method needs a value to run on.
  • The order in which a call's arguments, the parts of a join, the values in text, or an operator's two sides are evaluated isn't defined, which matters only when they call tasks that print, or when more than one of them would stop the program (see Numbers), which decides the message. (Where one of them contains a plan B, a change to a slice, or a scan, they are evaluated left to right, and show always works out its values left to right.)
  • An expression, including a shape literal or a call's arguments, must be written on one line.
  • Statements aren't yet required to end at a line break (show(1) show(2) on one line is accepted).
  • Code may nest at most 100 levels deep (parentheses, operators in a row, blocks inside blocks; a new, an array literal, and a tuple count as two, and a plan B as three); deeper code is an error rather than a crash.

Building the Compiler

The Vela compiler is written in Rust and generates standard, portable C11, which it compiles with the C compiler named by the CC environment variable (cc by default). CC may include arguments, as in CC="ccache gcc". 

cargo build
./target/debug/vela program.vela -o program
CC=clang ./target/debug/vela program.vela -o program

vela <input.vela> [-o <output>] [--emit-c | --check]: -o names the executable (a.out by default), --emit-c prints the generated C instead of compiling it (or, with -o, writes it to that file; a program without main is allowed here), --check only checks the program (everything a build checks before running the C compiler, including that it has a main), -h/--help prints the usage, and --version prints the compiler's version. The files the program includes are read from the disk, next to it (see Modules). The output can't be the program's own file or a file it includes. A file name starting with - goes after --. The exit status is 0 on success, 1 when the program can't be read or doesn't compile (in Vela or in C), and 2 for wrong arguments. 

./target/debug/vela program.vela --emit-c -o program.c
cc -std=c11 -I runtime program.c -o program -lm   # the C includes runtime/vela_rt.h

Errors point at the exact place in your source:

program.vela:3:10: error: unknown variable 'missing'
 3 |     show(missing)
   |          ^

To run the test suite (requires a C compiler, $CC or cc):

cargo test
CC=clang cargo test

Tests are plain Vela programs: tests/run/ holds programs with their expected output (and a .in file as their input, when they read any), tests/fail/ holds programs the compiler must reject, tests/trap/ holds programs that must stop with a runtime error (such as an integer overflow or an index out of range) after printing their expected output, and every file in examples/ is checked against tests/examples/, as is every complete program in docs/regions.html against the output the page shows. The C generated for run tests and examples must also compile as strict ISO C11 with no warnings (-std=c11 -pedantic-errors -Wall -Wextra -Werror). Rust tests in tests/*.rs run those programs (programs.rs) and cover the command line, the library's build pipeline, the lexer, internal compiler errors, and the runtime (runtime.rs: the C tests in tests/runtime/, and the programs in tests/run/, tests/trap/, and examples/ run under AddressSanitizer and UndefinedBehaviorSanitizer with leak checks).

The compiler is also a Rust library, vela, so tools can use the language without copying it: vela::driver checks and builds programs exactly as the vela command does (and can keep a partly checked program for editors), vela::lexer::highlight splits source into tokens without stopping at errors (for editors), and lexer::KEYWORDS, ast::BUILTIN_TYPES, ast::BUILTIN_TASKS and ast::BUILTIN_KIND_NAMES list the language's reserved words and the names nothing else may take (ast::builtin_kinds gives those kinds as declarations, which Vela Studio reads).

The repository is a Cargo workspace: the compiler is the default member, and Vela Studio, the editor, lives under ide/. Plain cargo build and cargo test cover only the compiler, which has no dependencies; add --workspace to include Vela Studio's crates. Building and testing Vela Studio's page are described in its own guide. 

cargo test --workspace

To lint the compiler (or everything, with --workspace):

cargo clippy --all-targets

The compiler's own code may not use unwrap(), expect(), panic!, or unchecked indexing (enforced by lints in Cargo.toml), so problems are reported as errors instead of crashes. An error starting with internal compiler error means a bug in the compiler itself, not in your program.

Design Notes

  • Vela is intentionally small. It is not meant to replace Rust or C, but to explore how little syntax is needed for a safe, compiled systems language.
  • Memory is managed with regions rather than a garbage collector or a borrow checker: lifetimes are blocks, visible in the source, and a few type rules keep every pointer valid.
  • The compiler generates readable C, making it easy to debug and interoperate with existing C code.
  • Syntax uses keywords over punctuation to keep source code friendly and self-documenting; the few symbols (->, <-, ^, @) each stand for one idea.
  • Missing values and failures are types (maybe T, T ~ E) rather than conventions such as null pointers or error codes, so the checker makes sure they are handled.
  • A member of a value is always written after a dot, .count inside a method as c.count outside it, so nothing comes into scope unseen, and a method that changes its value says so with alters, which is also the only time the generated C passes it a pointer.
