What is Vela?

Vela is a small systems programming language designed to be minimal like Go, strictly typed with exhaustive matching, and expressive like modern functional languages — without the bloat. It has one clear way to do things: one kind of function, one kind of record, one kind of sum type, and memory managed through regions, without a garbage collector.

Vela compiles to C through a Rust-based compiler, so it runs anywhere C runs and inherits its performance while keeping the source language tidy and opinionated.

Philosophy

  • Minimal surface. No classes and structs. No interfaces and traits. Just shapes, kinds, and tasks.
  • One way to do it. Immutability by default with bind; mutation explicitly opt-in with hold.
  • Safe by design. Static typing, exhaustive pattern matching, no uninitialized variables, no null pointers, and pointers that can never outlive their memory.
  • Beautiful syntax. Words for control flow and logic (when, and, not), blocks closed with fi, no semicolons, and a symbol only where it reads as a picture: -> names what a task gives back, and <- gives it back.
  • No GC, no free. Values live on the stack, and new allocates in a region, which frees everything in it at once when its block closes (see Memory and Regions).

Hello, Vela

# A tiny Vela program
task main()
    show("Hello, Vela!")
fi

A program is a .vela file, with any files it includes (see Modules). Compile and run it with (the output is a.out unless -o names it): 

cargo run -- examples/hello.vela -o examples/hello
./examples/hello

More programs are in examples/: fib.vela (recursion), kinds.vela (kinds and match), todo.vela (a linked list in a region, with maybe pointers, is, and a plan B), errors.vela (T or E, fail, and handling errors with match, is, and a plan B), regions.vela (a tree in a region, a region per loop pass, and copying a result into a longer-lived region), arrays.vela (arrays, and slices in a region: sorting and a sieve of primes), shop.vela (a program in three files, with include, braces, =>, and priv), and demo.vela (tasks, shapes, pointers, and control flow).

Prefer an editor? Vela Studio highlights Vela, shows errors as you type, completes names, and runs the file with F5: vela-studio examples.

Types

  • int — 64-bit signed integer
  • float — 64-bit floating point
  • bool — true or false
  • text — UTF-8 string; == compares contents. text lasts as long as the program, as a literal does, and text@r is in region r (see Text in a region)
  • unit — the return type of a task that returns nothing; it has no values, so it can't be the type of a variable, parameter, or field
  • ^T@r — pointer to a T in region r; it always points to something (see Memory and Regions)
  • [T; n] — an array: n values of type T, held in place (see Arrays)
  • [T]@r — a slice: a view of values of type T in region r (see Slices)
  • maybe T — a T, or none (see Maybe and Errors)
  • T or E — a T, or an error E, sent by a task that can fail
  • region — the type of a task's region parameter, r: region
  • User-defined shapes and kinds

Syntax Overview

Every block — a task, shape, kind, when, loop, each, or match — closes with fi. Write each statement on its own line, without a semicolon after it (a ; only separates an array's type or value from its count, as in [int; 4]). (The compiler doesn't insist on the line break yet; see Current Limits.) Files may use LF or CRLF line endings.

A statement is a binding, an assignment, a block, a send (<-), a result update (total <- value, see Named Results), a region, or a task call, which may have a plan B (see Maybe and Errors). Any other expression on its own line would do nothing, so it is an error: x == 1 alone reports the result of '==' is unused; use '=' to assign. Comments start with #.

Tasks

Functions are called tasks. -> T in the header says a task sends back a value of type T, and <- sends it: one arrow points out of the header to the result, the other brings the result back. A task that sends nothing back has no arrow in its header. 

task add(a: int, b: int) -> int
    <- a + b
fi

task greet(name: text)
    show(name)
fi

A task that returns a value must send one on every path: the compiler rejects a task that could reach its end without sending. A when counts only if both branches send, a match only if every case does, and a loop never counts, since its body might not run. A task without a return type uses a bare <- to return early. A task whose results are named sets them instead, and reaching its end sends them; the same paths are walked, to make sure each one is set (see Named Results). 

task sign(x: int) -> int
    when x < 0
        <- -1
    fi
    <- 1                 # without this line: task 'sign' can finish without sending a value
fi

task report(x: int)
    when x == 0
        <-                  # nothing to send: just leave
    fi
    show(x)
fi

A send starts its line. <- is always one symbol, so a comparison with a negative number needs a space: a < -1 compares, and a <-1 is an error. In the middle of a line the error says so — '<-' sends a value and must start a line; to compare with a negative number, write '< -' — and at the start of a line, where name <- value sets a named result, it reports that a isn't a result of the task.

Tasks can be called before they are declared, and can call themselves. Parameters are immutable, and arguments are copies, so a task can't change a shape it was given; pass a pointer to let it change the caller's value.

Every program starts at task main(), which takes no parameters and returns nothing.

Several Results

A task can send more than one value: its header lists the types after ->, and <- sends one value for each. A list of names receives them. 

task divmod(a: int, b: int) -> int, int
    <- a / b, a % b
fi

task main()
    bind q, r = divmod(17, 5)
    show(q)                      # 3
    show(r)                      # 2

    bind whole, _ = divmod(9, 4)  # _ drops a result
    show(whole)                  # 2
fi

The results are separate values, not one value: show(divmod(17, 5)) and bind pair = divmod(17, 5) are errors that say 'divmod' sends 2 values; receive them with 'bind a, b = …'. A task with several results can only be called as the whole right side of a list, which includes a <- that sends them on: 

task halves(n: int) -> int, int
    <- divmod(n, 2)         # sends both of divmod's values
fi

Each result follows the rules of a single one: -> maybe int, bool and -> ^Node@r, int work as they read, and the regions of a call's results are settled at the call (see Memory and Regions). One value can't be unit, since unit means no value at all. A value sent on from a call, as in halves above, goes as it is: it doesn't become a maybe or a T or E on the way, which a single sent value would, and the error says so. Results fail one at a time, not together: -> int, int or Bad is two results, the second of which may fail, and its receiver gives that one a plan B. A task that fails as a whole sends a single T or E.

bind, hold, and assignment take the same lists with plain values too, and every value is computed before the first of them is stored, so two variables can be swapped in one line: 

hold a = 1
hold b = 2
a, b = b, a                  # a is 2, b is 1
bind x: int, y: float = 3, 0.5

A name can appear once on the left of an assignment, and the names of a bind or hold must all be new, as any binding's must. A _ on the left takes a value and drops it, except a T or E, whose error must be handled.

Named Results

A result can have a name, written like a parameter. The name is a variable of the task, and the same arrow that sends results sets it. What stands before the arrow says what happens:

HeaderLineMeaning
-> int<- valueSend the value and end the task
-> int, int<- a, bSend both values and end the task
-> total: inttotal <- valueSet the result and keep going
-> total: int<- valueSend that value and end the task
-> total: int<-Send the results as they are and end the task
-> total: intthe closing fiReaching the end sends the results

So an empty left side means "send and stop", and a name on the left means "this is the result so far":

task score(hits: int, misses: int) -> total: int
    total <- hits * 10
    when misses == 0
        <- total + 50            # a perfect round: send the bonus score and end here
    fi
    total <- total - misses * 5  # otherwise keep going
    when total < 0
        total <- 0
    fi
fi                               # reaching the end sends total

Setting a result never ends the task. With several names, one line can set them all, and a bare <- sends what they hold: 

task collatz(start: int) -> steps: int, peak: int
    hold n = start
    steps, peak <- 0, start
    loop n != 1
        when n % 2 == 0
            n = n / 2
        else
            n = 3 * n + 1
        fi
        steps <- steps + 1
        when n > peak
            peak <- n
        fi
        when steps == 1000
            <-                  # give up and send what we have
        fi
    fi
fi

The rules:

  • All or none. Either every result has a name or none does: -> q: int, int is an error.
  • The names are the task's. A result can't share a parameter's name, and the body can't declare another variable with it. After it is set it reads like any variable, total <- total - 1.
  • Only <- changes a result. total = 0 reports 'total' is a result; set it with 'total <- …', and count <- 1 on an ordinary variable reports 'count' isn't a result of this task; assign it with 'count = …'. So every line that changes what a task sends starts with a result's name and an arrow.
  • No zero values. Vela has no uninitialized variables, and results are no exception: each must be set before it is read, before every bare <-, and before the end of the task, on every path. Reading one too early reports 'peak' might not be set here, and a path that reaches the end without setting one reports task 'collatz' can finish without setting 'peak'. A <- values line sends its own values, so nothing after it runs and nothing else need be set.
  • Whole values. best <- Point { x: 0, y: 0 } sets a shape result; setting one field of it, best.x <- 0, isn't part of this.
  • A task that sends unit or E succeeds by reaching its end, so its result has no value to name.

Bindings

bind creates an immutable binding. hold creates a mutable variable.

bind pi = 3.14
hold count = 0
count = count + 1
hold total: float = 0.0     # the type can be written out

Assigning copies the value. Shapes are copied whole, so after hold b = a, changing b.x leaves a alone.

A variable lives until the block that declares it closes. Vela has no shadowing: inside a task, a name cannot be declared again while another variable with that name is visible (including parameters). Separate blocks, such as the two branches of a when, may reuse a name. 

when ready
    bind label = "go"
    show(label)
else
    bind label = "wait"   # fine: a different block
    show(label)
fi
show(label)                # error: unknown variable 'label'

Numbers

Arithmetic (+ - * / %) works on int and float. If either operand is a float, the result is a float; two ints give an int, with division truncating toward zero. % on floats keeps the sign of the dividend. On ints too, % keeps the sign of the dividend (-7 % 3 is -1). Comparisons (< <= > >=) work on numbers of the same type. Number literals are decimal digits with an optional fraction (42, 3.14), and _ may separate digits (1_000_000); there are no exponent or hex forms, so 1e5 is an invalid number. An int literal can be at most 9223372036854775807, so the smallest int is written -9223372036854775807 - 1. 

show(7 / 2)       # 3
show(7 / 2.0)     # 3.5
show(5.5 % 2.0)   # 1.5

An int never wraps around. An operation whose result doesn't fit in an int, and a division or remainder by zero, stop the program with a message saying where, on every C compiler: 

task average(total: int, count: int) -> int
    <- total / count
fi

task main()
    show(average(10, 4))     # 2
    show(average(10, 0))     # stops: vela: division by zero at 2:14 in task 'average'
fi

The one quotient that doesn't fit is the smallest int divided by -1, and -x overflows only when x is the smallest int. A remainder always fits: the smallest int % -1 is 0. Arithmetic on floats never stops the program: 1.0 / 0.0 is infinity. Arithmetic written with literals only (60 * 60 * 24) gives the same result every time, so the compiler computes it and rejects one whose result doesn't fit (integer overflow: the result, 9223372036854775808, is more than an int holds (at most 9223372036854775807)), and a division or remainder by a zero written that way, as in n / 0 (division by zero).

Text, Output, and Logic

Text literals use double quotes and support the escapes \n, \t, \r, \\, \", and \0. A # starts a comment that runs to the end of the line. A text literal ends on the line it starts (a line break in it is written \n). Text holds any UTF-8, but a \0 ends it early ("ab\0cd" shows as ab). show is the only builtin task: it prints an int, float, bool, or text followed by a newline (or a maybe of one: its value, or none). Floats print with up to 6 significant digits, switching to exponent form for very large or small values (123456789.0 shows as 1.23457e+08), and 0.0 / 0.0 and 1.0 / 0.0 show as nan and inf.

Logic uses words: and, or, and not work on bool, and and/or skip the right side when the left side decides the result. Conditions in when and loop must be bool: when count is an error. == and != work on numbers, bool, text (by contents), and pointers (by address); both sides must have the same type, except that pointers into different regions can be compared (they are never equal). A maybe compares only with none. 

# greet the user
show("say \"hi\"")       # say "hi"
show(2.0 / 3.0)            # 0.666667
show(1 < 2 and not false)  # true
show(1 == 1.0)             # error: expected type int, got float

Shapes

Shapes group named fields, like C's structs. (Several values of one type are an array; see Arrays.)

shape Point
    x: int
    y: int
fi

bind p = Point { x: 10, y: 20 }
show(p.x)

A shape literal must give every field exactly once, in any order: Point { y: 20, x: 10 } is the same value. A shape may also have no fields (Marker {}).

Shapes and kinds can be used before they are declared. A type cannot contain itself by value, since its values would be infinitely large, but it can point to itself. A pointer always points to something, so the pointer to the next one must be a maybe: the last node has none. (A field's pointer names no region: a shape that holds pointers lives in one, written Node@r; see Memory and Regions.) 

shape Node
    value: int
    next: maybe ^Node      # ok: a pointer that can be none
fi

shape Loop
    inner: Loop            # error: 'Loop' contains itself by value
fi

shape Chain
    next: ^Chain           # error: 'Chain' can never be created: field 'next' needs an existing ^Chain
fi

Assigning to a field requires the variable to be a hold; task parameters are immutable.

hold q = Point { x: 1, y: 2 }
q.x = 5                    # ok
p.x = 5                    # error: cannot assign to a field of immutable variable 'p'

Kinds

Kinds are tagged unions with exhaustive pattern matching. Each case binds the variant's payload fields in order; the bindings are visible only inside that case, so different cases may reuse names. A kind value has no fields of its own (s.radius is an error): match is the way to read a payload. 

kind Shape
    Circle(radius: float)
    Rectangle(width: float, height: float)
fi

task area(s: Shape) -> float
    match s
    case Circle r
        <- 3.14 * r * r
    case Rectangle w h
        <- w * h
    fi
fi

A match must have a case for every variant, each once; leaving one out is an error that names it. A last case _ covers every variant not matched above (it is an error when there are none left), and _ in place of a binding leaves that payload field unnamed. 

match s
case Rectangle w _
    show(w)
case _
    show("not a rectangle")
fi

A variant can have no payload. Write its value as just its name, with or without parentheses; its case binds nothing. 

kind Light
    Red
    Green
    Dimmed(level: int)
fi

bind a = Red
bind b = Green()          # same as Green
bind c = Dimmed(3)

A variant can also be named through its kind: Light.Red and Light.Dimmed(3) are the same values as Red and Dimmed(3), and a pattern may be written the same way, case Light.Dimmed level (the kind it names must be the value's). It is how another module's variants are named when only their kind is brought in (see Modules). Since Light.Red reads like a field, no variable can be named like a kind.

Arrays

An array holds a fixed number of values of one type, written [type; count]. A literal lists the values, or repeats one: [0; 8] is eight zeros, the value computed once and copied. xs[i] is an item, counting from 0, and xs.len is how many items there are. An array is a value, like a shape: assigning or passing it copies every item, and an item can be assigned where a field could be, as in a hold. 

bind scores: [int; 4] = [90, 72, 85, 60]
show(scores[2])             # 85
show(scores.len)            # 4
hold grid = [[0; 3]; 2]     # [[int; 3]; 2]
grid[1][2] = 5
hold copy = scores          # a copy: changing it leaves scores as it was
copy[0] = 0
scores[0] = 0               # error: cannot assign to an item of immutable variable 'scores'
each score in scores
    show(score)
fi
  • Items. A literal's values have one type, except that none and a value make a maybe ([none, 7] is a [maybe int; 2]), and fail e and a value make a T or E. A literal of only none needs a written type, as in bind slots: [maybe text; 4] = [none; 4]. Arrays go anywhere a type does: fields, payloads, parameters, results, maybe [int; 2], and arrays of shapes (points[1].x = 4). An array holds its items by value, so a shape can't hold an array of itself, and an array of pointers lives in a region like a shape holding them ([^Node; 3]@r).
  • Count. A count is at least 1 and known before the program runs: a number in a type, and a number or arithmetic on numbers ([0; 2 * 8]) in a literal. For a count known only while the program runs, make a slice in a region (see Slices). A type whose values would take more than 1 TiB of memory is an error.
  • Index. An index out of range stops the program with a message saying where, on every C compiler (vela: index 4 is out of range 0..4 at 7:12 in task 'main'); a constant index out of range is an error when compiling.
  • each. each v in xs goes through the items in order. An array is gone through as it was when the loop started, even if the loop changes it; a slice, as many items as it had then, each read as it is.
  • Not yet. Arrays can't be compared with == or shown whole (show their items one at a time), and a part of an array is a slice, which points into a region.

Names

A name starts with an ASCII letter and continues with ASCII letters, digits, and _, but cannot contain __ (two underscores), which the compiler keeps for its own C names. Words that mean something in C, such as int, default, or stdout, are ordinary names in Vela.

Tasks, shapes, kinds, and variants share one namespace in a file: no two of them can have the same name, even across different kinds, and none can be named like a builtin (int, float, bool, text, unit, show). Another module has names of its own (see Modules). Every type you write must be a builtin, a shape, or a kind. A variable can't take the name of a variant, a kind, or a module the file includes, so a bare Red always means the variant, and Light.Red a variant of Light.

Control Flow

when x > 0
    show("positive")
else
    show("non-positive")
fi

loop count < 10
    show(count)
    count = count + 1
fi

each i in 0..5
    show(i)
fi

each counts from the start of the range up to, but not including, the end. Both ends are evaluated once, before the first iteration; the loop variable is immutable. A range such as 0..5 is not a value: it can only appear in each and in a slice. each also goes through the items of an array or slice, as in each score in scores (see Arrays).

loop repeats while its condition holds. There is no break or continue: end a loop through its condition, or leave the task with <-. There is no else when either; put a when inside the else.

A condition can also test a pattern with is, the same patterns a case takes. The names it binds are visible only in the block it guards (not in the else), and is must be the whole condition: combining it with and or or is an error. 

when light is Dimmed level
    show(level)
fi

loop current is {node}      # while current holds a node
    show(node^.value)
    current = node^.next
fi

Maybe and Errors

A value that might be missing has type maybe T. Wherever a maybe is expected (a typed binding, an assignment, an argument, a field, or a send), a plain value becomes one, and none is the empty one. A maybe can't be used as its value directly: m + 1 is an error, and == compares it only with none. A maybe can't hold another maybe. 

task half(n: int) -> maybe int
    when n % 2 == 0
        <- n / 2               # the int becomes a maybe int
    fi
    <- none
fi

bind m = half(7)
show(m)                    # none
show(m == none)            # true
show(m + 1)                # error: arithmetic requires numeric operands; the value in this maybe int must be extracted first

There are three ways to get the value out. match handles both outcomes:

match half(8)
case {n}
    show(n)                # 4
case none
    show("odd")
fi

is runs a block only when there is a value (see Control Flow): when half(8) is {n}. And a plan B, a block after the value, gives the value to use when there is none: 

bind a = half(7) { 0 }            # 0
bind b = half(7) { 1 } * 10       # 10: a plan B works inside expressions
bind c = half(7) {
    show("odd, using 3")
    3                              # the last line is the value
}
bind d = half(7) {
    <-                             # or leave the task instead
}

The value before the block is evaluated once, and the block runs only when it is empty. Its last line gives the value, of the type inside the maybe; a <- in the block sends from the task as usual, and when every path through the block sends, it needs no value line. Names declared in the block stay in it, and an empty block is an error. A call with a plan B can be a statement of its own: half(7) { <- } leaves the task when there is no value, and drops the value otherwise. A { after a shape's name followed, on the same line, by field: or } is a shape literal; any other { after a value starts a plan B, and a <- may follow it on the same line: m { <- 0 }.

A task that can fail sends T or E: its value when it works, or an error of type E, sent with <- fail error. The error type must differ from the value type, and can be any type but unit or a maybe. case {v} matches a success and case fail e an error, and a plan B's first line fail e names the error: 

kind SizeError
    Negative(value: int)
    TooBig
fi

task checked(size: int) -> int or SizeError
    when size < 0
        <- fail Negative(size)
    fi
    when size > 100
        <- fail TooBig
    fi
    <- size
fi

task main()
    bind a = checked(500) { 100 }       # ignore the error: use 100
    bind b = checked(-1) {
        fail e
        match e
        case Negative value
            show(value)            # -1
        case TooBig
            show("too big")
        fi
        0
    }
    match checked(7)
    case {size}
        show(size)                 # 7
    case fail e
        show("failed")
    fi
fi

unit or E is a task that sends nothing when it works: a bare <-, or reaching the end, succeeds, and case {_} matches that success. A call written as a statement can't drop an error by accident: when its or result goes unused, that is an error. (A result kept with bind stays a T or E that only a match or a plan B opens, but nothing yet checks that such a variable is ever used.) An empty plan B, save(file) { }, ignores the error on purpose. fail binds like - and not, so an error computed with operators needs parentheses. 

task save(size: int) -> unit or text
    when size > 100
        <- fail "too big"
    fi
    show("saved")
fi

save(500)                  # error: the error 'save' may send is ignored
save(500) {
    fail reason
    show(reason)           # too big
}

Memory and Regions

Vela has no garbage collector and no free. Values are copied and live where they are declared; a value that needs to be shared or linked, like the nodes of a list, is allocated with new in a region: an arena that gives out memory until the block declaring it closes, and then frees everything in it at once. Every pointer's type names its region, and the compiler makes sure no pointer is ever stored where it could outlive that region. So a Vela program can't use freed memory, free anything twice, or leak memory past the block that owns it, and the compiler does this with a handful of rules rather than a borrow checker.

This section is the reference. Vela Regions is the longer guide: why Vela has regions, their pros and cons, a step-by-step tutorial, the current limitations with a workaround for each, and ideas for where regions could go next.

The rules in short.
  • region r declares a region; new T(v) at r (or new@r T(v)) copies a value into it.
  • A pointer into r has type ^T@r, and a type can only name regions visible where it is written.
  • When the block declaring r closes, however it closes, everything in r is freed.
  • A task allocates only in a region it is given as a parameter, r: region; it can read and link pointers in any region its parameters' types name.
  • A pointer is never stored in a different region than the one its type names.

Allocating in a region

shape Point
    x: int
    y: int
fi

task main()
    region scratch                          # a new, empty region
    bind n = new int(42) at scratch         # n is a ^int@scratch
    bind p = new@scratch Point(Point { x: 1, y: 2 })
    n^ = n^ + 1                             # read and write through ^
    p^.x = 5
    show(n^ + p^.x)                         # 48
fi                                          # scratch, and all in it, is freed here

new T(value) at r and new@r T(value) are the same: both copy the value into region r and give back a ^T@r. The type after new names no region, since what it makes lives in the region it allocates in. A pointer to a shape has no fields of its own: read and write them through ^, as in p^.x (p.x is an error that says so). Writing through a pointer is allowed even from a bind, which holds the address, not the value.

Pointer types name their region

A pointer type is written ^T@r. The @r comes after ^ and maybe and before or, so maybe ^Node@r is a maybe pointer into r, and ^Node@r or text is such a pointer or a text error. A type without pointers lives in no region: int@r and Point@r are errors. A pointer always points to something: one that may be missing is a maybe ^T@r, which must be checked before it is used (see Maybe and Errors), and costs nothing extra, since the C it becomes is a plain pointer. 

region r
hold next: maybe ^int@r = none
when next == none
    next = new int(1) at r
fi
when next is {p}
    show(p^)                               # 1
fi
show(next^)                                # error: this pointer is a maybe ^int@r, which may be none
bind bad: ^int@r = none                    # error: expected type ^int@r, got none; a pointer can't be none, so use 'maybe ^int@r'
bind lost: ^int = new int(2) at r         # error: a pointer lives in a region, so its type names one

A region lives until its block closes

A region can be used from its region statement to the end of the block that declares it, like a variable, and shares the variables' names (no shadowing). Since a type can only name a region visible where the type is written, no variable, field, or result outside the block can hold a pointer into the region, so nothing is left pointing into it when it is freed. And a pointer is never stored in another region, which might live longer: 

hold saved: maybe ^int@inner = none     # error: unknown region 'inner'; declare it with 'region inner'

region outer
hold p = new int(0) at outer
when ready
    region inner
    p = new int(1) at inner                # error: expected type ^int@outer, got ^int@inner;
fi                                         #   a value can't move to another region

The region is freed however the block ends: at its fi, at the end of a plan B's block (after its last line has given its value), or by a send (<-) from anywhere inside it, which frees every region the task has declared before it returns (after computing the value it sends). A region in a loop's body is a new region on every pass, freed at the end of the pass, which is how a loop allocates without growing: 

each line in 0..1000
    region work                            # empty again on every pass
    bind temporary = new int(line) at work
    show(temporary^)
fi

There is no way to free one value early: free p is an error that explains this. Memory a region hands out stays in use until the region is freed, so a value replaced in a long-lived region (a hold pointer given a new new) keeps the old one's memory until then.

Tasks and regions

A task that allocates takes the region to allocate in as a parameter of type region, and the caller passes one of its regions by name. Its result can be a pointer into that region: 

shape Node
    value: int
    next: maybe ^Node
fi

task push(r: region, list: maybe ^Node@r, value: int) -> ^Node@r
    <- new Node(Node { value: value, next: list }) at r
fi

task sum(list: maybe ^Node@r) -> int         # only reads, so r is just a name
    hold total = 0
    hold current = list
    loop current is {node}
        total = total + node^.value
        current = node^.next
    fi
    <- total
fi

task main()
    region nodes
    hold list: maybe ^Node@nodes = none
    each i in 1..4
        list = push(nodes, list, i)
    fi
    show(sum(list))                        # 6
fi

A region named in a task's header without a region parameter, like r in sum, stands for whichever region the caller's arguments are in: sum(list) reads a list in nodes, and the same task reads lists in any other region. It costs nothing at run time, but the task can't allocate there (new … at r is an error that suggests the parameter). Two parameters with the same region name must be in the same region, and a result can only name regions the header's parameters name: 

task make() -> ^int@r                     # error: the result lives in region 'r', which the task isn't given
    region r
    <- new int(1) at r
fi

Regions aren't values: a region is only a region statement, a region parameter, an argument for one, or a name after @ or at. It can't be stored in a variable or a field, or sent from a task.

Shapes and kinds that hold pointers

A shape or kind whose fields hold pointers (directly, or in other shapes and kinds they hold by value) lives in a region too. Its declaration writes its pointers without a region, since they are in whatever region its value is, and a use names that region: Node@r. Everything one value holds lives in that one region, so reading a field of a Node@r gives a maybe ^Node@r. 

kind Tree
    Leaf(value: int)
    Branch(left: ^Tree, right: ^Tree)          # no region here: '^Tree@r' is an error
fi

task count(t: Tree@r) -> int
    match t
    case Leaf value
        <- value
    case Branch left right
        <- count(left^) + count(right^)
    fi
fi

task main()
    region trees
    bind one = new Tree(Leaf(1)) at trees
    bind two = new Tree(Leaf(2)) at trees
    show(count(Branch(one, two)))          # 3
    show(count(Leaf(5)))                   # 5
fi

A value built without any pointers, such as Leaf(5) or Node { value: 1, next: none }, takes the region of the place it goes: an argument, a field, or a variable with a written type. (So does the result of a task given only such values, as in first(none) for a task first(list: maybe ^Node@r) -> maybe ^Node@r, and a plan B on such a result takes the region of its fallback, which can't be a region declared in the plan B's own block, since that is freed when the block ends.) A binding without a type can't tell which region such a value should be in, so it asks for one: 

hold head = Node { value: 1, next: none }     # error: cannot tell which region 'head' lives in, ...;
                                              #   give it a type, such as 'head: Node@r'
hold first: Node@nodes = Node { value: 1, next: none }
first.next = push(nodes, none, 2)                # fine: first is in nodes

Text in a region

Text has a lifetime too. text lasts as long as the program, as a literal does, and text@r is in region r: text a value in r holds (an item of a [text]@r, a field of a Node@r, what a ^text@r points to) is in r, whatever it was made from. Text that lasts fits wherever text of a region is expected, and text of a region never goes where it could outlive its region: into a text, or text of another region.

A shape or kind holding text, but no pointers, may name a region or not. Person holds text that lasts, and Person@r may hold text in r; a literal takes the region of the text in it, and none when all of its text lasts. A shape holding pointers always names its region, and its text is in it. 

shape Person
    name: text
    age: int
fi

# Takes a Person whose text is in any region, or lasts.
task greet(p: Person@r)
    show(p.name)
fi

task main()
    region r
    hold names = new [text]() at r
    names.add("Ada")                               # a literal fits text@r
    bind first = names[0]                          # text@r
    bind plain = Person { name: "Bob", age: 7 }    # Person: its text lasts
    bind held = Person { name: first, age: 36 }    # Person@r: its text is in r
    greet(plain)                                   # Bob
    greet(held)                                    # Ada
    hold lasting = "none yet"
    lasting = first                                # error: text@r can't become text
fi
  • Tasks. A parameter of type text takes text that lasts. To take text of any region, a task names one in its header, as it does for pointers: name: text@r or p: Person@r takes text in r, or text that lasts, and a result of type text@r may send either back. Had greet taken a plain Person, greet(held) would be an error saying to name a region.
  • Comparing and showing. == compares text of any regions, and show prints any text.
  • Fields. A field or payload is written text: its text is in the region of the value holding it, when that value names one. A shape's text fields share that one region.
  • C. Text is a const char* either way; the region is only in the types, checked when compiling.

Slices

A slice, [type]@r, is a view of items in region r: in C, a pointer to the first and how many there are. It follows a pointer's rules: it is never none (a maybe [int]@r can be), its type names its region except in a field and after new, it can't be stored in another region, and a task sends one only into a region it is given. new [T](items) at r makes a slice by copying the items into r: [v; n] for n copies of v, where n may be known only as the program runs, an array, or another slice. new [T]() at r makes one with no items. 

task squares(r: region, n: int) -> [int]@r
    bind out = new [int]([0; n]) at r
    each i in 0..n
        out[i] = i * i
    fi
    <- out
fi

task main()
    region r
    bind all = squares(r, 5)            # 0 1 4 9 16
    bind middle = all[1..4]             # 1 4 9: the same memory, not a copy
    middle[0] = 100                     # a slice's items are written through it, even a bind's
    show(all[1])                        # 100
    show(middle.len)                    # 3
    bind copied = new [int](middle) at r  # its own items
fi
  • Slicing. xs[a..b] is the items from a up to, but not including, b, without copying. It works on a slice, and on an array in a region: one a pointer points to, as in p^[0..2] for p: ^[int; 4]@r, or an item of a slice. An array in a variable isn't in a region, so slicing it is an error; copy it with new [int](xs) at r, or keep it in a region with new [int; 4](xs) at r.
  • Checks. Every index and slice is checked as the program runs (vela: slice 2..7 is out of range 0..4, vela: slice 3..1 ends before it starts), and so is a count for new [T]([v; n]) (vela: count -2 is negative).
  • Writing. A slice's items can always be written, like what a pointer points to; its len can't be: it changes as items are added and taken out, or by slicing.
  • Regions. A slice's items live in its region, so new [^Node](nodes) at other is an error when the pointers are in another region, as copying a pointer there would be.

Adding and taking out items

A slice's length can change; an array's can't, since it is part of the array's type. Four changes are built in: 

task main()
    region r
    hold queue = new [text]() at r   # no items yet
    queue.add("b")                       # last: b
    queue.add("d")                       # b d
    queue.add(0, "a")                    # before item 0: a b d
    queue.add(2, "c")                    # a b c d
    show(queue.del(1))                  # b; now a c d
    show(queue.del())                   # d, the last; now a c
    show(queue.len)                     # 2
fi
  • The four changes. xs.add(v) puts v last and xs.add(i, v) before item i, where i may be the length (last). xs.del(i) takes item i out and xs.del() the last item; both give the item, which can also be dropped (xs.del(0) as a statement). The items after the change move to close or open the gap. They aren't methods, which Vela doesn't have: they are what a slice can do, as len is what it has.
  • Where. The slice changes where it is kept, so it must be in a place that can be assigned: a hold variable, a field of one, anything behind a pointer (bag^.items.add(v)), or an item of another slice. A bind, a parameter, a result, a call's value, and a part taken with xs[a..b] can't change; keep them in a hold variable first. To change a caller's slice, a task takes a pointer to what holds it.
  • The region. add may need more room, which it takes from the slice's region, so the task needs that region itself: a region r it declares, or an r: region parameter (as new does). del needs no region.
  • Checks. An index out of range stops the program (vela: index 5 is out of range 0..3; for add, the range includes the length), and so does del() on a slice with no items (vela: del() on an empty slice).
  • Evaluation. The slice's place is found first, then the arguments, left to right; a change inside a larger expression happens in order with the rest (xs.del() - xs.del() takes the last item first).

How it runs. A slice also knows its room: after the first add, its items are in a block of the region with free space after them, and an add is a copy into that space. A full block is replaced by one twice as large, the items copied into it; when the block ends where the region hands out memory next, it grows in place instead, without copying. Old blocks stay in the region until it is freed, like any memory there, so a slice that grows to n items has used at most about four times their size in the region. del moves the items after the one taken out, and taking out the last item gives its space back to the room. To take the first item out without moving the rest, read it and slice: bind first = xs[0], then xs = xs[1..xs.len].

Copies and parts. A copy of a slice (hold ys = xs) and a part of one (xs[1..3]) are views of the same items. Adding to one never writes over an item another counts: only the slice whose items end where the room begins adds in place, and the others copy their items into a block of their own first. Writing an item, del, and add in the middle move items in that shared memory, which the other views then see, as they see xs[i] = v. After changing a slice, use the slice you changed.

How it runs

A region is a list of chunks of memory. new takes the next bytes of the newest chunk (aligned for the type), so allocating is a few instructions; when a chunk is full, the next is twice as large, starting at 4 KB and growing up to 1 MB, and an allocation too big for that gets a chunk of its own. Freeing a region frees its chunks, however many values they hold. A region that never allocates costs nothing. In the generated C, a region is a local vela__rt__region r[1] (so r is a pointer to it, like a region parameter) and a vela__rt__region_free(r) on every way out of its block; the allocator is in runtime/vela_rt.h. If the system runs out of memory, the program prints vela: out of memory and stops.

What regions don't do (yet)

  • One value can't be freed on its own: memory is released a whole region at a time. For data that changes a lot over a long run, use a region per iteration, or copy what survives into a fresh region yourself.
  • Everything one value holds lives in one region: a shape can't hold pointers into two different regions, or text in two, and a pointer can't be copied into a longer-lived region (copy the value it points to instead). Text of a region can't yet be copied into another region or made to last.
  • A task that only names a region in its header can't allocate in it, and a region can't be returned.
  • A value holding pointers can't be copied into another region whole, even when its pointers are none: rebuild it field by field.
  • A task can't send a pointer-free value of a type that holds pointers (-> Tree@r sending Leaf(1)) unless a parameter names that region, and a name bound from a value in no region (@_, as when first(none) is {n}) can't be given a pointer.
  • Each of these has a workaround in Vela Regions, which also collects ideas for going further: easier region passing, freeing one value early, shapes with several regions, and more. The other memory models (borrowed references, move-only pointers) are in Future Directions.

Modules

A program can be split into several files. Each file is a module, and a file includes another with include, naming its path without .vela. What the other file declares is then named through the module's name, the path's last part: 

# main.vela
include shapes/geometry
include shapes/palette (Color, describe)

task main()
    bind square = geometry.Square(3.0)
    show(geometry.area(square))              # 9
    bind corner: geometry.Point = geometry.Point { x: 3.0, y: 4.0 }
    show(corner.x)                           # 3
    match square                             # a case names the variant alone
    case Square side
        show(side)                           # 3
    case Circle radius
        show(radius)
    fi
    bind red: Color = palette.Red           # Color came in by name
    show(describe(red))                      # red
    show(describe(Color.Blue))               # blue: a variant through its kind
fi

# shapes/geometry.vela
shape Point
    x: float
    y: float
fi

kind Figure
    Circle(radius: float)
    Square(side: float)
fi

task area(figure: Figure) -> float
    match figure
    case Circle radius
        <- pi() * radius * radius
    case Square side
        <- side * side
    fi
fi

priv task pi() -> float                # only geometry.vela can call it
    <- 3.14159
fi
  • Where. include lines come first in a file, before any task, shape, or kind. A path is relative to the folder of the file that has the include: include geometry reads geometry.vela next to it, include shapes/geometry reads it from the folder shapes, and .. goes up one folder (include ../common/strings). The command is the same as for one file: vela main.vela -o program reads every file the program includes, and an error in any of them names that file. The word is C's, but an include doesn't paste the file in: the other file stays a module with names of its own, and is read once however many files include it. Writing use or import instead is an error that names include.
  • Names. geometry.area(…) calls a task, geometry.Point { … } builds a shape, geometry.Square(3.0) makes a variant, and geometry.Point is a type anywhere a type is written (^geometry.Node@r, maybe geometry.Point, new geometry.Point(p) at r). A variant can also be named through its kind, geometry.Figure.Square(3.0). A case or is names a variant alone, as in case Square side, since the value's kind already says which module it is from, or through its kind, as in case geometry.Figure.Square side.
  • Bringing names in. include shapes/palette (Color, describe) also lets the file write Color and describe without palette., which still works too. Each name listed must exist in the module. A kind's variants come in only when listed themselves; otherwise they are named through the kind, Color.Blue.
  • Only the names listed. With braces, include shapes/palette {Color, describe} brings in Color and describe but not the module's name: palette names nothing in this file, so nothing else of the module can be reached. The parentheses include the module and the names; the braces, only the names.
  • Other names. => gives an included module or name another name, the real name on its left: include shapes/geometry => geo, or include shapes/palette (Color => Hue, describe). From then on the file writes only the new name: geometry.area, Color, and palette.Color are errors that say what to write instead. That is how a file includes two modules whose files have the same name (include shop/prices => shop and include fuel/prices => fuel), or two names that would clash. A variant keeps its own name, as a field does, since it belongs to its kind; rename the kind and write its variants through it, as in Hue.Red. Braces can rename names too ({Color => Hue}), but not the module, which has no name there.
  • Private. Everything a file declares can be used by the files that include it, unless it is marked priv: a task, shape, or kind (whose variants are then private too), or a shape's field. Another file can't read or assign a private field, or build its shape with a literal, so a module can keep a value's invariants to itself through its tasks. What other files see of a public task (its parameters and results), a public shape (its public fields), or a public kind (its variants' values) can't mention a private type, since they couldn't name it.
  • Each module's own names. Tasks, shapes, kinds, and variants share one namespace within a file, but each module has its own: two modules can both have an area, and a program can have its own Red beside palette.Red. A module sees only what it declares and what it includes; the main file's names aren't visible to the modules it includes. Only the main file's main starts the program; a module's main is an ordinary task, called as tools.main(). The program knows a module by its path from the main file's folder, so shop/prices.vela and fuel/prices.vela can both be in one program.
  • Messages. A message names things as the file with the error writes them: expected type Hue, got int after (Color => Hue), expected type geometry.Point, got int through the module's name. Something the file has no way to write is named by its module's path, as in expected type shapes/palette.Color, got int, and starts with ./ when that path reads like the name the file gives another module (./c.Thing, in a file with include x => c).
  • Rules. Modules can't include one another in a circle (modules can't include one another in a circle: a -> b -> a). A file includes each module once, however its path is written (from the folder app, ../app/shapes is shapes), and can't include two modules under one name. A name is listed once on an include line. The name a module is included under can't also be the name of something the file declares, of a name it brings in, or of a variable, and can't be a builtin type or task. A module or name can't be renamed to itself, or to a builtin.
# in main.vela, after include shapes/geometry
show(geometry.pi())            # error: 'pi' is private to module 'geometry'
show(area(square))             # error: unknown task 'area'; module 'geometry' has one: write 'geometry.area', …

examples/shop.vela is a program in three files. In the generated C, a module's names are prefixed with its path (vela_shapes__1__geometry__0__area), so every module's names stay apart.

Complete Example

task fib(n: int) -> int
    when n < 2
        <- n
    else
        <- fib(n - 1) + fib(n - 2)
    fi
fi

task main()
    each i in 0..10
        show(fib(i))
    fi
fi

Current Limits

Vela is young. These are known, and planned for (see Future Directions):

  • The compiler reports the first error in a program, not all of them.
  • Memory is freed a whole region at a time, and a value holds pointers into one region only (see Memory and Regions).
  • text is a C string, so a \0 ends it; there are no text operations besides ==, !=, and show.
  • There is no way to read input.
  • Arrays and slices can't be compared or shown whole, and an array's count is known before the program runs (see Arrays).
  • There are no packages to share modules between programs (see Modules).
  • show prints floats with 6 significant digits.
  • The order in which a call's arguments, or an operator's two sides, are evaluated isn't defined, which matters only when they call tasks that print, or when more than one of them would stop the program (see Numbers), which decides the message. (Where one of them contains a plan B or a change to a slice, they are evaluated left to right.)
  • An expression, including a shape literal or a call's arguments, must be written on one line.
  • Statements aren't yet required to end at a line break (show(1) show(2) on one line is accepted).
  • Code may nest at most 100 levels deep (parentheses, operators in a row, blocks inside blocks; a new and an array literal count as two, and a plan B as three); deeper code is an error rather than a crash.

Building the Compiler

The Vela compiler is written in Rust and generates standard, portable C11, which it compiles with the C compiler named by the CC environment variable (cc by default). CC may include arguments, as in CC="ccache gcc". 

cargo build
./target/debug/vela program.vela -o program
CC=clang ./target/debug/vela program.vela -o program

vela <input.vela> [-o <output>] [--emit-c | --check]: -o names the executable (a.out by default), --emit-c prints the generated C instead of compiling it (or, with -o, writes it to that file; a program without main is allowed here), --check only checks the program (everything a build checks before running the C compiler, including that it has a main), -h/--help prints the usage, and --version prints the compiler's version. The files the program includes are read from the disk, next to it (see Modules). The output can't be the program's own file or a file it includes. A file name starting with - goes after --. The exit status is 0 on success, 1 when the program can't be read or doesn't compile (in Vela or in C), and 2 for wrong arguments. 

./target/debug/vela program.vela --emit-c -o program.c
cc -std=c11 -I runtime program.c -o program -lm   # the C includes runtime/vela_rt.h

Errors point at the exact place in your source:

program.vela:3:10: error: unknown variable 'missing'
 3 |     show(missing)
   |          ^

To run the test suite (requires a C compiler, $CC or cc):

cargo test
CC=clang cargo test

Tests are plain Vela programs: tests/run/ holds programs with their expected output, tests/fail/ holds programs the compiler must reject, tests/trap/ holds programs that must stop with a runtime error (such as an integer overflow or an index out of range) after printing their expected output, and every file in examples/ is checked against tests/examples/, as is every complete program in docs/regions.html against the output the page shows. The C generated for run tests and examples must also compile as strict ISO C11 with no warnings (-std=c11 -pedantic-errors -Wall -Wextra -Werror). Rust tests in tests/*.rs run those programs (programs.rs) and cover the command line, the library's build pipeline, the lexer, internal compiler errors, and the runtime (runtime.rs: the C tests in tests/runtime/, and the programs in tests/run/, tests/trap/, and examples/ run under AddressSanitizer and UndefinedBehaviorSanitizer with leak checks).

The compiler is also a Rust library, vela, so tools can use the language without copying it: vela::driver checks and builds programs exactly as the vela command does (and can keep a partly checked program for editors), vela::lexer::highlight splits source into tokens without stopping at errors (for editors), and lexer::KEYWORDS and ast::BUILTIN_TYPES list the language's reserved words and types.

The repository is a Cargo workspace: the compiler is the default member, and Vela Studio, the editor, lives under ide/. Plain cargo build and cargo test cover only the compiler, which has no dependencies; add --workspace to include Vela Studio's crates. Building and testing Vela Studio's page are described in its own guide. 

cargo test --workspace

To lint the compiler (or everything, with --workspace):

cargo clippy --all-targets

The compiler's own code may not use unwrap(), expect(), panic!, or unchecked indexing (enforced by lints in Cargo.toml), so problems are reported as errors instead of crashes. An error starting with internal compiler error means a bug in the compiler itself, not in your program.

Design Notes

  • Vela is intentionally small. It is not meant to replace Rust or C, but to explore how little syntax is needed for a safe, compiled systems language.
  • Memory is managed with regions rather than a garbage collector or a borrow checker: lifetimes are blocks, visible in the source, and a few type rules keep every pointer valid.
  • The compiler generates readable C, making it easy to debug and interoperate with existing C code.
  • Syntax uses keywords over punctuation to keep source code friendly and self-documenting; the few symbols (->, <-, ^, @) each stand for one idea.
  • Missing values and failures are types (maybe T, T or E) rather than conventions such as null pointers or error codes, so the checker makes sure they are handled.

Vela — designed and implemented as a minimal systems language experiment.
