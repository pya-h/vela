Vela.

A minimal, safe, fast systems language with a fresh face.

What is Vela?

Vela is a small systems programming language designed to be minimal like Go, strictly typed with exhaustive matching, and expressive like modern functional languages — without the bloat. It has one clear way to do things: one kind of function, one kind of record, one kind of sum type, and explicit memory management without a garbage collector.

Vela compiles to C through a Rust-based compiler, so it runs anywhere C runs and inherits its performance while keeping the source language tidy and opinionated.

Philosophy

  • Minimal surface. No classes and structs. No interfaces and traits. Just shapes, kinds, and tasks.
  • One way to do it. Immutability by default with bind; mutation explicitly opt-in with hold.
  • Safe by design. Static typing, exhaustive pattern matching, no uninitialized variables, and explicit (for now unchecked) ownership through owned pointers.
  • Beautiful syntax. Words for control flow and logic (when, and, not), blocks closed with fi, no semicolons, and a symbol only where it reads as a picture: -> names what a task gives back, and <- gives it back.
  • No GC. Manual memory management with new and free, or stack allocation where possible.

Hello, Vela

# A tiny Vela program
task main()
    show("Hello, Vela!")
fi

A program is one .vela file. Compile and run it with (the output is a.out unless -o names it): 

cargo run -- examples/hello.vela -o examples/hello
./examples/hello

More programs are in examples/: fib.vela (recursion), kinds.vela (kinds and match), todo.vela (a linked list with maybe pointers, is, and a plan B), and demo.vela (tasks, shapes, pointers, and control flow).

Prefer an editor? Vela Studio highlights Vela, shows errors as you type, completes names, and runs the file with F5: vela-studio examples.

Types

  • int — 64-bit signed integer
  • float — 64-bit floating point
  • bool — true or false
  • text — UTF-8 string; == compares contents
  • unit — the return type of a task that returns nothing; it has no values, so it can't be the type of a variable, parameter, or field
  • ^T — owned pointer to T; it always points to something
  • maybe T — a T, or none (see Maybe and Errors)
  • T or E — a T, or an error E, sent by a task that can fail
  • User-defined shapes and kinds

Syntax Overview

Every block — a task, shape, kind, when, loop, each, or match — closes with fi. Write each statement on its own line; there are no semicolons. (The compiler doesn't insist on the line break yet; see Current Limits.) Files may use LF or CRLF line endings.

A statement is a binding, an assignment, a block, a send (<-), free, or a task call. Any other expression on its own line would do nothing, so it is an error: x == 1 alone reports the result of '==' is unused; use '=' to assign. Comments start with #.

These words can't be used as names:

Tasks

Functions are called tasks. -> T in the header says a task sends back a value of type T, and <- sends it: one arrow points out of the header to the result, the other brings the result back. A task that sends nothing back has no arrow in its header. 

task add(a: int, b: int) -> int
    <- a + b
fi

task greet(name: text)
    show(name)
fi

A task that returns a value must send one on every path: the compiler rejects a task that could reach its end without sending. A when counts only if both branches send, a match only if every case does, and a loop never counts, since its body might not run. A task without a return type uses a bare <- to return early. 

task sign(x: int) -> int
    when x < 0
        <- -1
    fi
    <- 1                 # without this line: task 'sign' can finish without sending a value
fi

task report(x: int)
    when x == 0
        <-                  # nothing to send: just leave
    fi
    show(x)
fi

A send starts its line. <- is always one symbol, so a comparison with a negative number needs a space: a <-1 is an error that says so, wherever it appears, and a < -1 compares.

Tasks can be called before they are declared, and can call themselves. Parameters are immutable, and arguments are copies: a task that changes a shape it was given changes its own copy (pass a pointer to share one value).

Every program starts at task main(), which takes no parameters and returns nothing.

Bindings

bind creates an immutable binding. hold creates a mutable variable.

bind pi = 3.14
hold count = 0
count = count + 1
hold total: float = 0.0     # the type can be written out

Assigning copies the value. Shapes are copied whole, so after hold b = a, changing b.x leaves a alone.

A variable lives until the block that declares it closes. Vela has no shadowing: inside a task, a name cannot be declared again while another variable with that name is visible (including parameters). Separate blocks, such as the two branches of a when, may reuse a name. 

when ready
    bind label = "go"
    show(label)
else
    bind label = "wait"   # fine: a different block
    show(label)
fi
show(label)                # error: unknown variable 'label'

Numbers

Arithmetic (+ - * / %) works on int and float. If either operand is a float, the result is a float; two ints give an int, with division truncating toward zero. % on floats keeps the sign of the dividend. On ints too, % keeps the sign of the dividend (-7 % 3 is -1). Comparisons (< <= > >=) work on numbers of the same type. Number literals are decimal digits with an optional fraction (42, 3.14), and _ may separate digits (1_000_000); there are no exponent or hex forms, so 1e5 is an invalid number. Integer overflow and division by zero are not checked yet (see Current Limits). 

show(7 / 2)       # 3
show(7 / 2.0)     # 3.5
show(5.5 % 2.0)   # 1.5

Text, Output, and Logic

Text literals use double quotes and support the escapes \n, \t, \r, \\, \", and \0. A # starts a comment that runs to the end of the line. Text holds any UTF-8, but a \0 ends it early ("ab\0cd" shows as ab). show is the only builtin task: it prints an int, float, bool, or text followed by a newline (or a maybe of one: its value, or none). Floats print with up to 6 significant digits, switching to exponent form for very large or small values (123456789.0 shows as 1.23457e+08), and 0.0 / 0.0 and 1.0 / 0.0 show as nan and inf.

Logic uses words: and, or, and not work on bool, and and/or skip the right side when the left side decides the result. Conditions in when and loop must be bool: when count is an error. == and != work on numbers, bool, text (by contents), and pointers (by address); both sides must have the same type. A maybe compares only with none. 

# greet the user
show("say \"hi\"")       # say "hi"
show(2.0 / 3.0)            # 0.666667
show(1 < 2 and not false)  # true
show(1 == 1.0)             # error: expected type int, got float

Shapes

Shapes are Vela's only composite data type — like structs, but the only one.

shape Point
    x: int
    y: int
fi

bind p = Point { x: 10, y: 20 }
show(p.x)

A shape literal must give every field exactly once, in any order: Point { y: 20, x: 10 } is the same value. A shape may also have no fields (Marker {}).

Shapes and kinds can be used before they are declared. A type cannot contain itself by value, since its values would be infinitely large, but it can point to itself. A pointer always points to something, so the pointer to the next one must be a maybe: the last node has none. 

shape Node
    value: int
    next: maybe ^Node      # ok: a pointer that can be none
fi

shape Loop
    inner: Loop            # error: 'Loop' contains itself by value
fi

shape Chain
    next: ^Chain           # error: 'Chain' can never be created: field 'next' needs an existing ^Chain
fi

Assigning to a field requires the variable to be a hold; task parameters are immutable.

hold q = Point { x: 1, y: 2 }
q.x = 5                    # ok
p.x = 5                    # error: cannot assign to a field of immutable variable 'p'

Kinds

Kinds are tagged unions with exhaustive pattern matching. Each case binds the variant's payload fields in order; the bindings are visible only inside that case, so different cases may reuse names. A kind value has no fields of its own (s.radius is an error): match is the way to read a payload. 

kind Shape
    Circle(radius: float)
    Rectangle(width: float, height: float)
fi

task area(s: Shape) -> float
    match s
    case Circle r
        <- 3.14 * r * r
    case Rectangle w h
        <- w * h
    fi
fi

A match must have a case for every variant, each once; leaving one out is an error that names it. A last case _ covers every variant not matched above (it is an error when there are none left), and _ in place of a binding leaves that payload field unnamed. 

match s
case Rectangle w _
    show(w)
case _
    show("not a rectangle")
fi

A variant can have no payload. Write its value as just its name, with or without parentheses; its case binds nothing. 

kind Light
    Red
    Green
    Dimmed(level: int)
fi

bind a = Red
bind b = Green()          # same as Green
bind c = Dimmed(3)

Names

A name starts with an ASCII letter and continues with ASCII letters, digits, and _, but cannot contain __ (two underscores), which the compiler keeps for its own C names. Words that mean something in C, such as int, default, or stdout, are ordinary names in Vela.

Tasks, shapes, kinds, and variants share one namespace: no two of them can have the same name, even across different kinds, and none can be named like a builtin (int, float, bool, text, unit, show). Every type you write must be a builtin, a shape, or a kind. A variable can't take a variant's name, so a bare Red always means the variant.

Control Flow

when x > 0
    show("positive")
else
    show("non-positive")
fi

loop count < 10
    show(count)
    count = count + 1
fi

each i in 0..5
    show(i)
fi

each counts from the start of the range up to, but not including, the end. Both ends are evaluated once, before the first iteration; the loop variable is immutable. A range such as 0..5 is not a value: it can only appear in each.

loop repeats while its condition holds. There is no break or continue: end a loop through its condition, or leave the task with <-. There is no else when either; put a when inside the else.

A condition can also test a pattern with is, the same patterns a case takes. The names it binds are visible only in the block it guards (not in the else), and is must be the whole condition: combining it with and or or is an error. 

when light is Dimmed level
    show(level)
fi

loop current is {node}      # while current holds a node
    show(node^.value)
    current = node^.next
fi

Maybe and Errors

A value that might be missing has type maybe T. Wherever a maybe is expected (a typed binding, an assignment, an argument, a field, or a send), a plain value becomes one, and none is the empty one. A maybe can't be used as its value directly: m + 1 is an error, and == compares it only with none. A maybe can't hold another maybe. 

task half(n: int) -> maybe int
    when n % 2 == 0
        <- n / 2               # the int becomes a maybe int
    fi
    <- none
fi

bind m = half(7)
show(m)                    # none
show(m == none)            # true
show(m + 1)                # error: arithmetic requires numeric operands; a maybe int must be extracted first

There are three ways to get the value out. match handles both outcomes:

match half(8)
case {n}
    show(n)                # 4
case none
    show("odd")
fi

is runs a block only when there is a value (see Control Flow): when half(8) is {n}. And a plan B, a block after the value, gives the value to use when there is none: 

bind a = half(7) { 0 }            # 0
bind b = half(7) { 1 } * 10       # 10: a plan B works inside expressions
bind c = half(7) {
    show("odd, using 3")
    3                              # the last line is the value
}
bind d = half(7) {
    <-                             # or leave the task instead
}

The value before the block is evaluated once, and the block runs only when it is empty. Its last line gives the value, of the type inside the maybe; a <- in the block sends from the task as usual, and when every path through the block sends, it needs no value line. Names declared in the block stay in it, and an empty block is an error. A { after a shape's name followed by field: or } is a shape literal; any other { after a value starts a plan B, and a <- may follow it on the same line: m { <- 0 }.

A task that can fail sends T or E: its value when it works, or an error of type E, sent with <- fail error. The error type must differ from the value type, and can be any type but unit or a maybe. case {v} matches a success and case fail e an error, and a plan B's first line fail e names the error: 

kind SizeError
    Negative(value: int)
    TooBig
fi

task checked(size: int) -> int or SizeError
    when size < 0
        <- fail Negative(size)
    fi
    when size > 100
        <- fail TooBig
    fi
    <- size
fi

task main()
    bind a = checked(500) { 100 }       # ignore the error: use 100
    bind b = checked(-1) {
        fail e
        match e
        case Negative value
            show(value)            # -1
        case TooBig
            show("too big")
        fi
        0
    }
    match checked(7)
    case {size}
        show(size)                 # 7
    case fail e
        show("failed")
    fi
fi

unit or E is a task that sends nothing when it works: a bare <-, or reaching the end, succeeds, and case {_} matches that success. An error can't be dropped by accident: a call whose or result goes unused is an error, and an empty plan B, save(file) { }, ignores the error on purpose. fail binds like - and not, so an error computed with operators needs parentheses. 

task save(size: int) -> unit or text
    when size > 100
        <- fail "too big"
    fi
    show("saved")
fi

save(500)                  # error: the error 'save' may send is ignored
save(500) {
    fail reason
    show(reason)           # too big
}

Memory

Owned pointers are explicit and manually freed. No garbage collector.

bind p: ^int = new int(42)
show(p^)
p^ = 43                    # writing through a pointer is allowed, even from a bind
free(p)

new T(value) copies a value to the heap and gives back a ^T. A pointer to a shape has no fields of its own: read and write them through ^. 

bind origin = new Point(Point { x: 0, y: 0 })
origin^.x = 5
show(origin^.x)            # 5
show(origin.x)             # error: type ^Point has no fields; dereference it first, as in 'p^.x'
free(origin)

A pointer always points to something: there is no null pointer. A pointer that may be missing is a maybe ^T, which must be checked before it is used (see Maybe and Errors); it costs nothing extra, since the C it becomes is a plain pointer. free accepts a maybe ^T and does nothing for none. 

hold next: maybe ^int = none
when next == none
    next = new int(1)
fi
when next is {p}
    show(p^)                # 1
fi
show(next^)                # error: this pointer is a maybe ^int, which may be none
bind bad: ^int = none     # error: a pointer can't be none, so use 'maybe ^int'
free(next)
Note: Vela intentionally keeps memory management simple. There is no borrow checker; ownership is manual, like C but with clearer syntax. Use new/free with care: using a freed pointer, or freeing one twice, is not caught.

Complete Example

task fib(n: int) -> int
    when n < 2
        <- n
    else
        <- fib(n - 1) + fib(n - 2)
    fi
fi

task main()
    each i in 0..10
        show(fib(i))
    fi
fi

Current Limits

Vela is young. These are known, and planned for (see Future Directions):

  • The compiler reports the first error in a program, not all of them.
  • Integer overflow and division by zero are not checked: they behave as in C, where they are undefined.
  • Using a freed pointer, or freeing one twice, is not caught.
  • text is a C string, so a \0 ends it; there are no text operations besides ==, !=, and show.
  • There are no arrays, no modules (a program is one file), and no way to read input.
  • A task sends at most one value; to report two, declare a shape that holds both and send that.
  • show prints floats with 6 significant digits.
  • The order in which a call's arguments, or an operator's two sides, are evaluated isn't defined, which matters only when they call tasks that print. (Where one of them contains a plan B, they are evaluated left to right.)
  • Statements aren't yet required to end at a line break (show(1) show(2) on one line is accepted), and a text literal may contain a raw line break.
  • Code may nest at most 100 levels deep (parentheses, operators in a row, blocks inside blocks); deeper code is an error rather than a crash.

Building the Compiler

The Vela compiler is written in Rust and generates standard, portable C11, which it compiles with the C compiler named by the CC environment variable (cc by default). CC may include arguments, as in CC="ccache gcc". 

cargo build
./target/debug/vela program.vela -o program
CC=clang ./target/debug/vela program.vela -o program

vela <input.vela> [-o <output>] [--emit-c] [--check]: -o names the executable (a.out by default), --emit-c prints the generated C instead of compiling it (or, with -o, writes it to that file), --check only checks the program, without generating C or running a C compiler, -h/--help prints the usage, and --version prints the compiler's version. A file name starting with - goes after --. The exit status is 0 on success, 1 when the program can't be read or doesn't compile (in Vela or in C), and 2 for wrong arguments. 

./target/debug/vela program.vela --emit-c -o program.c
cc -std=c11 -I runtime program.c -o program -lm   # the C includes runtime/vela_rt.h

Errors point at the exact place in your source:

program.vela:3:10: error: unknown variable 'missing'
 3 |     show(missing)
   |          ^

To run the test suite (requires a C compiler, $CC or cc):

cargo test
CC=clang cargo test

Tests are plain Vela programs: tests/run/ holds programs with their expected output, tests/fail/ holds programs the compiler must reject, and every file in examples/ is checked against tests/examples/. The C generated for run tests and examples must also compile as strict ISO C11 with no warnings (-std=c11 -pedantic-errors -Wall -Wextra -Werror). Rust tests in tests/*.rs run those programs (programs.rs) and cover the command line, the library's build pipeline, the lexer, and internal compiler errors.

The compiler is also a Rust library, vela, so tools can use the language without copying it: vela::driver checks and builds programs exactly as the vela command does (and can keep a partly checked program for editors), vela::lexer::highlight splits source into tokens without stopping at errors (for editors), and lexer::KEYWORDS and ast::BUILTIN_TYPES list the language's reserved words and types.

The repository is a Cargo workspace: the compiler is the default member, and Vela Studio, the editor, lives under ide/. Plain cargo build and cargo test cover only the compiler, which has no dependencies; add --workspace to include Vela Studio's crates. Building and testing Vela Studio's page are described in its own guide. 

cargo test --workspace

To lint the compiler (or everything, with --workspace):

cargo clippy --all-targets

The compiler's own code may not use unwrap(), expect(), panic!, or unchecked indexing (enforced by lints in Cargo.toml), so problems are reported as errors instead of crashes. An error starting with internal compiler error means a bug in the compiler itself, not in your program.

Design Notes

  • Vela is intentionally small. It is not meant to replace Rust or C, but to explore how little syntax is needed for a safe, compiled systems language.
  • Memory is manually managed to avoid GC complexity while keeping the implementation approachable.
  • The compiler generates readable C, making it easy to debug and interoperate with existing C code.
  • Syntax uses keywords over punctuation to keep source code friendly and self-documenting; the few symbols (->, <-, ^) each stand for one idea.
  • Missing values and failures are types (maybe T, T or E) rather than conventions such as null pointers or error codes, so the checker makes sure they are handled.
