Vela vs. The Landscape

A practical comparison across the programming-language spectrum.

At a Glance

Vela sits in the systems-language zone: it is compiled and statically typed, and it manages memory with regions that the compiler checks, with no garbage collector. This page compares it with representatives from every level of abstraction, from bare-metal C to dynamic high-level languages like Python and JavaScript.

Performance

Vela generates plain C, so its theoretical performance ceiling is essentially the same as C, C++, Zig, and Rust. There is no interpreter and no garbage collector adding overhead; the runtime is a small C header of helpers (printing, and the region allocator).

Rust and C can still edge ahead in some micro-benchmarks because they offer finer control over aliasing and layout, but for typical programs the difference is negligible. Go, Java, and C# are fast but carry GC pauses and runtime weight. CPython and Ruby are often one or two orders of magnitude slower for CPU-bound work because they interpret dynamically typed code; JavaScript's JIT compilers narrow that gap to a small multiple of C for many workloads.

Memory

Vela manages memory with regions: region r declares an arena, new int(42) at r allocates in it, and everything in r is freed at once when the block declaring it closes. There is no free. A pointer's type names its region (^int@r), and the checker keeps pointers from being stored anywhere that outlives their region, so use-after-free and double free can't happen, with no garbage collector, reference counts, or borrow checker. The costs: memory is freed a whole region at a time, and one value's pointers all live in one region (see Memory and Regions, and Vela Regions for the full guide, its limitations, and their workarounds).

  • Rust is the safest here: its borrow checker prevents data races and use-after-free at compile time.
  • Zig makes allocators explicit and checks bounds, overflow, and more at run time in debug and safe release builds (checks that fast release builds drop), sitting between C and Rust.
  • Go, Java, C#, Python, JS, Ruby use garbage collectors, trading memory overhead and latency for convenience.
  • C++ offers RAII and smart pointers, but safety is opt-in and easy to bypass.
  • Vela's region names are a lightweight cousin of Rust's lifetimes: always one name the programmer writes, tied to a block, and never inferred across tasks. That keeps the rules few, at the price of rejecting some safe programs that Rust accepts, such as a value pointing into two regions.
Regions are the closest match to how Zig programs use arena allocators, and to the region systems of languages such as Cyclone, with the checking kept to a few rules. Allocation is a pointer bump, and freeing a region costs one call per chunk. Future Directions keeps the other options, such as move-only pointers and borrowed references, as ways to grow the model.

Build Speed

Vela's compiler is tiny and emits C quickly. The total build time is dominated by the C compiler, which is still very fast for small programs. This makes Vela competitive with C, Zig, and Go for iterative development.

  • Fast: C, Go, Zig, OCaml, Vela, Python/JS/Ruby (no compile step).
  • Moderate: Rust, Java, C#, Swift.
  • Slow: C++ and Haskell, due to templates, headers, or aggressive optimization.

Safety

Vela provides static type safety and exhaustive pattern matching on kinds, which catches many bugs at compile time: there are no implicit conversions (except that mixing int and float in arithmetic gives a float, and a plain value becomes a maybe where one is expected), every value-returning task must produce a value on every path (a <- value, or named results that are set), a missing value is a maybe T that must be checked before use (pointers can't be null), and a failure is a T or E whose error can't be ignored by accident. Memory is freed through regions, whose pointers the checker keeps from outliving them, so freed memory can't be used or freed again. Integer overflow and division by zero stop the program with a message instead of being undefined, as they are in C, and so does an index out of range of an array or slice. It is much safer than C, but its guarantees are narrower than Rust's (which also rules out data races) or those of GC'd languages.

Syntax & Complexity

Vela aims for Go-like minimalism: one way to define functions, one way to define records, one way to define unions. It avoids the dualities that plague other languages (structs vs classes, interfaces vs traits, references vs pointers).

  • Minimal: Go, Vela.
  • Moderate: C, Python, Ruby, JavaScript.
  • Complex: C++ (templates, headers), Rust (lifetimes, traits), Haskell (type classes, laziness).

Regions add the most to Vela's syntax of any feature: a region statement, @r in pointer types, and r: region parameters. That is still far less than lifetimes and borrowing, and code that doesn't use pointers never sees it.

Like Go, a Vela task can send several values — task divmod(a: int, b: int) -> int, int, then bind q, r = divmod(17, 5) — so a pair of results needs no record and no output parameter, as it does in C. Unlike Go, those values are not a tuple type of their own: they can only be received by a list of names, so there is one way to carry several values around, a shape.

Results can also be named, as in Go: -> total: int, set with total <- value and sent by reaching the end of the task. Go gives a named result its zero value, so forgetting to set it is silent; Vela has no zero values, so the compiler rejects a path that reads one, or ends, without setting it. Every line that changes what a task sends starts with a result's name and an arrow, which Go's plain = doesn't show.

Modules work much like Go's packages, but a module is one file: include shapes/geometry reads shapes/geometry.vela, whose names are written geometry.area, and include shapes/geometry (area) also brings area in, as Python's from … import does. The word is C's, but unlike #include it doesn't paste the file's text in: the file keeps its own names, and is read once however many files include it. Where Go exports a name by capitalizing it and Rust by marking it pub, everything in a Vela file is public unless marked priv, fields included, so a name's spelling never decides who can use it. There is no package manager yet.

Arrays are written as in Rust, [int; 4], and are values copied whole, as C's arrays are inside a struct. A slice, [int]@r, is Go's slice or Rust's &[T] as a pointer and a length, but like every Vela pointer it points into a region, so it can't outlive its memory; it doesn't grow, as Go's append does. Every index is checked, as in Go, Rust, and Zig's safe builds, and the length is xs.len, as in Zig.

Where Vela Fits

Vela is best understood as an experimental, teaching-friendly systems language. It is not trying to dethrone Rust or C. Instead, it demonstrates that you can have a small, fast, compiled language with modern features — pattern matching, sum types, maybe values instead of null, errors as types, memory in checked regions, and clean syntax — while staying close to the metal.

When to choose Vela: learning about compilers and language design, experiments, and small demos where you want C performance without C syntax. (Vela can't yet read input; see Current Limits.)

When to avoid Vela: production systems, large teams, programs that need growable collections, rich standard libraries, or concurrency support, and long-running programs whose data changes piece by piece, since regions free memory in bulk (see the workarounds).

Summary

Vela borrows the best ideas from the systems world — C's simplicity and speed, Rust's static safety mindset, Go's minimalism, Zig's explicit memory philosophy, and Cyclone's checked regions — while keeping the implementation small enough to understand in one sitting. It trades absolute safety for simplicity, and rich ecosystems for a clean slate. For what it is, that is exactly the point.
