Vela Future Directions

A Kimi-edition design notebook: bolder memory models, zero-cost abstractions, and ideas that push Vela's power without losing its smallness.

Language Regions Library Studio Comparison Future Future (Kimi) Safety May Waste Events

Vela is already a clean, opinionated little language. This document is a sketch of where it could go if it dared to be more ambitious — especially in memory safety, performance, and expressive power. The ideas here are meant to be inspiring rather than a rigid roadmap; some are experiments, some are long-term bets, and a few are small enough to land today.

🧠 Memory Safety: Beyond Manual new and free

Vela's memory model was explicit but unsafe: a missing free leaked, a double free corrupted, and a freed pointer could still be read. Named regions, below, have since replaced new/free (see Memory and Regions, and the guide Vela Regions). The other ideas here stay: several of them can still make regions more flexible, or cover resources other than memory. (Null is already gone: a ^T always points to something, and a pointer that can be missing is a maybe ^T.) The ideas below aim to keep the explicit feel while making common mistakes impossible — or at least caught at compile time.

🔐 Capability Ownership: own, read, write

Instead of a single ^T pointer, Vela could track capabilities at the type level. A capability says what you are allowed to do with a value, and the compiler rejects operations that don't match. 

task copy_name(own src: text) -> text
    ; `own` means this task now owns src; the caller cannot use it after.
    <- src
fi

task print_name(read name: text)
    ; `read` means immutable, temporary access. The owner keeps the value.
    show(name)
fi

task reset(hold write counter: ^int@r)
    ; `write` means mutable access to memory owned by someone else.
    counter^ = 0
fi
Pros
  • Eliminates use-after-free and double-free for owned values
  • No hidden reference counting or garbage collector
  • Capabilities are visible in types, so APIs are self-documenting
Cons
  • Requires a borrow/capability checker in the compiler
  • More concepts for beginners than today's single pointer
  • Needs careful design to keep Vela's syntax minimal
Why it's cool: it is Rust's ownership model distilled to three words. Vela could implement it as an opt-in layer: keep today's region pointers (^T@r, already checked and never null), and add own/read/write on top of them for new code.
With regions: capabilities would sit on top of region pointers rather than replace them. A read ^Node@r parameter would promise the task doesn't change the list, and read-only pointers are what would let younger data point into an older region safely; an own ^T@r could be dropped from its region early. See Ideas for regions.

🧭 Named Regions: T@arena Done

Make regions first-class and named. A value's type can include the region it lives in, and references cannot escape that region. This is stronger than arenas alone: it lets the compiler prove a reference is still valid. 

task process_files() -> int
    region arena
    bind buffer: [byte]@arena = allocate(arena, 4096)
    work(buffer)
    ; `buffer` and everything in `arena` are freed here automatically.
    <- 0
fi

A function can accept a region parameter so that callers decide where data lives: 

task load_config(arena: region) -> text@arena
    bind bytes: text@arena = read_file(arena, "config.ini")
    <- bytes
fi
Pros
  • Bulk deallocation is extremely fast
  • Region names make lifetimes explicit but not cryptic
  • Combines beautifully with capability ownership
Cons
  • Region subtyping ("this region outlives that one") adds complexity
  • Some long-lived data needs escape mechanisms
Why it's cool: regions give Vela a memory model that is safer than C's malloc/free, faster than reference counting, and simpler than a full borrow checker. Named regions make the safety visible in source code.
Implemented. Vela now works this way, spelled for the language as it is (it has no allocate): region arena declares a region freed when its block closes; new T(value) at arena (or new@arena T(value)) allocates in it, giving a ^T@arena; a task allocates in a parameter arena: region and may return -> ^T@arena; a task that only reads names the region in its types (list: maybe ^Node@r) without taking it; and a shape holding pointers lives in one region, Node@arena. There is no free, and there is no region subtyping yet: a pointer is never stored in another region. Details: Memory and Regions; the tutorial, the limitations with their workarounds, and ideas such as shapes with several regions are in Vela Regions.

🛡️ Scope Guards: defer

A small, powerful statement that schedules cleanup when the current block ends. It works with any resource, not just memory: files, locks, network sockets. 

task read_lines(path: text)
    bind f = open(path)
    defer close(f)

    loop not eof(f)
        show(read_line(f))
    fi
    ; close(f) runs here, even if a `<-` above had left the task early.
fi
Pros
  • Cleanup is written next to acquisition, not at the bottom of the block
  • Deterministic, no GC
  • Cheap to implement: the compiler emits cleanup code at block exits
Cons
  • Order of multiple defers matters and must be intuitive (LIFO is standard)
  • A deferred expression must not itself fail, or failure needs a story
Why it's cool: defer is the missing half of manual memory management. It lets Vela keep explicit ownership while removing the tedium and bug surface of matching every acquisition with a release.
With regions: memory no longer needs it, since a region is already released on every way out of its block. defer is still the right tool for everything else a block acquires, such as locks and sockets (a file is closed by the region it was opened in, see Vela Library), and the generated C would run deferred code at the same exits where regions are freed.

🎯 Niche-Optimized Nullability

Vela's maybe ^T already uses the null pointer as none, so it costs nothing extra over ^T. But Vela could go further: track which types have spare niches and use them automatically, so other maybe values need no separate flag. 

kind Option
    Some(value: int)
    None
fi

; The compiler sees that `Some` always has a non-zero tag, and stores the
; whole kind in a single int64_t: the payload when the tag is non-zero,
; and zero for `None`. No extra memory, no indirection.
Why it's cool: most languages pay for Option<T> with extra memory or branches. Vela could make nullable pointers, booleans-with-missing, and small tagged unions as cheap as their raw counterparts.

📊 Static Leak Checking

The compiler could require every resource-acquiring expression to have a matching release on every control-flow path. This is like a borrow checker but only for resources, and only forward-propagating. 

task leaky(path: text) -> int
    bind f = open(path)
    show(read_line(f))
    ; Error: `f` is owned but never closed.
    <- 0
fi

With defer, this becomes trivial to satisfy; without it, the checker demands an explicit close on every path. The rule is simple: every own value must be consumed exactly once by the end of its scope.

(This example allocated memory with new before regions existed. Regions already rule out memory leaks past a block, so the idea now matters for other resources, and for owned pointers dropped from a region early.)

Why it's cool: this is the safety benefit of Rust's Drop without the complexity of lifetimes. It catches the most common resource bug — forgetting to release something — at compile time.

⚡ Performance: Zero-Cost Power Features

Vela compiles to C, so it already inherits C's speed. The ideas below add features that let programmers express intent the C compiler cannot see on its own.

🔮 Compile-Time Execution: comptime

Let Vela run code while compiling. Use it for constants, lookup tables, parser generators, and type-driven code generation. 

comptime fib(n: int) -> int
    when n < 2
        <- n
    else
        <- fib(n - 1) + fib(n - 2)
    fi
fi

bind table: [int#10] = comptime build_lookup_table()

comptime tasks run in the compiler using the same interpreter (or the same code generator targeting a small VM). They have no I/O and no mutable global state. The result must be a constant value.

Why it's cool: metaprogramming and zero-cost abstractions become possible without a separate macro language (types a declaration takes are already there, see Types a declaration takes). Vela stays one language from runtime to compile time.

A first step is built: a macro, #SIZE = 4, is a value the compiler computes from literals, other macros, and operators, and macros that take values are planned. A comptime task would be the step after, running whole tasks.

🚀 SIMD Vector Types

Explicit vector types that map directly to CPU SIMD registers. No auto-vectorization magic, just predictable performance. 

bind a: vec4f = [1.0, 2.0, 3.0, 4.0]
bind b: vec4f = [5.0, 6.0, 7.0, 8.0]
bind c: vec4f = a + b   ; four additions in one instruction

Vectors support lane-wise arithmetic, shuffles, reductions, and masked operations. The compiler generates the right intrinsics for the target; if SIMD is unavailable, it scalarizes cleanly.

Why it's cool: Vela could become a serious language for numeric and game code without abandoning its minimalism. Vector types are small syntax with huge upside.

🧱 Controlled Shape Layout

Let programmers control how shapes are laid out in memory for cache, ABI, or hardware reasons. 

shape Vec3 packed
    x: float
    y: float
    z: float
fi

shape Header aligned(64)
    magic: int
    version: int
fi

Vela could also support field reordering hints: shape Foo hot tells the compiler to group hot fields together and pad cold fields to the end. This is information a C compiler usually ignores.

Why it's cool: systems programming sometimes needs to talk directly to hardware or squeeze cache lines. Vela can expose this power without making it the default.

🔗 Inline Assembly with Vela Types

An asm block where inputs and outputs are ordinary Vela values, type-checked by the compiler. 

task rdtsc() -> int
    hold low = 0             ; Vela has no uninitialized variables
    hold high = 0
    asm("rdtsc" : "=a"(low), "=d"(high))
    <- (high << 32) | low
fi

The compiler checks that the constraints match the Vela types, inserts the right clobbers, and forbids outputs that don't fit in a register. It is as unsafe as assembly always is, but the boundaries are typed.

Why it's cool: Vela could be used for kernel code, cryptography, and micro-optimization without dropping to a separate assembler or losing type safety at the interface.

🧬 Monomorphization Hints

Vela already makes one task or shape for every set of types a program uses (Types a declaration takes), which is the fast choice and the only one. This would let a declaration ask for the other: share one body when binary size matters more than speed. 

task max<T: ordered>(a: T, b: T) -> T inline
    when a > b
        <- a
    fi
    <- b
fi

inline names what Vela does today: a separate copy for every set of types. shared would mean one body reached through type-erased pointers, paying a call and losing the copy per type. Sharing only works where the body never needs a value's size, so the words a type is asked to allow would have to say which of them a shared body may use.

Why it's cool: generic code often hits a tension between speed and size. Letting the programmer decide, rather than the compiler guessing, is a rare power feature.

🎨 Expressiveness: More Language in Less Syntax

Vela's syntax is one of its best features. These ideas extend what a small syntax can express.

🧩 Match Expressions Done

Built on 2026-09-25, for when as well, and with both spellings a case can have: case p = value on the case's own line, or a block whose last line gives the value, the rule a plan B's block already had. -> stayed out of it, as Future Directions argued. The language guide describes it.

Let match produce a value, so it can be used on the right side of a binding. 

bind grade = match score
    case A _ -> "excellent"
    case B _ -> "good"
    case C _ -> "pass"
    case F _ -> "fail"
fi

Each branch ends with -> expr instead of <-, distinguishing match values from task returns. The compiler still checks exhaustiveness. (Future Directions argues against -> here, since it already names a task's result type, and suggests a plan B's rule instead: the last line of each case is its value.)

Why it's cool: it removes the need for helper tasks that only exist to compute a value from a kind. Less boilerplate, same safety.

🎭 Algebraic Effects

A lightweight effect system where a task can perform an effect and a caller can handle it. This unifies errors, generators, async, and dependency injection in one concept. 

effect Log
    case Message(text: text)
fi

task do_work()
    perform Log.Message("starting")
    ; ...
fi

task main()
    handle do_work()
    case Log.Message msg
        show(msg)
        resume           ; continue the caller
    fi
fi
Why it's bold: algebraic effects are powerful but can make control flow hard to follow. They fit Vela only if kept simple and explicit — no implicit effect inference, and handlers must be lexically visible.

🚦 Typestate / Session Types

Encode state machines in the type system. A file handle can be File<Open> or File<Closed>; calling read on a closed file is a compile error. A shape takes types already (Shapes that take types), so what this needs on top is types that stand for a state and hold no values, and a rule that a value of one is used once. 

shape File<State>
    fd: int
fi

task open(path: text) -> File<Open>
    ; ...
fi

task close(f: File<Open>) -> File<Closed>
    ; ...
fi

task read(f: File<Open>) -> text
    ; ...
fi

This generalizes to session types for protocols: a socket type tracks whether the next allowed action is send or receive, preventing protocol bugs at compile time.

Why it's cool: typestates turn runtime bugs into compile-time errors for resources, protocols, and UI flows. They are a natural fit for a systems language with explicit lifetimes.

📦 Derive for Shapes and Kinds

Ask the compiler to generate common tasks for a shape or kind: equality, hashing, cloning, debug printing. 

shape Point
    x: int
    y: int
derive Eq, Hash, Show
fi

bind a = Point { x: 1, y: 2 }
bind b = Point { x: 1, y: 2 }
show(a == b)   ; true, generated automatically
Partly there without a word: every value can already be shown (show(a) writes Point { x: 1, y: 2 }, see values as text) and compared item by item with ~= (a ~= b is true). a == b compares where they are, so it is false here (see Comparing). What derive would still add is hashing and copies.

Derive is implemented with compile-time reflection (or comptime code generation), so it costs nothing at runtime and adds no hidden vtables.

Why it's cool: it gives Vela the convenience of Rust's derives without adding traits or macros to the core language. Derive is just a compiler service.

🔀 Pipeline Operator

A syntax for chaining tasks left-to-right, making nested calls read more naturally. 

bind result = fetch(url)
    |> parse_json()
    |> extract_user()
    |> validate()

value |> task(args) is rewritten to task(value, args). It is pure sugar, but it makes data-flow pipelines readable without methods.

Why it's cool: it gives Vela most of the ergonomics of method chaining without adding methods, receivers, or namespaces.

🌐 Concurrency Without Shared Mutation

Vela's minimalism is a good foundation for a concurrency model that is easy to reason about. The theme is: share by communicating, and ownership travels with the message.

📬 Ownership-Transferring Channels

A channel can only carry own values. After sending, the sender can no longer use the value; the receiver becomes the sole owner. 

task worker(input: Chan[own Job], output: Chan[own Result])
    loop true
        bind job = recv(input)
        bind result = process(job)
        send(output, result)
    fi
fi

Because ownership moves, there can be no data races on the carried values. The runtime only needs to synchronize the channel itself, not the data.

With regions, a message could also carry a whole region: every pointer into it names it, so once it is sent, the sender has nothing left that points there.

Why it's cool: this is Go's channels plus Rust's ownership guarantees. It keeps the friendly syntax of channels while eliminating an entire class of concurrency bugs.

🧵 Actor-Style Tasks

A task can be spawned as an actor with its own mailbox. The actor owns its state; messages are handled sequentially. No locks, no shared mutable state. 

actor Counter
    hold count = 0

    on Increment
        count = count + 1
    fi

    on Get(reply: Chan[int])
        send(reply, count)
    fi
fi

The actor/fi syntax is just a task with a built-in message loop. The compiler guarantees that the actor's state is only touched inside its own on handlers.

Why it's cool: actors give Vela a concurrency model that is both simple and safe, with no risk of deadlocks or data races on actor state.

🧪 Smaller but Worthwhile Ideas

Refinement types Idea

bind n: int where n > 0 = 5 — the compiler checks predicates where it can, and runtime checks where it must.

Tagged pointers Idea

Small variants and booleans stored inside a pointer's unused low bits, cutting allocation for common cases.

Lazy streams Idea

each n in fib_stream() where the stream is computed on demand, backed by a generator task.

First-class assertions Idea

assert(x > 0) as a statement, compiled out in release builds or turned into traps.

Static array slices Done

[]T as a fat pointer (ptr, len) with bounds checking and no ownership. Implemented as [T]@r, a pointer and a length into a region, with every index checked; see Slices.

Named arguments Idea

resize(width: 2.0, height: 3.0) for readability, mirroring shape literals.

Source maps in generated C Idea

#line directives so C compiler errors and debuggers point at Vela source lines.

Compile-time benchmarks Idea

comptime bench fib(35) runs a benchmark during build and warns if it regresses.

✅ Already Applied in This Fork

Minor improvements that landed while writing this document:
  • --version flag: prints the compiler name and version and exits successfully.
  • --check flag: parses and type-checks a file without generating C or invoking the C compiler. Useful for editors and CI.
  • Integer literal underscores: numbers like 1_000_000 and 1_000.000_001 are accepted, with underscores ignored for readability. Malformed forms such as 1__000 or 1_ are rejected.

These are non-breaking additions: existing programs compile unchanged, and the CLI flags follow the same style as --emit-c.

Since then, a larger idea from this notebook has landed too, as a breaking change: named regions. region r, ^T@r, and new T(v) at r replaced new/free; see Vela Regions.

💡 The Kimi Take

Vela's biggest opportunity is to become a safer C that still feels like C — not a smaller Rust. That means keeping explicit memory and explicit control, but adding just enough compile-time proof to eliminate leaks, use-after-free, and data races. Named regions are now in place; defer, static leak checking for resources, borrowed slices, and the region ideas in Vela Regions would complete a memory story that is both innovative and practical.

For performance, comptime and SIMD are the high-leverage bets: they make Vela competitive with C++ and Zig without adding complexity to the everyday syntax. And for expressiveness, match expressions (now built) and derive keep Vela small while removing the boilerplate that currently forces helper tasks and hand-written equality.

Vela — small by design, with room to be bold.
