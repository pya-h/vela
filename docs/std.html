Using the library

Vela's library is a set of modules written in Vela that come with the compiler. A program brings one in the way it brings in a module of its own, with include and a path that starts with std: 

include std/files {File}          ; File, by its own name
include std/files                 ; or through the module: files.File
include std/files => disk         ; or under a name of the file's choosing: disk.File

Nothing is read from the disk to find it: the library is part of the compiler, so the command, Vela Studio, and the web editor all have the same library, and a program needs nothing installed beside the compiler. Everything the module rules say holds for it too: priv keeps what a module keeps to itself, names brought in may be renamed with =>, and a file includes each module once.

  • std is not a word. It is only the first part of a path on an include line, the way std:: starts a name in C++. A variable, a task, or a field may still be called std.
  • A module is named. include std alone is refused: 'std' is Vela's library, not one of its modules; include a module of it, as in 'include std/files'. So is a module the library doesn't have, and the message lists the ones it does.
  • A program's folder can't be called std. A module in a folder named std beside the main file would have a name that reads as the library's, so it is refused: '../std/helpers' is in a folder named 'std' beside the main file, which would read as Vela's library; give the folder another name.

std/collections

Lazy iterators and eager tasks over the items of a slice. The pattern Iterator<T> is one next() after another; a slice has its chain members (map, filter, take, skip, zip, enumerate, and the consumers collect, fold, find, all, any) in a file that includes the module, each step reading the one before it and gathering nothing until a consumer asks. zip gives Pair shapes (.first, .second) and enumerate gives Indexed (.index, .item); either side of zip may be a slice, read as its own iterator. The shapes Iterator, Pair, Indexed, and SliceIter are brought in by name; the chain members need no import, and each x in it goes through any iterator.

The eager tasks are written to be read in a pipe: each takes the slice first, then what it does with an item (a task value, or a one-line lambda, whose types the slice tells), then, for those that make a new slice, the region it goes in, last, so at r gives it. Brought in with include std/collections (map, filter), or named collections.map(…) after include std/collections. 

include std/collections (map, filter, fold, take)

task main()
    region r
    fixed nums = new [int]([1, 2, 3, 4, 5]) at r
    show(nums |> filter(n -> n > 2) at r |> map(n -> n * 10) at r)   ; [30, 40, 50]
    show(nums |> fold(0, (sum, n) -> sum + n))                   ; 15
    show(nums |> take(2))                                          ; [1, 2], a view of nums
fi
TaskWhat it gives
map(xs, f, r) -> [R]@ra new slice in r of what f gives for each item, in order
filter(xs, keep, r) -> [T]@ra new slice in r of the items keep holds for, in order
fold(xs, initial, step) -> Ainitial, then step of it and each item in turn: fold(xs, 0, (sum, n) -> sum + n) adds them up; makes no memory
zip(xs, ys, r) -> [(A, B)]@ra new slice in r of pairs of the items at the same place, as long as the shorter slice
enumerate(xs, r) -> [(int, T)]@ra new slice in r of each item with its place, from 0
take(xs, n) -> [T]@athe first n items, a view of the same slice; all of them when it has fewer, none when n is below 1
skip(xs, n) -> [T]@athe items after the first n, a view of the same slice; none when it has n or fewer
find(xs, test) -> maybe Tthe first item test holds for, or none
all(xs, test) -> boolwhether test holds for every item; true for none
any(xs, test) -> boolwhether test holds for some item; false for none
  • Eager. Each task goes through all the items when it is called, and map, filter, zip and enumerate make their slice at once, so a pipe of two of them makes one slice in between. Lazy chains that make nothing until collected are planned (see Iterators & Collection Pipelines).
  • Slices only. An array never becomes a slice, so [1, 2, 3] |> map(…) is refused with a message saying so: write the values as a slice, [1, 2, 3] at r, or copy them into one.
  • zip and enumerate make tuples, whose items never change, so their items are frozen types: numbers, bools, text, and tuples and shapes of those, not slices or pointers.
  • A lambda takes nothing from the code around it, so a one-line lambda given here reads only its item and what the file declares, and makes no memory in a region of the caller; one that keeps what it uses ([@r]) goes only where the task's type says [@r], which these don't.

std/files

Files on the disk. A File is made from its path, and making one opens nothing: it is a value that names a file, which its methods ask about, open, read, write, rename, and delete. A file is opened in a region, which closes it when its block ends, as it frees its memory (a block … fi makes a block anywhere, for just that); close() closes it sooner. Everything that touches the disk can fail, with a FileError that a plan B handles. 

include std/files {File, FileMode}

task main()
    region r
    flex notes = File { path: "notes.txt" }
    notes.open(FileMode.Write) at r { failure e
        show("could not open it")
    }
    notes.write("first line\n") { failure e
        show("could not write")
    }
    notes.close() { failure e
        show("could not close")
    }
    notes.open(FileMode.Read) at r { failure e
        show("could not open it")
    }
    loop notes.line() at r { none } is {line}
        show(line)                  ; first line
    fi
fi                              ; r's block ends, and closes the file

File

The methods marked alters change the File, so they are called on a flex variable (or through a pointer). The ones that take a region take it last, so it is written after the call: notes.read() at r, as any such call may.

Regions and copies

The region a file is opened in owns it: when the region's block ends, the file is closed, even when a File naming it lives on outside the block. A File is a value, and a copy of it names the same open file, so closing either closes it for both. Neither can tell the File they didn't close, so its state still says Open until one of its own methods finds out: every method then finds the file closed, and fails with NotOpen, never reaching a file opened since (a close() that finds it so sets state to Closed). The state is what the File's methods left it, and what the file is, its methods tell. 

region r
flex kept = File { path: "notes.txt" }
each pass in 0..1
    region round
    kept.open(FileMode.Read) at round { failure e
        show("could not open it")
    }
fi                                  ; round's block ends, and closes the file
show(kept.str() at r)                ; notes.txt (open): what open left it
show(kept.line() at r { failure e
    "closed"                        ; NotOpen, so the plan B runs
})                                  ; { "closed" }: line() gives a maybe text, none at the end

examples/files.vela is a whole program: a list written to a file, added to, read back line by line, and deleted.

std/int512

512-bit signed integers in two's complement, Int512. Brought in with include std/int512 {Int512, int512, zero512}. A value is held across eight 64-bit unsigned limbs, lowest limb first. Every arithmetic operation strictly follows Vela's checked-arithmetic safety: any overflow past 512 bits or division by zero immediately stops the program with an informative runtime trap. Int512 follows the module's Numeric<T> pattern, so it also answers the operators the pattern names: a + b, a * b, -a, and a < b read as the methods plus, times, neg, and cmp, both operands Int512. 

include std/int512 {Int512, int512, int512_parse}

task main()
    region r
    fixed a = int512(1000)
    fixed b = int512_parse("98765432101234567890") { Int512.zero() }
    fixed c = a.times(b)
    show(c.str(r))                          ; 98765432101234567890000
    show("{a} / 3 = {a.div(int512(3))}" at r)
fi

std/loops

What a loop that gives a value fails with, LoopResult<B, M>: a kind that takes types, written in Vela. A loop gives a value in any file, with or without this module; a file that writes LoopResult itself, in a type or a variant, brings it in by name (unknown type 'LoopResult'; it is in Vela's library, and 'include std/loops {LoopResult}' brings it in). A case Broke b on a loop's failure names no kind, and needs no include. 

include std/loops {LoopResult}

task main()
    flex last = 0
    fixed found: int ~ LoopResult = each x in [2, 7, 4]
        when x > 5
            break = x
        fi
        last = x
    finally
        when last == 4 fail LoopResult.Manual("four") else last fi
    fi
    show(found { 0 })                  ; 0: a break stopped it at 7
fi
VariantWhy the loop has no value
Skippedits body never ran: the condition failed at once, or there was nothing to go through
Broke(value: maybe B)a break stopped it, with what break = v gave, or none
EndedByContinueits final pass ended with continue, before the last line
Manual(value: M)the last line of its final pass failed with fail LoopResult.Manual(m)

B is what the loop's breaks give and M what its last lines fail with, each taken from the place the value goes where the loop gives none, and bool where no place names it either. On a loop's own variable, a bare LoopResult takes the loop's types, as found does above; anywhere else they are written, LoopResult<int, text>.

std/math

Numbers beyond arithmetic: the macros P (pi) and e, and tasks for powers, trigonometry, exponentials, and logarithms. Every task takes and gives floats, so an int is written as a float (math.sin(1.0)) or turned into one (math.sin(float(n))). Angles are in radians. 

include std/math (P, e, sin)

task main()
    show(sin(P / 2.0))              ; 1
    show(math.cos(P))               ; -1
    show(e ** 2.0)                  ; 7.38906, computed as math.exp(2.0)
    show(math.log(1000.0))          ; 3, base 10 when none is given
    show(math.log(8.0, 2.0))        ; 3
    show(math.log(e, e))            ; 1, the natural logarithm
fi

A value outside what a task takes gives what C's gives, as float arithmetic does: math.log(-1.0) and math.asin(2.0) are nan, and math.log(0.0) is -inf. Nothing stops the program. math.P and math.e are macros, so nothing can change them ('P' is a macro, a value that never changes, not a variable), and a file that brings in e by name can't name a variable e; one that writes math.e can.

std/web

Non-blocking networking, HTTP/1.1 request/response shapes, pattern-matching routers, decorator-based route registration, and composable call-time middleware. Brought in with include std/web {Socket, Request, Response, Method, WebError, get, post, serve} or include std/web => web. See also the architectural guide in docs/web.html. 

include std/web {Socket, Request, Response, WebError, get, post, serve}

task auth(next: (Request@r, @r) -> Response@r ~ WebError@r, req: Request@r, r: region default) -> Response@r ~ WebError@r
    when req.header("authorization") is {token}
        when token == "Bearer secret"
            <- next(req, r)
        fi
    fi
    <- fail WebError.Unauthorized("invalid token")
fi

$get("/greeting/\{name\}")
task greet(req: Request@r, r: region default) -> Response@r ~ WebError@r
    fixed name = req.param("name") { "friend" }
    <- Response.text("Hello, {name}!\n" at r, r)
fi

$get("/secret")
$(auth)
task secret_panel(req: Request@r, r: region default) -> Response@r ~ WebError@r
    <- Response.text("Confidential data\n", r)
fi

task main()
    serve("127.0.0.1:8080") { failure err
        show("server stopped: ", err)
    }
fi

  • Path parameters and wildcards. Patterns like /users/\{id\} capture dynamic path segments accessible via req.param("id"). Wildcards like /assets/* capture remaining path text via req.param("*").
  • Method-aware routing. If a route's path matches but the request method does not, the router automatically fails with WebError.MethodNotAllowed, yielding HTTP 405. If no route matches, it fails with WebError.RouteNotFound, yielding HTTP 404.
  • Composable middleware. Decorators like $(auth, logged) wrap handlers at call time, intercepting requests and short-circuiting on failure with typed errors such as WebError.Unauthorized.
  • Event loop, keep-alive, and timeouts. The single-threaded event loop multiplexes connections using non-blocking I/O. HTTP/1.1 connections remain persistent by default; idle sockets past idle_timeout_ms are swept, stalled partial reads past read_timeout_ms are closed with 408 Request Timeout, and Server.stop() shuts down gracefully.

How the library is made

The library is Vela source in the repository's std/ folder, which the compiler holds as it is built. Most of it is Vela like any program's. What Vela itself can't do, such as asking the system about a file, is a native task: its header is Vela, and its body is a function of the runtime that the generated C includes. 

; std/files.vela
priv native task path_exists(path: text@p) -> bool

A native task has no body and no fi, and the compiler writes its body as a call of the runtime function src/library.rs names for it. Only the library has them: in a program, native task is refused ('native' marks a task whose body the compiler writes in C, which only Vela's library has), so the library is not a way to call any C a program likes. Like read, native is a word only there, so a program may still name anything native. The runtime's functions use standard C11 alone, so a program that uses the library builds wherever any other does. std/math's tasks are native ones whose bodies are C's own functions of math.h, and its P and e are macros like any program's.
