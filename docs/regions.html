1. The idea

A region is a named place to put memory. You declare one with region r, and new T(value) at r copies a value into it and gives you a pointer to the copy. Nothing in a region is freed on its own. Instead, the whole region is freed at once, when the block that declared it ends.

Think of a whiteboard in a meeting room: during the meeting anyone can write on it, and when the meeting ends it is wiped clean in one go. Nobody erases single words, and nobody can read the board after it was wiped, because the meeting (the block) is over.

What makes Vela's regions safe is that the region's name is part of every pointer's type. A ^Node@nodes is "a pointer to a Node in region nodes". A type can only name a region that exists where the type is written, so a pointer can never be kept anywhere that lives longer than its region. The compiler checks this with a few simple rules, and nothing is checked at run time. 

task main()
    region scratch                     ; a new, empty region
    fixed n = new int(42) at scratch    ; n has type ^int@scratch
    show(n^)                           ; 42
fi                                     ; scratch, and everything in it, is freed here

The whole model in five rules

  1. region r declares a region; new T(v) at r, or new@r T(v), allocates in it. region r default makes r the block's default, and then what allocates there names no region.
  2. A pointer into r has type ^T@r, and a type can only name regions visible where it is written.
  3. When the block declaring r ends, however it ends, everything in r is freed.
  4. A task allocates only in a region it takes as a parameter (r: region); it can read and link pointers in any region its parameters' types name.
  5. A pointer is never stored in a different region than the one its type names.

2. Why Vela has regions

Most Vela values don't need any of this. Numbers, bools, shapes, and kinds are copied when they are assigned or passed, and live in the block that declares them (When a type needs a region is the full answer to which values do). But some data can't work that way:

  • Linked data, such as lists, trees, and graphs, where one value points to another.
  • Shared data, where several places must see and change the same value.
  • Data that outlives a call, built by one task and used by its caller.

These need pointers to memory allocated somewhere else. Before regions, Vela did this the way C does: new allocated a value, and free(p) gave it back. That is simple, and it is where the classic memory bugs come from: 

; Vela before regions: this no longer compiles.
task main()
    fixed p = new int(1)
    free(p)
    show(p^)          ; use after free: reads memory that may belong to something else
    free(p)           ; double free: corrupts the allocator
    fixed q = new int(2)
fi                    ; q is never freed: a leak

Nothing in the language stopped any of these. Languages solve this in a few ways, and each has a price:

ApproachUsed byWhat it costs
Garbage collectionGo, Java, C#A runtime that pauses or slows the program, and memory freed "later" rather than at a known point

Borrow checkerRustLifetimes and borrowing rules to learn, and a large, complex checker

Vela chose regions (the full comparison is in Future Directions), because they fit what Vela wants to be:

  • Minimal. One statement (region), one type annotation (@r), one parameter type (region). There are no lifetimes to infer and no borrowing rules.
  • Explicit. You can see where memory lives (the region's name) and when it goes away (the end of the region's block).
  • Fast. Allocating is a pointer bump, and freeing a region frees all its values at once.
  • Checkable. Safety follows from a handful of local type rules, all checked at compile time.
  • Plain C. The generated C is an ordinary local variable and a function call at each block exit.

3. What regions guarantee

If a Vela program compiles:

  • No use after free. No variable, field, or result can hold a pointer after its region is freed, because its type would have to name a region that no longer exists.
  • No double free. Only the compiler frees memory, once per region, and there is no free.
  • No leaks past a block. Every way out of a block frees its regions: its fi, the end of a plan B block, and a <- from anywhere inside it.
  • No null pointers. A ^T@r always points to something; one that may be missing is a maybe ^T@r, which must be checked before use (see Maybe and Errors).
  • No hidden costs. No garbage collector, no reference counts, and no run-time checks when a pointer is used.

What they don't promise:

  • Bounded memory. A long-lived region keeps growing while you allocate in it, even if old values are no longer used. Choosing regions well (see Choosing regions) is how you keep memory flat.
  • Surviving out of memory. If the system has no memory left, the program prints vela: out of memory and stops.

4. Pros and cons

Pros

  • Memory safety checked entirely at compile time, with nothing to pay at run time
  • Very fast allocation (a pointer bump) and freeing (one call per chunk of memory, not per value)
  • Good cache locality: values allocated together sit next to each other
  • Lifetimes are blocks you can see, named in types you can read
  • Few rules to learn; no lifetime annotations beyond a region's name
  • Tasks that only read are generic over regions for free (no extra argument), as they are over the types they take (Types a declaration takes)
  • A natural fit for work that happens in phases: a request, a frame, a loop pass, a compiler pass

Cons

  • One value can't be freed early; memory goes a whole region at a time
  • Data that changes over a long run needs care, or its region keeps growing
  • A value holds pointers into one region only, and a pointer can't be copied into another region
  • Region names appear in signatures, and tasks that allocate take an extra argument (though a block can name a default region, so the lines inside it needn't repeat it)
  • Some safe programs are rejected (see Limitations)
  • Regions aren't values: a program can't choose a region at run time or keep a list of regions

5. When a type needs a region

The question that comes up first, and keeps coming up, is: does this type name a region or not? The short answer is the one you would guess — memory that would be on the heap in C goes in a region — but it is worth seeing why, because the rule then answers every case, including the one type that goes both ways.

Where a value's bytes are

Every byte in a running Vela program is in one of three places, and each has its own answer to "when is it freed?":

  1. In the value itself. A number, a bool, an array of a known size, a shape of such fields: the bytes sit in the variable, the field, or the parameter that holds them, and are copied when the value is. Their size is known as the program is compiled. Freed when the variable's block ends, automatically, with nothing to say about it. In C: a local variable or a field.
  2. In the program. The bytes of a text literal are in the compiled program, put there before main starts. Never freed. In C: a string literal in static storage.
  3. In a region. Bytes the program asked for while it was running, because their size or their number wasn't known before: what a pointer points at, a slice's items, text built out of other text. Freed when the region's block ends. In C: the heap, taken from a region's chunks.

Only the third kind needs a name, and that is the whole reason regions are in types. For the first two, the compiler already knows the answer to "when do these bytes go away?" — with the block, or never. For the third, the answer is "when that region ends", and a pointer can be stored anywhere; without the region's name in the type, there would be nothing to compare when the pointer is stored somewhere longer-lived. So:

A type names a region exactly when a value of it can reach bytes the program made while it was running. Three types do: a pointer ^T@r, a slice [T]@r, and text made rather than written, text@r. Every other type names a region only because it holds one of those.

Note what this is not about. It isn't about how big the value is: a [int#1000] is eight thousand bytes and needs no region, because they are part of the value. It isn't about being changed: a flex variable of any plain type changes in place. And it isn't about being passed around: plain values are copied into a task and copied back out, which needs no shared memory at all.

Text, the one that goes both ways

Text is the one type the answer isn't settled for: the same text is sometimes in a region and sometimes not, and a shape or kind holding text follows its text. That is why it causes most of the questions, and the reason is simple: a text is a pointer and a length, and the bytes it points at are either in the program (a literal, written in the source, there before the program starts) or in a region (made while running, out of other text or out of a number). So the test is not what the text says but where its bytes came from: text you wrote needs no region; text the program made needs one.

The two never mix in the wrong direction. Text that lasts fits anywhere text of a region is expected, since it outlives every region; text of a region can't be kept in a text, which would outlive it (that limitation, and .copy() is the way across). And a task that reads text of a region names the region in its header, title: text@r, exactly as it would for a pointer.

What a value holds decides for it

A shape or a kind is in a region when anything it holds is — a pointer, a slice, text made while running, or another shape or kind that is. Its fields never name a region: they are all in the one region of the value that holds them, which is what Node@r says. That is also why one value can't hold pointers into two regions (this limitation): @r is one name for all of it.

A shape holding only text is the case where both exist, and the same declaration serves both: Person is a person whose name is a literal, Person@r one whose name was read or built in r. A kind is the same, variant by variant: Status.Todo holds nothing and fits any region, Status.Blocked(reason) holds text, so it is in the region that text is in.

Tuples work the other way around, because their items never change: a tuple holds no pointer and no slice at all, and each item keeps its own type, so (text@a, text@b) — text of two different regions in one value — is fine, where a shape with two such fields is not. maybe and ~ only wrap: whether maybe ^Node@r is in a region is decided by the ^Node@r inside it.

One case looks like a region and isn't: a value built with no pointers in it yet, such as Leaf(1) or Node { value: 1, next: none }. It fits into any region, so nothing in it fixes one; that is why such a value needs its region written where it is bound (flex head: Node@nodes = …), and why the compiler writes @_ for "no region" when it talks about one (this limitation).

When a region is an argument, and when a name is enough

The second half of the question is about headers. A task can always read data in a region it merely names in a type; it can only allocate in a region it was given as a parameter or declared itself. So the test is not whether a task touches memory in a region, but whether it makes any:

task largest(list: maybe ^Node@r) -> int

    flex most = 0

largest is the one to notice: it allocates a slice on every call, and its header says nothing about regions, because that memory is nobody else's business — it is freed at the task's fi. Taking r: region there would be wrong twice over: the caller would pay for it, and the scratch items would stay in the caller's region until its block ended.

Three rules follow from the same place, and each has its own message when it is broken:

  • A named region can't be allocated in. @r in a type is a name for whatever region the caller's value was in; there is no region to allocate with, which is exactly what makes the task free to call. Writing new … at r there says this task can't allocate in 'r', which it only names in its types; take it as a parameter, 'r: region'. The same goes for making text and for add on a slice, which may need more room.
  • A result's region must be a parameter's. A region the task declares is freed when it returns, so nothing it sends can point into it; a region only the result names isn't accepted either (why, and the workaround).
  • The same name means the same region. Two parameters written @r must be in one region, and two written @x and @y may differ, which is what lets a task link two lists safely or refuse to (Lesson 5).

Where a region is an argument, it is passed by name at the call, push(nodes, list, i), even inside a block with a default region: a default settles where an allocation goes, not which region a task is handed. And .copy() takes its region from the place the copy goes, so a copy needs one written only where nothing else names it.

Deciding, in order

  1. Does the value hold a pointer, a slice, or text the program made? If not, there is no region to write, and nothing to pass: use it as a plain value.
  2. If it does, when should its memory go away? Declare the region in the block that ends then: the top of main for data the whole program uses, inside the loop for data of one pass.
  3. Who makes it? The task that allocates needs the region — as a parameter when the caller keeps the result, as its own region when the memory is scratch.
  4. Who else touches it? Everything that only reads, walks, or links it names the region in its types and takes nothing.
  5. Does one region do nearly all the work in the block? Then name it the block's default and let the lines that go elsewhere be the ones that say so.

Questions that come up

  • Does a big array need a region? No. [int#1000] is part of its value however large it is; it makes the value large. A number of items known only while running is a slice, which does need one.
  • My task allocates, but gives back an int. Then it needs no region in its header: declare one in its body (the first limitation shows the shape of it).
  • Does printing a shape of mine need a region? No. show writes the text of each value into a region it makes for the line and frees straight after, so printing needs no region of yours; one you declare is for text you keep, pass on, or send back.
  • Two regions in one value? Not in a shape or a kind — all of one value is in one region. A tuple of text can hold two, a task can send several results in different regions (-> ^int@a, ^int@b), and .copy() moves data across.
  • Can the program pick a region while it runs? No: a region is not a value (why). Call the task in both branches of a when instead.
  • What should a task that takes text write? name: text@r, nearly always: it takes text of any region and literals, since text that lasts fits everywhere. name: text takes only text that lasts, which is right for a task that keeps what it is given beyond any region.
  • How do I check where a value really went? Hover it in Vela Studio: it shows the type Vela worked out, fixed p: ^int@kept. That is the quickest way to confirm an allocation landed where you meant — including one that named no region because the block has a default.

6. Tutorial

The lessons build on each other. Each program is complete: save it as a .vela file and run it with vela file.vela -o file && ./file, or open it in Vela Studio and press F5.

Lesson 1: A first region

task main()
    region scratch
    flex count = new int(41) at scratch
    count^ = count^ + 1
    show(count^)
fi
42

region scratch is a statement: from here to the end of the block (the task), scratch is a region you can allocate in. new int(41) at scratch copies 41 into it and gives back a pointer, so count has type ^int@scratch. count^ is the value it points to, which you can read and write, since count is a flex: through a fixed, nothing changes, not even the value it points to. At the task's fi, the region is freed.

Lesson 2: Pointer types name their region

shape Point
    x: int
    y: int
fi

task main()
    region points
    flex p: ^Point@points = new Point(Point { x: 1, y: 2 }) at points
    flex q = new@points Point(Point { x: 3, y: 4 })
    p^.x = p^.x + q^.x
    show(p^.x)

    flex spare: maybe ^Point@points = none
    when spare is {s}
        show(s^.y)
    else
        show("no spare yet")
    fi
    spare = q
    show(spare { p }^.y)
fi
4
no spare yet
4
  • new Point(v) at points and new@points Point(v) mean the same thing; use whichever reads better.
  • A pointer's type is ^T@r. You can write it out (p: ^Point@points) or let Vela infer it (q).
  • The type after new names no region (new Point(…), not new Point@points(…)): what it makes lives in the region it allocates in.
  • A pointer to a shape has no fields; go through ^: p^.x.
  • A pointer is never none. A pointer that may be missing is a maybe ^Point@points, read with is, match, or a plan B (spare { p } is spare's pointer, or p when there is none).

Lesson 3: When memory is freed

task first_square_over(limit: int) -> int
    region work
    each i in 0..100
        fixed square = new int(i * i) at work
        when square^ > limit
            <- square^
        fi
    fi
    <- -1
fi

task main()
    region outer
    flex total = new int(0) at outer
    each round in 0..3
        region pass
        fixed step = new int(round * 10) at pass
        total^ = total^ + step^
    fi
    show(total^)
    show(first_square_over(50))

    fixed missing: maybe int = none
    fixed rescued = missing {
        region rescue
        fixed spare = new int(7) at rescue
        spare^ * 6
    }
    show(rescued)
fi
30
64
42

A region is freed when the block that declares it ends, whichever way it ends:

  • At its fi. A region declared in a loop's body is a new region on every pass and is freed at the end of each pass, so pass never holds more than one value. This is how a loop allocates without growing.
  • At a <-. In first_square_over, the send frees work (after computing square^, the value it sends), even though it happens deep inside a loop.
  • At the end of a plan B's block, after its last line has given its value.
  • At the fi of a block, a block of its own, written anywhere a statement is, for a region (and the files opened in it) that should end before the task does, with no loop or condition around it.

Notice that total lives in outer, declared before the loop: values that must survive every pass go in a region outside the loop, and values for one pass go in a region inside it.

Lesson 4: Linked data

shape Node
    value: int
    next: maybe ^Node
fi

task push(r: region, list: maybe ^Node@r, value: int) -> ^Node@r
    <- new Node(Node { value: value, next: list }) at r
fi

task sum(list: maybe ^Node@r) -> int
    when list is {node}
        <- node^.value + sum(node^.next)
    fi
    <- 0
fi

task main()
    region nodes
    flex list: maybe ^Node@nodes = none
    each i in 1..6
        list = push(nodes, list, i)
    fi
    show(sum(list))
    show(sum(none))
fi
15
0
  • In the shape, the field next: maybe ^Node names no region. A field's pointers are in the region of the value that holds them.
  • push allocates, so it takes the region to allocate in as a parameter, r: region, and its result is a pointer into it, ^Node@r. The caller decides where the list lives: push(nodes, list, i).
  • sum only reads, so it just names a region in its parameter's type, @r, without taking it. It works on a list in any region, and costs nothing extra at run time. sum(none) works too. It calls itself for the rest of the list rather than moving a flex cursor along it, since its parameter is a fixed name and no flex name may be given what one owns (see What a fixed name owns).

Lesson 8: Scratch work, and keeping what survives

A common shape for a program is: do some work that creates a lot of temporary data, keep a small result, and throw the rest away. With regions, the temporary data goes in a region inside the work's block, and the result is copied into a region outside it: 

shape Node
    value: int
    next: maybe ^Node
fi

task push(r: region, list: maybe ^Node@r, value: int) -> ^Node@r
    <- new Node(Node { value: value, next: list }) at r
fi

task sum(list: maybe ^Node@r) -> int
    when list is {node}
        <- node^.value + sum(node^.next)
    fi
    <- 0
fi

task main()
    region kept
    flex best: maybe ^Node@kept = none
    each round in 0..3
        region work
        flex draft: maybe ^Node@work = none
        each i in 0..round + 2
            draft = push(work, draft, i)
        fi
        when sum(draft) > sum(best)
            best = draft.copy()                    ; every node, into kept
        fi
    fi
    show(sum(best))
fi
6

A pointer into work can't be stored in best, which lives in kept (that would leave best pointing at freed memory after the pass). So draft.copy() copies the list into kept, the region best names: every node, following the pointers. Each pass's draft is freed at the end of the pass, so only the lists that were copied stay allocated. A copy keeps a node two pointers share as one node, and copies a cycle as a cycle; where nothing names the region to copy into, write it: draft.copy() at kept (or draft.copy()@kept). See Copying into another region for what a copy covers.

Lesson 9: Slices in a region

An array in a variable, [int#4], is a value like any other and needs no region. When the number of items is known only as the program runs, they go in a region, as a slice: [int]@r is a pointer to the first and a count, and follows every rule a pointer does. new [int](…) at r makes one, copying the items in; xs[a..b] views part of it without copying:

Lesson 10: A default region

Writing at r on every line that allocates says where memory goes, and in a block where nearly everything goes to one region it says it over and over. A block may name one of its regions its default: what allocates there needs no at r, and only the lines that go somewhere else name a region. 

task collect(r: region default, upto: int) -> [text]@r
    flex lines = new [text]()             ; in r, the region this task was given
    each n in 1..upto
        lines.add("line " + n.str())      ; the join and the number, both in r
    fi
    <- lines
fi

task main()
    region kept default
    fixed lines = collect(kept, 4)
    each line in lines
        show(line)
    fi
    each round in 0..2
        region pass default              ; the inner block's own default
        fixed note = "pass " + round.str()  ; text@pass: freed at the end of the pass
        show(note)
    fi
    fixed after = new int(1)             ; ^int@kept: the outer default again
    show(after^)
fi

The rules are few, and the types don't change: a value allocated in the default still has the region in its type (^int@kept), which is what keeps it from outliving its memory, and what hover in Vela Studio shows.

  • One per block. A second default in one block is an error: two lines that look alike would allocate in regions with different lifetimes. An inner block may name its own, and after it the enclosing default is in force again.
  • A region a task is given can be one (r: region default), which is where at r repeats most. A region the header only names can't: nothing can allocate there.
  • Everything that makes memory takes it: new, new [T](…), joining text, text holding values, x.str() and text(x), scan(prompt), and a call of a task or method that takes its region last and leaves it out (label(n)). A region a task takes anywhere else is still passed by name: collect(kept, 4).
  • A copy is the exception. x.copy() goes where the value it becomes goes, which says more than a default could, so a copy that nothing gives a region still asks for one.
  • It is opt-in. A block that names no default is exactly as it was: every allocation there names its region.

When to reach for it: a task or a block where one region does nearly all the work. When not to: a block that allocates into two regions in turn, where the names are the point — as in Lesson 8, where scratch work and what survives sit side by side.

Lesson 11: Choosing regions

Rules of thumb, once which types need a region is settled:

  • Match regions to lifetimes. Declare a region in the block whose end is when the data stops being needed. Data for the whole program: a region at the top of main. Data for one request, frame, or loop pass: a region inside that block.
  • Let callers choose. A task that builds data for its caller takes r: region. A task that only reads names the region in its types. A task's own temporary data goes in a region it declares.
  • Don't replace values in a long-lived region inside a long loop. Each new adds memory that stays until the region is freed. To change a value, write through the pointer (p^ = v); for temporary values, use a region inside the loop.
  • Prefer plain values when you can. A Point or a small shape passed by value needs no region at all. Reach for pointers when data is linked, shared, or must be changed by another task.
  • Copy out to keep a little of a lot. Build in a scratch region, copy the result into a longer-lived one with .copy() (Lesson 8).
  • Name a default where one region does the work. In a block or a task where nearly everything goes to one region, region r default (Lesson 10) leaves the region written on the lines that go somewhere else, which are the ones worth noticing. Where two regions share a block, as in Lesson 8, write both.

7. How it runs

A region is a list of chunks of memory. new takes the next free bytes of the newest chunk, aligned for the type, and copies the value in: a few instructions. When the chunk is full, a new one is added, twice as large as the last, starting at 4 KB and growing up to 1 MB. An allocation too large for that gets a chunk of exactly its size, placed behind the newest chunk, which keeps serving small allocations. Freeing a region frees its chunks, however many values they hold. A region that never allocates costs nothing.

The generated C for Lesson 1's main (vela 01_first.vela --emit-c):

void vela_main(void) {
    vela__rt__region scratch[1] = { VELA__RT__REGION_EMPTY };
    int64_t* count = ((int64_t*)vela__rt__new(scratch, (int64_t[1]){ 41 }, sizeof(int64_t), _Alignof(int64_t)));
    (*(count)) = (vela__rt__add((*(count)), 1, "4:21 in task 'main'"));
    vela__rt__show_int((*(count)));
    vela__rt__region_free(scratch);
    return;
}

A region parameter is a plain vela__rt__region*; region names in types disappear, since C doesn't need them. A copy (value.copy()) is a generated function per type that copies the value's bytes, then its text, its slices' items, and what its pointers point to; each pointed-to value is copied once, remembered in a table, and waits in a list rather than in a C call, so a long list copies without deep recursion. The allocator is about a hundred lines in runtime/vela_rt.h, and the test suite runs the region programs in tests/run and examples under AddressSanitizer and UndefinedBehaviorSanitizer, with leak detection.

8. Limitations and workarounds

Regions trade some flexibility for simplicity. Some of these limits are part of the model; others reject programs that would be safe, because the rules that would accept them would be more complicated. Ideas for regions discusses how each could be lifted.

One value can't be freed early

Memory is returned a whole region at a time; free(p) is an error. A big temporary value stays allocated until its region's block ends.

Workaround: give short-lived data a region of its own, in the smallest block that holds its use, such as a helper task or a loop body. Return plain values, or copy what must survive.

shape Report
    lines: int
    total: int
fi

task summarize(count: int) -> Report
    region work                          ; only this call's scratch data
    flex sum = new int(0) at work
    each i in 0..count
        sum^ = sum^ + i
    fi
    <- Report { lines: count, total: sum^ }
fi

task main()
    fixed report = summarize(5)
    show(report.total)
fi
10

Replacing a value in a long-lived region keeps the old one's memory

Text of a region can't become text that lasts

flex chosen = "nothing"

; error: expected type text, got text@items; this text is in region 'items', and text here must last as long as the program

Workaround: keep the text where its region is known: a text@items variable, a shape named with the region (Person@items), or a slice in it. A task that reads it names the region in its header (title: text@r). To keep it longer, copy it into a region that lives longer: kept_title = item^.title.copy(), where kept_title is a text@kept.

Younger data can't point at older data

A node in an inner region pointing at a node in an outer region would be safe, since the outer region lives longer. But a value's pointers are all in its own region, so this is rejected:

    region inner
    fixed leaf = new Node(Node { value: 2, next: root }) at inner
    ; error: expected type Node@inner, got Node@outer; a value can't move to another region
fi

A task that only names a region can't allocate in it

task grow(list: maybe ^Node@r) -> ^Node@r
    <- new Node(Node { value: 1, next: list }) at r
    ; error: this task can't allocate in 'r', which it only names in its types; take it as a parameter, 'r: region'
fi

A named region has no run-time handle to allocate with; that is what makes such tasks free to call. Workaround: take the region as a parameter, task grow(r: region, list: maybe ^Node@r).

A method can't allocate in its value's region

shape Bag
    items: [int]

    alters put(value: int)
        .items.add(value)
        ; error: adding to a slice may need more room in its region, and '@this' is the region the value
        ;   this method is called on lives in, which a method isn't given, so it can't allocate there, and a
        ;   region it takes is another one, which the value can't point into; add to it where the value is
        ;   kept, outside the method
    fi
fi

A method is given the value it is called on, and @this only names that value's region in its types, as a task's named region does (above). A region parameter is another region, which the value can't point into. Workaround: grow the value where it is kept, bag.items.add(v), or bag^.items.add(v) behind a pointer. Giving an alters method its value's region is an idea for later.

Regions aren't values

A region can't be stored in a variable or field, sent from a task, or chosen at run time, and a task can't make a region for its caller: task fresh() -> ^int@r with a region r inside is an error, because r is freed when fresh returns.

Workaround: declare the region in the caller and pass it down; to pick between two regions, call the task in both branches of a when.

A task can't send a pointer-free value in a region none of its parameters names

task leaf() -> Tree@r
    <- Leaf(1)
    ; error: the result lives in region 'r', which the task isn't given; take it as a parameter, as in 'r: region'
fi

Leaf(1) holds no pointer and could go in any region, but a result's region must be one a parameter names. (task leaf(t: Tree@r) -> Tree@r may send Leaf(1), since t names r.) Workaround: add a parameter that names the region; a region parameter works even if the task never allocates in it. 

kind Tree
    Leaf(value: int)
    Branch(left: ^Tree, right: ^Tree)
fi

task leaf(r: region, value: int) -> Tree@r
    <- Leaf(value)
fi

task main()
    region trees
    fixed t: Tree@trees = leaf(trees, 3)
    match t
    case Leaf value
        show(value)
    case Branch _ _
        show("branch")
    fi
fi

A name bound from a pointer-free value can't be given a pointer

region a
fixed q = new Node(Node { value: 2, next: none }) at a
when first(none) is {flex n}
    n^.next = q
    ; error: expected type maybe ^Node@_, got ^Node@a; this place holds a value without pointers (of no region), ...
fi

first(none) is given nothing from any region, so its result is in no region (@_), and so is n. Storing q in it would put a pointer where Vela can't tell how long it may live. (Here n can never exist, since first(none) is always none, but the rule doesn't look at values.) Workaround: give the call a value whose type names the region. 

shape Node
    value: int
    next: maybe ^Node
fi

task first(list: maybe ^Node@r) -> maybe ^Node@r
    <- list
fi

task main()
    region a
    flex q = new Node(Node { value: 2, next: none }) at a
    flex start: maybe ^Node@a = new Node(Node { value: 1, next: none }) at a
    when first(start) is {flex n}
        n^.next = q
        show(n^.value + q^.value)
    fi
fi

A binding without a type can't hold a pointer-free regional value

flex head = Node { value: 1, next: none } is an error, because nothing says which region head is for. Workaround: write its type: flex head: Node@nodes = ….

Regions have no size limit, and running out of memory stops the program

There is no way to cap a region or to handle a failed allocation. Workaround: none inside Vela yet; keep regions short-lived so memory use stays predictable.

9. Ideas for regions

These are proposals, each with what it would cost and how it fits the rest of the language; the ones built since are marked Done, and the rest are not implemented. Badges: Recommended Worth trying Later Not recommended.

Easier region passing

Every call to a task that allocates passes a region: push(nodes, list, 1). In a program that allocates a lot, that region argument repeats everywhere, and it is easy to confuse with the real arguments. Several spellings could make it lighter:

Done in part A task that takes its region last is now given it after the call, as new is: push(list, 1) at nodes or push(list, 1)@nodes, and a call that leaves it out takes the block's default region (see The region after a call). What follows is still open for a region taken anywhere but last, and for working the region out from the arguments.

nodes.push(list, 1): the region before a dot Later

task push(r: region, list: maybe ^Node@r, value: int) -> ^Node@r
    <- new Node(Node { value: value, next: list }) at r
fi

list = nodes.push(list, 1)       ; the same call as push(nodes, list, 1)
  • Grammar: no conflict today. The parser would accept a call after name., and since regions share the variables' names and have no fields, the checker tells nodes.push(…) from a field access by looking nodes up.
  • Conflict with methods: this is the real cost. Vela now has methods, where p.shift(2, 2) finds shift in p's shape. nodes.push(…) would give .name(…) a second lookup rule ("a task whose first parameter is a region"), decided by whether the left side is a region; a region has no methods, so the two never meet, but a reader has to know which the left side is.
  • Reads as: "push is something a region does", which isn't quite the model.
  • Verdict: if Vela adopts uniform call syntax (x.f(a) means f(x, a) for any x), region calls come with it and need no rule of their own. Vela's methods chose the other way (a method belongs to its type, and a task is never called after a dot), so this would be the one place a task is.

nodes->push(list, 1): an arrow from the region Not recommended

  • Grammar: no conflict. -> only appears after a task header's ), and after a value it is a syntax error today, so a parser can accept it.
  • Meaning: Vela gives each symbol one idea, and -> already means "what a task sends back", paired with <-. Here it would mean "in this region". C and C++ programmers would read it as a member access through a pointer, which suggests a region is an object with a push member.
  • Verdict: implementable, but it muddies one of Vela's few symbols.

push->nodes(list, 1): an arrow to the region Not recommended

  • The same symbol problem as above, and it reads backwards: nodes sits where the called name usually is, so push->nodes(copy->kept(list), 1) is hard to scan.

task push[r: region](…) and push[nodes](list, 1): regions in brackets Recommended

task push[r: region](list: maybe ^Node@r, value: int) -> ^Node@r
    <- new Node(Node { value: value, next: list }) at r
fi

task sum[r](list: maybe ^Node@r) -> int      ; a region the task only names
    ...
fi

list = push[nodes](list, 1)
  • The declaration matches the call: regions go in brackets in both, and ordinary values in parentheses. The region stops looking like a value argument.
  • Grammar: [ after a name indexes an array or slice (a[i]), but tasks aren't values, so name[…](…) is a region list when name is a task and an index when it is a variable. Go resolves its generic calls (f[int](x)) the same way.
  • Room to grow: a task or a shape takes types in angle brackets today (task first<T>(…), shape Box<T>, see Types a declaration takes), and a type it takes names no region of its own; a shape given types names the one its values live in, Box<text>@r. Regions are compile-time parameters too, so a task that wrote both would have two lists, task find<T>[r](…), or one that holds types and regions together. Shapes could take several regions the same way (see below).
  • Safer headers: task sum[r](…) declares the regions a task only names. Today a misspelled @rr silently becomes a second region, and the mistake only shows where the two meet.
  • Cost: parser (brackets in headers and calls), checker (region parameters apart from parameters), codegen (region arguments first in C), Vela Studio, and changing every existing region task. On its own it isn't shorter, but it makes the next idea unambiguous.

push(list, 1): inferred region arguments Recommended, with brackets

region nodes
flex list: maybe ^Node@nodes = none
list = push(list, 1)             ; r is nodes: list's type says so
fixed other = push[nodes](none, 2) ; nothing names a region, so it is written
  • Rule: the brackets may be left out when the arguments' types, or the type the result must fit, name every region parameter. Otherwise the call is an error that asks for them: cannot tell which region 'push' allocates in; write push[r](…).
  • Sound: the inferred region must be one the caller can allocate in; a region the caller only names is still an error that suggests taking r: region.
  • Implementable: calls already infer a task's regions from its arguments (unify_regions in the checker); a missing region argument would use the same result, plus the expected type that coerce already has for bindings, assignments, arguments, and sends.
  • Needs brackets: with today's positional region parameters, "one argument fewer" can't be told apart from a forgotten argument, and a task with two region parameters would be ambiguous.
  • Cost to readers: the call no longer shows where memory goes. Vela Studio can show the inferred [nodes] as an inline hint.

fixed p: ^int@scratch = new int(1): new takes its region from the type Worth trying

  • When the place a new goes already names a region (a typed binding, an assignment, a field, an argument, or a send in a task whose result names it), at r could be left out.
  • Small: the checker would fill in new's region from the expected type, with the same error as today when nothing names one.
  • Best limited to places where the region is written on the same line, such as typed bindings, so the source still says where memory goes.

region r default: a default region for a block Done

  • Built on 2026-09-24, and written up as Lesson 10: a block, or a task through r: region default, names one region, and everything in it that allocates without naming a region goes there.
  • This was Not recommended here, for hiding where memory goes behind something declared lines away. What changed the verdict was measuring it: of the lines that allocate and name a region in examples/ and tests/run/, only about one in nine also writes that region in a type on the same line, so the narrower idea below (new takes its region from the type) reaches few of them, while a default reaches nearly all — a cut of about two thirds in the region names those lines carry.
  • What answers the objection: it is opt-in, a block names one default at most (so two lines in a block never differ in where they allocate), the region is still in every value's type, and a copy keeps taking its region from the place it goes. Region arguments at calls are untouched; that is the idea above.

Freeing one value early

Smaller regions Available now

The model's own answer: a value that should go early belongs in a region that ends early. It covers most cases, but not long-lived data where individual values come and go, like a cache or a game's entities.

Owned pointers with drop Recommended, long term

region cache
fixed big = new own Buffer(Buffer { size: 1024 }) at cache
read(big^)
drop big                         ; its memory goes back to the region now
show(big^.size)                  ; error: 'big' was dropped
  • An own ^T@r is move-only (the linear ownership option in Future Directions): assigning or passing it moves it, and the old name can't be used again. Since there is only ever one, drop can free it safely.
  • The region keeps dropped memory in free lists by size and reuses it for later allocations of that size.
  • Cost: a move checker (which variables have been moved from, on every path), and an own pointer can't be copied into shapes freely. Plain ^T@r pointers keep working as today.

Pools with checked handles Worth trying

pool entities of Entity at world
fixed player = entities.add(Entity { health: 100 })  ; a handle, not a pointer
entities.remove(player)
when entities.get(player) is {e}                     ; none: removed
    show(e^.health)
fi
  • A pool hands out handles (a slot index and a generation number). Removing a value frees its slot; a stale handle is detected at run time because its generation no longer matches, so get gives a maybe.
  • Safe without a move checker, and a good fit for long-lived, changing collections (games, caches, graphs being edited). The cost is a small run-time check on every access, and handles instead of pointers.

Recycling memory by type Not recommended

recycle p could return p's memory for the next new of the same type in the region, without checking that p is the only pointer. The memory stays a valid T, so it can't crash, but an old pointer would silently see a different value: a use-after-free bug without the undefined behavior. That trades a crash for a wrong answer, which is worse.

Lifting today's limitations

Result-only regions are free Recommended, small

Fixes this limitation. A region that only the result names (no parameter names it, and it isn't a region parameter) can only ever hold values without pointers: the task has no pointer into it and no way to allocate there, and its body can't declare a region with that name. So task leaf() -> Tree@r is sound, and each call's result can be in no region (@_) and take the region of the place it goes, as Leaf(1) does. The change is removing one error from the header check.

Typed patterns and region inference for bindings Recommended

when first(none) is {flex n: ^Node@a} ; the pattern names the region
    n^.next = q
fi

flex head = Node { value: 1, next: none }
head.next = push(nodes, none, 2)      ; head's region is inferred from this line
  • Fixes this limitation and this one.
  • Typed patterns are small: a pattern's name may have a type, which the value must fit (an @_ value fits any region).
  • Inference is larger: a binding of a value in no region gets a region variable that the first use with a real region settles, checked across the whole task. A variable nothing settles never holds a pointer, so any region is correct for it.

Shapes with several regions Worth trying

shape Edge[from, to]
    source: ^Node@from
    target: ^Node@to
fi

task connect(a: ^Node@x, b: ^Node@y) -> Edge[x, y]
    <- Edge { source: a, target: b }
fi

Fixes this limitation for data that really spans regions. Node@r would stay the shorthand for a shape with one region. It fits the bracket syntax above. The cost is in the checker: a shape's regions are substituted like a task's, and every field access maps them.

Younger data pointing at older data Later, with borrowing

Fixes this limitation, but it needs care. An enclosing region always outlives the regions of the blocks inside it, so storing a pointer into outer in a value in inner is safe. Simply letting ^Node@outer pass as a ^Node@inner is not safe, though: through that pointer, a program could write a pointer into inner into a node that lives in outer, and it would dangle when inner is freed. It is only sound for pointers that can't be written through: read-only views, which is the borrowing idea (&T) in Future Directions. With several regions per shape (above), shape Leaf[own, parent] is another way to say it.

A generated copy: value.copy() Done

Done (2026-09-17): value.copy() copies into the region the place it goes names, as in node^.title = line.copy(), or into r with value.copy() at r (or value.copy()@r) where nothing names one; see Copying into another region. It copies text, slices' items, and what pointers point to, all the way down, and lifted the limit that a value holding pointers couldn't be copied to another region whole. The compiler generates a copy for each type the program copies; linked data can share nodes or form cycles, so a copy keeps a table of what it has already copied (freed when it ends) to keep shared nodes shared and to stop at cycles.

Moving a whole region into another Worth trying

region kept
each line in lines
    region work
    fixed parsed = parse(work, line)
    when parsed.ok
        move work into kept          ; everything in work is in kept now; work can't be used again
    fi
fi

A cheaper alternative to copying, in some cases. A value can't be moved out of a region on its own: a region hands out memory in chunks and frees only whole chunks, and other pointers may still reach the value, so freeing it early would leave them dangling. A whole region can move, though. Its chunks would be linked into the longer-lived region's list without copying a byte, and every value of the moved region would count as the other region's from then on. Rules it needs: the target must outlive the moved region (it is declared in an enclosing block, or is a region parameter); after the move, no name of the moved region can be used, which is a flow check like the one for named results; and the values that stay in variables are retyped to the target's region. Cost: constant time, and no memory is copied, but nothing is freed either: the moved region's scratch data comes along. It suits building a value in a scratch region and keeping it only when the work succeeds, where .copy() would copy what is kept and free the rest.

Text fields of their own region, and tasks that take text of any region Worth trying

Today a shape's text is in the one region of the value holding it, and a task that reads text of a region names that region in its header (name: text@r), as it does for pointers. Two ideas would ease that. Per-field regions would let a shape hold text of two regions, or text that lasts inside a value in a region, as part of Shapes with several regions above. Header elision would read a text parameter, and a Person holding text, as text of a region the header doesn't name, shared by the header's other unnamed ones, so a task that only reads text needs no @r; its results would need the same rule, as Rust's lifetime elision has. Both were weighed when text got regions (2026-09-17), and the plain rule came first: a region is written where it matters.

Handing a region to the next loop pass Later, research

A long-running loop that keeps a changing state (a simulation, an editor's document) would ideally copy the live state into a fresh region each pass and free the old one, like a copying garbage collector run by hand. Today a region can't outlive its pass. A construct to "continue with this region as the next pass's region" needs every variable that names the old region to be replaced at the same time, which is a flow analysis of its own.

Growing with the other memory models

Regions were chosen over the other options in Future Directions, but those options aren't discarded. Several combine well with regions:

  • Borrowed, read-only references (from Rust's model): a task could take a view into any region that lives at least as long as the call, and younger data could point at older data (above).
  • Move-only ownership: own pointers that can be dropped early (above), and that can move between threads.
  • Capabilities (own, read, write, from the second notebook): a read ^Node@r parameter would document and enforce that a task doesn't change the list.
  • Reference counting for the few values shared across a whole program, in a region kind of their own, without making every pointer pay for it.

A suggested order.

  1. Small and safe: result-only regions, typed patterns, the growth lint, the chunk cache, and a first chunk on the stack.
  2. Region brackets with inferred region arguments, and new taking its region from the type.
  3. Generated copies and shapes with several regions.
  4. Owned pointers with drop, or pools, once real programs show which fits better.
