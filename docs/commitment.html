Commitments & Async/Await

Design analysis of Vela's await-by-default async model: colorless tasks, Commitment[T] vs. Promise, safety boundaries with regions and ownership, and a safe Vela-native architecture.

Design Proposal Await by Default Colorless Concurrency Safety Analysis
Status Notice: This document captures and evaluates a proposed async/await and Commitment design for Vela. Nothing described below as Commitment or async => continuations is implemented in the compiler yet. For concurrency primitives available today, see Concurrency & Design Boundaries, Channels, and Actors.

📜 1. The Proposed Commitment Model

Most mainstream languages with async/await (JavaScript, TypeScript, Python, C#, Rust) flip the ergonomic default: calling an async function returns a lazy or detached Promise/Future, and the caller must explicitly write await at every call site to obtain the value. Forgetting await is a notorious source of silent bugs, dropped errors, and type mismatches.

Your proposed Vela model inverts that default around three core rules:

1. No async Function Color

Tasks never declare an async modifier. Callers decide whether to wait immediately or launch concurrently.

2. Await Forced by Default

Calling a promising task blocks/suspends until completion and yields the resolved value T directly — impossible to forget await.

3. Opt-In Deferral via =>

Using => { ... } { ... } launches fire-and-forget / deferred execution with inline then and optional plan B error handling, binding a handle y.

Sketch of Your Original Draft Syntax

; 1. Default call: awaited automatically (x has type T, not Commitment[T])
bind x = callPromisingTask()

; 2. Deferred / fire-and-forget call with '=>' (then) and optional Plan B (catch)
bind y = callPromisingFunc() => {
    ; Continuation executed when the commitment settles
} {
    ; Optional Plan B: executed if rejected. If omitted, y holds a rejected handle.
}

; 3. Manual inspection of the handle y
loop y.is_not_resolved_yet()
    ; work while waiting
fi
fixed val = y.resolved_value

🏷️ 2. Naming: Commitment vs. Promise vs. async/await

Should this concept be named Commitment, Promise, or async/await?

Name Mental Model & Fit with Vela Verdict
Commitment[T] Signals an active, bound obligation rather than a passive callback container. Because a plain call immediately fulfills the commitment unless explicitly deferred, the name matches Vela's anti-forgetting philosophy and gives Vela its own clean vocabulary (like shape, kind, task, region). Best Vela Fit
Promise[T] Immediately recognizable to developers from JavaScript/TypeScript, C++ (std::promise), and Scala. Slightly mismatched if a call without modifiers never returns a Promise by default. Best Familiarity
async / await Implies coloring functions with async and prefixing every call with await. Since your model removes both keywords from normal code, calling the feature async/await in syntax would contradict the design. Misleading Term
Recommendation: Keep Commitment[T] as the official Vela type/page name (paired with terms like pending, fulfilled, and failed), while cross-referencing Promise / async-await in the docs so newcomers map the concept instantaneously.

🧠 3. Alignment with Vela & Architectural Consequences

Is It Logical and In Sync with Vela?

Yes in spirit, mixed in syntax. Two halves of your intuition fit Vela extraordinarily well:

  • Making waiting the safe default: Vela refuses implicit null pointers, ignored errors (T ~ E), and unannotated mutation (alters, flex&). Requiring opt-in syntax to launch asynchronous background work instead of opt-in await fits the exact same "safe by default, explicit at the sharp edge" philosophy.
  • Avoiding function coloring: Vela's task system already distinguishes capabilities cleanly via types (@r, T ~ E) and scheduler execution without splitting every library in two (sync vs async).

Consequences & Performance Costs of "No async Keyword"

Eliminating the async marker on task declarations is not free — in a language that compiles to strict ISO C11 without a VM, there are only two ways to implement it, each with clear runtime costs:

Implementation Path A: Stackful Coroutines / M:N Scheduler Fibers

Matches Vela's Runtime

Every task can suspend on I/O or channels by parking its fiber stack on Vela's M:N scheduler thread pool (an extension of how runtime/vela_rt.h already multiplexes actors and blocking channel waiters).

  • Pros: Truly colorless! Any regular task can call another task and block/yield transparently without AST rewriting or state-machine explosion. C11 codegen stays simple.
  • Costs: Each concurrently deferred call needs its own stack allocation (e.g., 64 KiB+ or virtual memory / segmented stack bookkeeping) and context switch / OS thread parking when calling blocking C APIs (like synchronous std/files or std/gui X11 calls).
  • Important nuance: Calling a plain synchronous task directly without spawning (the default awaited path!) should execute as a normal C function call at zero extra cost, only allocating a fiber/worker task when deferred.

Implementation Path B: Stackless State Machines (Compiler Transform)

High Complexity in C11

Like Rust or C#, the compiler transforms every suspendable task into a heap/struct frame + switch/case resumption machine in C11.

  • Why "no async" hurts here: Without async on signatures, the compiler must either (1) infer "may suspend" across the entire call graph (breaking separate compilation, task values (A) -> B, and clean error messages), or (2) compile every task in the entire program as a heap state machine, adding huge overhead to tight loops and numeric code.
Verdict on Performance Cost: As long as the default awaited call compiles to a direct C call on the current fiber/thread, normal sequential code pays zero cost. Overhead is paid only when a call is explicitly deferred onto the scheduler (spawning a fiber/work item and allocating a result slot).

⚖️ 4. Pros & Cons of the Draft Design

Strengths (Pros) Weaknesses (Cons)
Zero forgotten awaits: Normal calls always produce T, eliminating an entire bug class common in JS/Python. Keyword/syntax collisions: bind already means an un-reassignable mutable binding in Vela; { ... } already means Plan B; => already starts labeled loops.
No "function coloring" split: Standard libraries (std/collections, helpers) do not need duplicate sync and async APIs. Dual callback + handle confusion: Mixing => { then } callbacks with returning a handle y blurs who owns the result and when it executes.
Structured fan-out friendly: With the right deferred handle, spawning multiple concurrent calls in parallel stays concise. Busy-loop polling trap: loop y.is_not_resolved_yet() burns CPU (or starves cooperative fibers) unless it yields cleanly.
Fits Vela's T ~ E errors: Rejections don't need exceptions; they map directly onto Vela's existing failure channel. Unsafe as written for regions & flex&: Deferred calls that escape the current scope break region lifetime safety and aliasing guarantees (see Section 5).

🚨 5. Safety Audit: 5 Real Safety Holes in the Draft

If implemented literally as sketched, your draft introduces compile-time-breaking soundness holes against Vela's region memory model and data-race guarantees:

Hazard 1: Escaping region r & Dangling ^T@r Pointers

Suppose a task takes a pointer into a caller's region: task load(cfg: ^Config@r, out_r: region) -> text@out_r. When awaited by default, region r stays alive until load returns — 100% safe. If launched asynchronously with => (fire-and-forget), the caller continues immediately, exits the block declaring region r, and calls vela__rt__region_free(r) while the background commitment is still dereferencing cfg^ → Use-After-Free crash!

Hazard 2: flex& References Across Threads → Data Races

Vela prevents aliasing races on flex& parameters within a single call tree. If a deferred commitment receives &counter while the caller continues running and also reads or passes &counter, two OS threads access the same stack/heap address simultaneously → undefined behavior & data race!

Hazard 3: Unsafe Callback Capture in => { ... }

If the continuation block => { ... } captures local flex variables or regional @r values from the enclosing scope and runs later on a worker thread:

  • Capturing local references races with the caller's stack/locals and dangles if the enclosing task returns first.
  • Capturing @r values fails once the enclosing region frees.

Hazard 4: Unchecked y.resolved_value & Busy-Spin Loops

Exposing y.resolved_value directly on a pending handle breaks two core Vela promises:

  • Reading before settlement or after rejection: Either traps at runtime or reads invalid memory — whereas Vela uses maybe T and T ~ E so invalid states are unrepresentable at compile time.
  • CPU starvation / deadlock: loop y.is_not_resolved_yet() pins a scheduler worker thread at 100% CPU. In an M:N fiber runtime with fixed worker threads, spinning without yielding can even prevent the commitment itself from ever being scheduled!

Hazard 5: Unawaited Fire-and-Forget Error Swallowing & Resource Leaks

If the optional plan B catch block is omitted on a true fire-and-forget task whose handle is ignored, a failing T ~ E result disappears silently — violating Vela's core invariant that call failures cannot be silently dropped — and any sockets/files inside that detached task may outlive program shutdown or actor lifetimes.

🛡️ 6. A Safer, Cleaner Vela-Native Model

We can preserve every goal you wanted — no async keyword on tasks, forced await by default, concise opt-in concurrency, and clean handling of success/failure — while making it 100% memory-safe and data-race free by reusing the exact mechanisms Vela already proved in Channels, Actors, and select:

Rule 1: Crossing Concurrency Boundaries Follows Channel Rules

A plain awaited call can use anything (^T@r, flex&, region parameters) because it never outlives the call site. When a call is explicitly deferred as a Commitment, arguments must obey Vela's existing send-safety check:

  • No flex& parameters (prevents concurrent aliasing races).
  • Either arguments/results contain no escaping @r pointers (lasting data or moved with own), OR the commitment is bound inside a structured concurrency scope that guarantees completion before those regions exit.

Rule 2: Replace => { then } + bind Overload with Explicit Deferral + Structured Join Scope

Keep fixed / bind / flex purely for mutability! Trigger concurrency at the call site with a clear keyword or suffix (e.g., later or fork, or a dedicated call modifier), returning a Commitment[T] (or Commitment[T ~ E]): 

; Safe Model Preview: syntax brainstorm integrating with Vela's existing primitives
task fetch_user(id: int) -> User ~ HttpError
    ; Normal HTTP call inside: awaited cleanly by default!
    fixed resp = http_get("/users/{id}")?
    <- parse_user(resp)?
fi

task load_dashboard(id: int) -> Dashboard ~ HttpError
    ; 1. Default: synchronous from caller's perspective (auto-awaited)
    fixed config = load_config()?

    ; 2. Explicit concurrent launch: returns Commitment[User ~ HttpError]
    fixed c_user = fetch_user(id) later
    fixed c_orders = fetch_orders(id) later

    ; 3. Join & handle errors via Vela's existing '<<-' and Plan B!
    fixed user = (<<- c_user) { failure err
        <- fail err
    }
    fixed orders = (<<- c_orders) { [] }

    <- Dashboard { config: config, user: user, orders: orders }
fi

Rule 3: Structured Concurrency Guarantees Zero Dangling Commitments

What if a caller launches c_orders with later and then returns early (for instance, because c_user failed)? In unstructured threads/promises, c_orders leaks into the background. In Structured Concurrency, every unconsumed Commitment[T] is lexically scoped to the block (or an enclosing region / nursery block) that created it:

  • On scope exit (normal return, fail, or break), the runtime signals cancellation and joins any unawaited commitments created in that scope before freeing its region frames.
  • True long-lived background work uses spawn Actor(...), whose mailbox lifetime is explicit.

Rule 4: Replace y.resolved_value & Polling Loops with poll(), <<-, and select

Never expose a partially valid y.resolved_value field or force users to write CPU-burning spin loops:

  • Blocking wait: <<- c (or c.wait()) parks the calling task efficiently on a condition variable/waiter node with 0% CPU waste and returns T (or T ~ E, requiring Plan B / ? / match).
  • Non-blocking check: c.poll() returns maybe T (or maybe (T ~ E)), forcing callers to unwrap via is / match / Plan B.
  • Multi-commitment racing & timeouts: Because a Commitment[T] works just like a single-shot channel handle, it plugs straight into Vela's existing select!
; Racing two commitments with a timeout using Vela's existing select + <<-
fixed primary = query_mirror("us-east") later
fixed backup = query_mirror("eu-west") later

fixed fastest = select
case data <<- primary = data
case data <<- backup = data
case after 250 = "mirror timeout"
fi

✨ 7. Ideas to Make Commitments Extra Cool in Vela

1. Native select & <<- Unity

Making Commitment[T] interoperate with <<- and select means no separate Promise.all / Promise.race runtime is needed: racing two calls with a timeout reuses syntax Vela programmers already know.

2. Zero-Cost Sequential Fast Path

Because un-annotated calls await inline, 99% of calls compile to ordinary direct C11 calls with zero scheduler allocation or fiber stack overhead.

3. Cooperative Cancellation Token

When a select picks the winner (or scope exits via fail), losing commitments automatically receive a lightweight cancellation flag (cancelled()), stopping wasted HTTP/DB work cleanly.

4. Region Transfer Integration

Once Chan[own region] lands, a deferred task can allocate inside an isolated child region and hand off the entire region pointer graph in O(1) when its commitment settles — zero deep copy.
