Selected Architectural Direction (Finalized Syntax) Current Choice

Before diving into the step-by-step evaluation from the original draft to all alternatives, the selected approach is the Enhanced Colorless Commitment Model using the prefix rush keyword:

  • Colorless tasks & await-by-default: Regular tasks never need an async keyword; plain calls run and await automatically, paying zero runtime overhead on sequential code.
  • Explicit concurrency with prefix rush: Writing rush task_name(...) launches the task concurrently and returns a single-shot Commitment[T] (or Commitment[T ~ E]) bound by structured concurrency to its lexical block.
  • Unified waiting & racing: Wait via <<- c (with Plan B error handling, including parenthesis-free <<- c { ... }), inspect non-blockingly via c.poll() -> maybe T (including maybe Commitment[T] slots), or race commitments and timeouts inside existing select.
  • Continuations via |> pipes, =>, and .then/.recover: Post-settlement transforms work seamlessly with call pipes (rush (call() |> step()) and <<- c |> then(lambda)), fluent c.then(fn) / c.recover(fn), and inline call() => (v) { ... } [{ failure e ... }].
fixed cfg = load_config() { failure e <- fail e }      ; Config (awaited automatically, errors propagated via Plan B)
fixed c_user = rush fetch_user(id)                     ; Commitment[User ~ HttpError]
fixed c_name = rush (fetch_user(id) |> format_name())  ; Commitment[text ~ HttpError] (.then via pipe)

fixed user = <<- c_user { failure e <- fail e }         ; User (unwrapped with Plan B)

fixed c_visits = rush count_visits(id)                 ; Commitment[int] (cannot fail)
fixed report = select                                     ; text
    case n <<- c_visits = "{n} visits"                   ; n: int
    case after 250 = "timeout"                             ; c_visits is cancelled & joined
fi

📜 1. The Proposed Commitment Model (Original Draft)

Most mainstream languages with async/await (JavaScript, TypeScript, Python, C#, Rust) flip the ergonomic default: calling an async function returns a lazy or detached Promise/Future, and the caller must explicitly write await at every call site to obtain the value. Forgetting await is a notorious source of silent bugs, dropped errors, and type mismatches.

Your original draft inverted that default around three core rules:

1. No async Function Color

Tasks never declare an async modifier. Callers decide whether to wait immediately or launch concurrently.

2. Await Forced by Default

Calling a promising task blocks/suspends until completion and yields the resolved value T directly — impossible to forget await.

3. Opt-In Deferral via =>

Using => { ... } { ... } launches fire-and-forget / deferred execution with inline then and optional plan B error handling, binding a handle y.

Sketch of the Original Draft Syntax

; 1. Default call: awaited automatically (x has type T, not Commitment[T])
bind x = callPromisingTask()

; 2. Deferred / fire-and-forget call with '=>' (then) and optional Plan B (catch)
bind y = callPromisingFunc() => {
    ; Continuation executed when the commitment settles
} {
    ; Optional Plan B: executed if rejected. If omitted, y holds a rejected handle.
}

; 3. Manual inspection of the handle y
loop y.is_not_resolved_yet()
    ; work while waiting
fi
fixed val = y.resolved_value

🏷️ 2. Naming: Commitment vs. Promise vs. async/await

Should this concept be named Commitment, Promise, or async/await?

Name Mental Model & Fit with Vela Verdict
Commitment[T] Signals an active, bound obligation rather than a passive callback container. Because a plain call immediately fulfills the commitment unless explicitly deferred, the name matches Vela's anti-forgetting philosophy and gives Vela its own clean vocabulary (like shape, kind, task, region). Best Vela Fit
Promise[T] Immediately recognizable to developers from JavaScript/TypeScript, C++ (std::promise), and Scala. Slightly mismatched if a call without modifiers never returns a Promise by default. Best Familiarity
async / await Implies coloring functions with async and prefixing every call with await. Since the colorless model removes both keywords from normal code, calling the syntax async/await would contradict the design. Misleading Term
Recommendation: Keep Commitment[T] as the official Vela type/feature name (with states pending, fulfilled, and failed), while cross-referencing Promise / async-await in documentation so newcomers map the concept instantaneously.

🧠 3. Alignment with Vela & Performance Cost of Dropping Function Coloring

Is It Logical and In Sync with Vela?

Yes in spirit, refined in syntax. Two halves of your intuition fit Vela extraordinarily well:

  • Making waiting the safe default: Vela refuses implicit null pointers, ignored errors (T ~ E), and unannotated mutation (alters, flex&). Requiring opt-in syntax to launch background work instead of opt-in await follows the exact same "safe by default, explicit at the sharp edge" rule.
  • Avoiding function coloring: Vela's task system avoids splitting standard libraries into duplicate sync and async APIs.

Does the Enhanced Colorless Model Still Have Performance or Compile-Time Cost?

Important honest answer: Making tasks colorless does not magically erase the underlying implementation tradeoff — even in the enhanced rush model, dropping async function signatures leaves two possible C11 compilation strategies, each with specific costs:

Implementation Path A: Stackful Coroutines / M:N Scheduler Fibers

Matches Vela's Runtime Best
  • Sequential fast path = 0 cost: A normal call (fetch_user(id) without rush) compiles to a direct C11 function call on the current fiber/thread stack. Zero heap frame, zero scheduler queue push, zero context switch.
  • Deferred path (rush) = fiber allocation cost: Each concurrent rush launch allocates a fiber stack (or worker task + virtual/segmented stack) and a small Commitment cell, then runs normal C11 code inside that stack. Any blocking wait deeper down its call graph yields cooperatively without needing async signatures anywhere.
  • C FFI / blocking syscall caveat: If any deep task invokes a raw blocking OS call (e.g., synchronous POSIX file I/O or X11 event waits without runtime-managed polling), that fiber temporarily pins its OS worker thread unless offloaded to a blocking thread pool or routed through non-blocking Poll.

Implementation Path B: Stackless State Machines Without async

High Compile-Time Cost
  • Without async markers in task types, generating Rust-like C11 state machines requires whole-program call-graph suspension analysis during compilation to discover which tasks can transitively call <<- or yield.
  • Compile-time & modularity costs: Hurts separate/incremental C compilation, complicates task function pointers (int) -> int (an indirect call might or might not suspend!), or forces every task conservatively into a heap-allocated state frame — hurting tight numeric loops.
Bottom Line on Cost: Under Path A (direct C calls by default + fibers spawned only at rush / spawn), dropping coloring adds zero runtime cost to normal synchronous code, only a modest per-rush fiber allocation + context-switch cost when you explicitly branch concurrently, and negligible compile-time cost.

⚖️ 4. Pros & Cons of the Initial Draft

Strengths (Pros) Weaknesses (Cons)
Zero forgotten awaits: Normal calls always produce T, eliminating an entire bug class common in JS/Python. Keyword/syntax friction: bind already means an un-reassignable mutable binding in Vela; => already starts named loops/blocks and module aliases; { ... } already means Plan B.
No "function coloring" split: Standard libraries (std/collections, helpers) do not need duplicate sync and async APIs. Dual callback + handle confusion: Mixing => { then } callbacks with returning a handle y blurs what type y has and when the continuation executes.

Fits Vela's T ~ E errors: Rejections don't need exceptions; they map onto Vela's existing failure channel. Unsafe as written for regions & flex&: Detached fire-and-forget calls break lexical region lifetimes and aliasing rules (Section 5).

🚨 5. Safety Audit: 5 Real Safety Holes in the Initial Draft

If implemented literally as sketched, the initial draft introduces compile-time-breaking soundness holes against Vela's region memory model and data-race guarantees:

Hazard 1: Escaping region r & Dangling ^T@r Pointers

Suppose a task takes a caller region pointer: task load(cfg: ^Config@r, out_r: region) -> text@out_r. When awaited by default, region r stays alive until load returns — 100% safe. If launched detached with =>, the caller continues immediately, exits the block declaring region r, and frees r while the background commitment still reads cfg^ → Use-After-Free crash.

Hazard 2: flex& References Across Threads → Data Races

If a deferred commitment captures or receives &counter while the caller continues running and also modifies or reads counter, two worker threads touch the same memory simultaneously → data race.

Hazard 3: Unsafe Callback Capture in => { ... }

An inline callback block running concurrently on a worker thread cannot safely touch caller stack variables or caller @r values after the caller exits or mutates them unless captured explicitly with Vela's closure rules ([@r] / moved own values).

Hazard 4: Unchecked y.resolved_value & Busy-Spin Loops

Direct field access before settlement breaks compile-time exhaustiveness (maybe T / T ~ E), and polling loops like loop y.is_not_resolved_yet() burn 100% CPU and can deadlock M:N cooperative worker pools.

Hazard 5: Unawaited Fire-and-Forget Error Swallowing & Resource Leaks

If optional plan B is omitted on an abandoned handle, a T ~ E failure disappears silently — violating Vela's rule that failures cannot be ignored — and background sockets/files can leak past scope shutdown.

🛡️ 6. A Safer, Cleaner Vela-Native Model (Enhanced & Selected)

We preserve every goal — colorless tasks, forced await by default, concise opt-in concurrency, and clean handling of success/failure — while guaranteeing 100% memory and data-race safety by unifying Commitments with Channels, select, and structured concurrency:

Four Core Safety & Ergonomic Rules

  1. Send-boundary safety at rush: Normal awaited calls accept any ^T@r, flex&, alters, and arbitrary region arguments. Across rush, arguments and results obey concurrency safety: no flex&/fixed&/bind& references, no alters methods or mutable shared state, and at most one destination caller region (when provided, the worker allocates inside an isolated worker region that splices in O(1) into the caller's region on settlement or frees automatically on cancel/failure).
  2. Explicit call deferral returning Commitment[T]: Prefixing rush spawns concurrent execution cleanly without overloading bind, and inline => [(v)] { ... } [{ failure e ... }] offers concise fire-and-forget and inline mapping.
  3. Structured lexical scope cleanup: Any Commitment[T] (including maybe Commitment[T] slots) created in a block that exits early (fail, <-, break) or is overwritten cancels cleanly and joins before the block's region allocations are freed. (Immortal daemons use spawn Actor(...).)
  4. Proper inspection & racing: Wait with <<- c (or c.wait()) returning T or T ~ E, check without blocking via c.poll() (returns maybe T / maybe (T ~ E)), or race inside select ... case after ms ... fi.

Annotated Example: Concurrent Fetch & Error Propagation

task fetch_user(id: int) -> User ~ HttpError
    ; Normal HTTP call + pipe inside: awaited automatically with pipe error short-circuiting!
    <- http_get("/users/{id}") |> parse_user()
fi

task load_dashboard(id: int) -> Dashboard ~ HttpError
    ; 1. Default synchronous path: awaited immediately (0 worker overhead)
    fixed config = load_config() { failure e <- fail e }  ; Config

    ; 2. Explicit concurrent launch: returns Commitment handles immediately
    fixed c_user = rush fetch_user(id)                   ; Commitment[User ~ HttpError]
    fixed c_orders = rush fetch_orders(id)               ; Commitment[[Order]]

    ; 3. Join & handle errors via '<<-' and Plan B
    fixed user = <<- c_user { failure err                 ; User (unwrapped after Plan B handles HttpError)
        <- fail err
    }                                                     ; Note: if fetch_user fails above, c_orders auto-cancels & joins at fi!
    fixed orders = <<- c_orders                           ; [Order]

    <- Dashboard { config: config, user: user, orders: orders }
fi

Annotated Example: Racing Commitments with Timeout via select

fixed primary = rush query_mirror("us-east")             ; Commitment[text]
fixed backup = rush query_mirror("eu-west")              ; Commitment[text]

fixed fastest = select                                    ; text
    case data <<- primary = data                          ; data: text (losing commitment auto-cancels)
    case data <<- backup = data                           ; data: text
    case after 250 = "mirror timeout"
fi

💬 7. Design Q&A: Channels, Expressions, Parentheses & Feature Completeness

Q1. Does rush func() become a Chan[T], or stay a Commitment[T]? Runtime Design

It stays a distinct Commitment[T] — not a Chan[T] — though both plug into the same <<- and select protocol.

Property Chan[T] (Multi-Message Pipe) Commitment[T] (Single-Shot Future)
Cardinality 0, 1, or N messages over time (stream/queue). Exactly 1 settled result (value T or error E) + cancellation state.
Waiting & Polling <<- ch (wait_and_receive) blocks and returns T (trapping if closed and drained); non-blocking ch.receive() returns maybe T; select uses case none <<- ch on closure. <<- c returns T (or T ~ E); non-blocking c.poll() returns maybe T (or maybe (T ~ E)).
Closing & Memory Requires explicit .close() so producers can stop sending while consumers drain. Automatically closes on settlement and cleans up automatically at structured scope exit — zero manual .close() needed!
Runtime Link Both implement the internal waiter queue interface in runtime/vela_rt.h, so select can mix case msg <<- ch, case res <<- commitment, and case after ms in one atomic block.

Q2. Can we use fire-and-forget / <<- in the middle of expressions? Expression Semantics

Consider your two snippets:

; Snippet A (without 'rush')
fixed r1 = (<<- task_call()) { ... }

; Snippet B (explicit 'rush' inside '<<-')
fixed r2 = (<<- (rush task_call())) { ... }
  • Why Snippet A doesn't work as fire-and-forget: <<- means await the result right here, and task_call() without rush already awaits and returns T (not a commitment). So <<- task_call() wouldn't defer anything; it is simply a redundant type error unless task_call() itself returned a Commitment[T] or Chan[T].
  • Could <<- on a direct call be redefined to mean "launch"? Not safely. (1) It would flip the operator's meaning: fixed v = <<- ch gives a value, while fixed v = <<- f() would give a pending handle. (2) It is ambiguous when f() legitimately returns a channel (e.g. a make_feed() factory): is <<- make_feed() "receive from the returned channel" or "launch make_feed"? (3) A fixed variable cannot later change from a handle into its value, so "the result dispatches into the variable when it arrives" still means the variable's type is Commitment[T]. Keeping launch on rush and waiting on <<- avoids all three problems.
  • Snippet B works anywhere in expressions, with one nuance: (<<- (rush task_call())) { ... } is valid in any sub-expression (e.g., inside arguments, arrays, math), except launching rush and immediately wrapping it in <<- waits on that very same line — giving no overlap unless another commitment was already running!
  • Where inline expressions shine for real parallelism: Starting sibling commitments first and awaiting them inside any expression:
; Launch concurrently, then resolve inside one composite expression
fixed c_a = rush fetch_price("ETH")          ; Commitment[float ~ ApiError]
fixed c_b = rush fetch_price("BTC")          ; Commitment[float ~ ApiError]
fixed total = ((<<- c_a) { 0.0 }) + ((<<- c_b) { 0.0 })   ; float

; Or pass launched Commitments straight into a multi-arg gather helper:
fixed pair = await_both(rush fetch_price("ETH"), rush fetch_price("BTC"))

Q3. Can we drop parentheses around (<<- c_user) { failure err ... }? Parser Grammar 

; Desired clean form (no outer parentheses):
fixed user = <<- c_user { failure err
    <- fail err
}

Can this work cleanly? Yes, with a deliberate precedence adjustment in src/parser.rs!

  • How Vela's parser behaves today: Inside parse_prefixed(), prefix <<- calls parse_operand() → parse_suffixes(), which greedily consumes trailing { ... } as a Plan B on the channel/handle expression itself! So without a parser tweak, <<- c_user { ... } would currently parse as <<- (c_user { ... }) — attaching Plan B to c_user rather than the awaited value.
  • The clean fix: Adjust Token::ChanRecv (<<-) parsing so its operand consumes member accesses (.field), indexing ([i]), calls ((args)), and deref (^), stopping before Plan B { ... }. That lets trailing { ... } wrap the outer (<<- c_user) expression automatically!
  • Tiny edge case: In the rare case where someone stores channels in a fallible lookup (channels[#0] returning maybe Chan[T]) and wants Plan B on the lookup before receiving, they just keep explicit inner parentheses: <<- (channels[#0] { default_ch }). For the 99% case (<<- c_user { failure err ... }), no parentheses are needed.

⛓️ 8. Solving .then Continuations: Combining => and Call Pipes (|>)

With rush and <<- alone, error handling (catch / Plan B) is effortless, whereas chained post-settlement transformations (.then()) need a clear story. Let's analyze combining your => fire-and-forget style, Vela's native Call Pipes (|>), and lambdas/closures (all now implemented alongside <<- c { ... }).

Approach A: Hybrid => { then } { plan b } Combined with <<-

Allowing func() => (v) { ... } { ... } (and fire-and-forget func() => { ... } statements) to return a Commitment handle that can still be awaited later with <<- x: 

; Combined style with explicit value binder + Plan B
fixed x = fetch_user(id) => (u) {
    log_audit(u.id)
    u.display_name                  ; maps Commitment[User] -> Commitment[text]
} { failure err
    "Guest ({err})"                 ; fallback value if fetch_user fails
}                                   ; x has type Commitment[text]

; ... other concurrent work ...
fixed name = <<- x                  ; text (already transformed or Plan B fallback)

; Or separate the catch to await time:
fixed c_raw = fetch_user(id) => (u) { normalize(u) }   ; Commitment[User ~ HttpError]
fixed user = <<- c_raw { failure e <- fail e }
  • Notice why binding (u) (or similar) is required: Without a parameter/binder, a raw => { ... } block cannot name the resolved value produced by fetch_user(id)!
  • Costs & grammar tradeoffs of => { ... } { ... }:
    • Lexer/Parser token overload: => already denotes module aliases (include x => y), alias Name => Type, and labeled loops/blocks (outer => loop ... fi). After a closing call ) it is unambiguous to parse, though two unrelated constructs share one symbol.
    • Dual meaning of { ... }: Elsewhere in Vela, expr { ... } always means Plan B fallback. With func() => { A } { B }, the first { A } means success and only the second { B } means Plan B failure — even if recognizable, omitting { B } leaves => { A } looking suspiciously like a Plan B block.
    • Async capture rule: Because { A } runs inside the background commitment before <<-, any variables it reads from outside must follow safe capture rules (immutable copies inside structured scope, no dangling stack flex&).

Approach B: Vela Call Pipes (|>) — Two Seamless Modes

Vela already has Call Pipes (|>, |>>) that pass values forward step by step, short-circuit T ~ E errors automatically, and let a single trailing { ... } Plan B handle failures for the whole pipeline! Pipes solve .then in two complementary ways:

Mode B1: Pipe on Await ((<<- x) |> ...)

Runs transforms on the caller's thread right when awaiting x. Zero closure capture complexity; can freely touch local caller state and local regions r!

fixed x = rush fetch_raw(url)     ; Commitment[text ~ HttpError]
; ... do other work ...
fixed y = (<<- x)
    |> parse_user() at r          ; runs only if fetch_raw succeeded
    |> format_badge() at r { failure e
        "Error: {e}"              ; Plan B catches ANY step in the pipe!
    }                             ; y: text@r

Mode B2: Background Piped Commitment (rush (call |> ...))

Runs the entire .then chain on the background worker before settling c — so waiting callers receive the final transformed type cleanly!

fixed c = rush (
    fetch_raw(url)
    |> parse_user()
    |> save_cache()
)                                 ; Commitment[CacheReceipt ~ AppError]

; Other branches race or await the finished pipeline:
fixed receipt = <<- c { failure e
    <- fail e
}                                 ; CacheReceipt

Extra Example: Using Closures & Lambdas in Pipe-Based .then Chains

With builtin polymorphic then(lambda) and Commitment.then / Commitment.recover implemented, you can pipe awaited commitments into both plain lambdas and [@r] closures on the caller thread, OR chain non-capturing lambdas on the background worker: 

task process_profile(r: region, prefix: text@r, user_id: int) -> text@r ~ HttpError
    ; Launch concurrent work first
    fixed c_user = rush fetch_user(user_id)               ; Commitment[User ~ HttpError]
    fixed c_prefs = rush fetch_prefs(user_id)             ; Commitment[Prefs ~ HttpError]

    fixed prefs = (<<- c_prefs) { Prefs.defaults() }      ; Prefs (fallback on failure)

    ; Pattern 1 (pipe style via builtin 'then(value, f)' + kept closures [@r]):
    ; '|>' passes the value as then's first argument; each [@r] lambda safely reads 'prefix' and 'prefs'.
    fixed label = (<<- c_user)                           ; User ~ HttpError flows into the pipe
        |> then([@r] u -> u.full_name)                    ; runs only on success: text
        |> then([@r] full -> "{prefix}: {full} ({prefs.theme})") { failure err
            "{prefix}: Anonymous ({err})"                  ; one Plan B for the whole chain
        }                                                 ; label: text@r

    ; Pattern 2 (.then/.recover methods on Commitment for background chaining):
    fixed c_raw = rush fetch_user(user_id)                                    ; Commitment[User ~ HttpError]
    fixed c_name = c_raw.then((u: User) -> text <- u.full_name fi)            ; Commitment[text ~ HttpError]
    fixed c_badge = c_name.recover((err: HttpError) -> text <- "Guest" fi)   ; Commitment[text] (error handled in bg)
    ; plain lambdas capture nothing, so they are always safe to run on a worker thread

    fixed badge = <<- c_badge                             ; text
    <- label
fi

Pros & Cons of Call Pipes vs. Inline Continuations — Can We Support Both?

Dimension Call Pipes (|> + rush) Method Combinators (.then()) / => (v) { ... }
Access to resolved value Direct — piped value becomes argument 1 (|>) or 2 (|>>), and works directly with named tasks or lambdas via then(v -> ...). Requires binding a parameter (.then(v -> ...) or => (v) { ... }).
Failure propagation Already built into Vela! First T ~ E stops the pipe chain; one trailing Plan B handles every step. Needs separate .recover() or second { plan b } block.
Background vs. foreground Crystal clear by syntax: rush (f() |> g()) runs in background; (<<- c) |> g() runs on caller. Always schedules inside the background commitment (must enforce strict closure capture isolation).
Both Supported Together Yes — Vela now implements both! Call pipes handle linear transform pipelines seamlessly; c.then(fn) / c.recover(fn) and f() => (v) { ... } [{ failure e ... }] cover fluent background callbacks while keeping capture rules statically checked.

🎨 9. Syntax Alternatives Registry (Future Reference)

So we don't lose any brainstormed forms while finalizing grammar, here is how each call-site syntax candidate behaves in Vela's parser:

Candidate Syntax Example Parser Conflict Check & Ergonomic Assessment
Prefix keyword: rush func() Selected Default fixed c = rush fetch(id)
fixed c2 = rush obj.save()		 Reserved keyword (Token::Rush in src/lexer.rs). Crisp, punchy opposite of awaiting; warns the reader before arguments, supports passing at most one destination caller region with O(1) region splicing on settlement, and avoids postfix precedence clashes with { plan b }.
Earlier candidates considered: doing (initial prototype name, later upgraded to rush), running, pending, starting, working.
Postfix later Top Alternative fixed c = fetch(id) later Can also be contextual (like select). Reads naturally left-to-right ("call fetch, later"), though postfix placement requires careful precedence rules with trailing at r and { plan b }.
Prefix later / fork / async Strong Contender fixed c = later fetch(id)
fixed c = fork fetch(id)		 Notice: prefix warns the reader before arguments are parsed ("non-blocking ahead!"), avoids clashes with postfix at r / Plan B { ... }, and makes nested calls unmistakable ((later fetch(a))). Note later/fork/start/async are not currently reserved keywords in src/lexer.rs.
Prefix dot later.func() fixed c = later.fetch(id) High Confusion Looks identical to module/shape/value field access (later reads like an imported namespace!). Also awkward on method calls: later.user.save() looks like a field on later, not a method on user.
Pre-arg dot func.later() fixed c = fetch.later(id) Ambiguous Breaks visual association with normal fetch(id) and clashes with method/module lookups if a shape actually defines a later method.
Post-call dot func().later() / .latered fixed c = fetch(id).later()
fixed c = fetch(id).latered		 Semantic Trap Because bare fetch(id) means await synchronously and return T, writing fetch(id).later() looks like running fetch synchronously first and then calling a .later() method on the returned value T!
Postfix ellipsis func() ... fixed c = fetch(id) ... Token Overload Risk Checked in src/lexer.rs & src/parser.rs: Token::Ellipsis (...) is already used for type groups (P...), argument splats (f(args...)), and open-ended slice literals ([1, 2, ...] at r). Overloading ... after a call visually blurs multi-line continuation and varargs.
Bar fence | func() | fixed c = | fetch(id) | Possible, With Lexer Traps A single | is free today (src/lexer.rs rejects it and asks for or), and the "separate lane" look is short and memorable. But: (1) || is already a token (loop parts), so | | f() | | or |f()|| mis-lexes; (2) |> is the pipe, so |c|>0 lexes as a pipe; (3) the same symbol opens and closes, so nesting needs parentheses; (4) Rust/Ruby readers see closure parameters, and math readers see absolute value; (5) it uses up |, which bitwise operations list as a candidate; (6) it isn't searchable the way a word is, and Vela prefers words (and, or, otherwise).
Prefix sigil ~> func() fixed c = ~> fetch(id) Matches Vela's arrow aesthetic (<<-, ->>, ~). Easy to scan visually, though adding yet another arrow symbol alongside ->, =>, <-, <<-, ->> can make dense code symbol-heavy.

Check without blocking c.poll() -> maybe T c.ready (bool) + c.poll(), receive(c) Never a bare c.value field: a pending or failed handle has no value to read.
.then on the caller <<- c |> step() (<<- c) |> step() (optional parens) Prefix <<- already binds tighter than |> in src/parser.rs; uses existing pipe rules, including one Plan B for the whole chain.
.then in the background rush (f() |> step()), f() => (v) { ... }, c.then(fn) (f() |> step()) later, f() => { it ... } All three selected forms (pipe inside rush, inline =>, and fluent .then(fn)) are implemented with static isolation checks.
Catch Plan B at the wait: <<- c { failure e ... } Second block on =>: f() => (v) { ... } { failure e ... }; c.recover(fn) Catching at the wait keeps the background task free of caller state.
Cancel Automatic (losing select arm, early scope exit) c.cancel(), a cancelled() check inside the task Manual cancel is a useful addition; the automatic version guarantees nothing is left running.

🎨 10. Colored Alternative Model & Other Async Designs

Even though our selected path keeps tasks colorless, what happens if Vela intentionally chose colored tasks (requiring async or an explicit Commitment[T] signature) or another structured concurrency primitive instead? Below are the concrete alternatives for comparison.

Alternative 1: Colored Tasks (async task and/or -> Commitment[T] Signature)

Stackless Friendly, Colored Libraries

In this design, you keep await-by-default at every call site (so callers still cannot forget await!), but require any suspendable task to mark itself explicitly in its declaration — either via an async modifier, an explicit Commitment[T] return type, or both: 

; Style A: 'async task' marker + await-by-default at call sites
async task fetch_user(id: int) -> User ~ HttpError
    <- http_get("/users/{id}") |> parse_user()  ; awaited automatically & pipe-propagated
fi

; Style B: Return-type coloring ('-> Commitment[T]') without an extra keyword
task fetch_orders(id: int) -> Commitment[[Order]]
    <- db_query("orders", id)                 ; body sends [Order]; the signature marks the task as suspendable
fi                                           ; plain call still auto-awaits to [Order]; 'rush' gives the handle

async task dashboard(id: int) -> Dashboard ~ HttpError
    fixed user = fetch_user(id) { failure e <- fail e }  ; auto-awaited with Plan B propagation
    fixed c_orders = rush fetch_orders(id)   ; explicit concurrency: Commitment[[Order]]
    fixed orders = <<- c_orders               ; [Order]
    <- Dashboard { user: user, orders: orders }
fi
  • What improves under coloring: The compiler knows locally per-signature which tasks may suspend, making zero-allocation stackless C11 state machines feasible with fast separate compilation, zero hidden fiber stacks, and an explicit visual signal telling callers "this call may block/yield on I/O".
  • Why it is less appealing than our selected colorless model: Re-introduces the classic "red vs. blue function" split: higher-order utilities like map, wrappers, and pattern methods must either duplicate sync/async signatures or introduce polymorphic effect generics (async?), bloating Vela's clean type system.

Alternative 2: Pure Structured Nursery Block (concurrent ... fi)

Instead of first-class Commitment[T] values, only a lexical block allows concurrent bindings: 

concurrent
    fixed user = fetch_user(id) { failure e <- fail e }
    fixed orders = fetch_orders(id)
fi  ; guaranteed joined here

Verdict: Maximally simple and eliminates dangling handles altogether, but cannot express select racing, conditional awaiting, or storing handles in structs/slices.

Alternative 3: Explicit Channel Request/Reply Helper

No new syntax at all: add a tiny stdlib/compiler helper spawning a fiber onto a 1-slot Chan[T] and returning a one-shot reply channel, using existing <<- and select.

Verdict: Minimal implementation effort today, though callers must manage channel lifecycle/closing rules manually unless wrapped in a single-shot auto-reclaimed type.

Alternative 4: Classic Explicit async + Explicit await (Rust / JS Style)

Calling an async task returns a lazy Commitment[T], and every call needs an explicit await prefix/suffix. Included in the final table below as an industry baseline — though it gives up your core goal of preventing forgotten awaits.
