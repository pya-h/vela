Concurrency & Boundaries

How Vela achieves real OS multithreading today with Actors and Channels — and why raw threads, mutexes, async/await, and several common primitives are intentionally left out.

M:N Worker Pool Actors & Channels Intentional Omissions Safety by Structure

🧵 What Vela Supports Today

Vela supports real OS multithreading and concurrent execution out of the box. Instead of exposing low-level thread handles and lock primitives directly to application code, the runtime executes Actors across a shared POSIX worker thread pool and moves data across thread boundaries through thread-safe Channels.

1. M:N Worker Thread Pool

On first actor dispatch, runtime/vela_rt.h lazily creates a pool of detached POSIX threads (pthread_create) sized to the machine's online cores (up to 31, defaulting to 4). When main() exits, generated C calls vela__rt__sched_stop() to stop workers cleanly.

2. Isolated Actors

spawn MyActor(...) allocates isolated state paired with a 32-slot mailbox and returns an Actor[MyActor] handle. Different actors run in parallel on worker threads, while each actor drains its own mailbox one step at a time.

3. Thread-Safe Channels

Chan[T] (chan_new<T>(cap)) is a bounded FIFO ring buffer protected by a mutex and condition variables (not_empty / not_full), supporting dispatch, wait_and_receive, non-blocking receive, and close.

4. Multi-Channel select & Timeouts

Contextual select ... case ... otherwise ... fi blocks wait atomically on multiple receives (case msg <<- ch), closed detection (case none <<- ch), bounded sends (case [own] v ->> ch), and case after ms timeouts without lock-inversion deadlocks.

5. Compile-Time Boundary Safety

Linear own T move checking stops use-after-move and shared aliasing bugs before C is emitted, and regional values (@r) are rejected at channel and actor boundaries so memory never outlives its region.

6. Colorless Commitments (rush & Commitment[T])

Launch synchronous tasks concurrently with prefix rush task(...), gather or cancel via structured block scope exit, wait with <<- c or select, and splice worker allocations in O(1) into one destination caller region (Commitments).

For the full mechanics of message passing and isolated actor state, see Channels, Channel Lifecycle & Explicit Closing, Actors, Commitments, and Data Races & Alters.

🚧 What Vela Intentionally Does Not Have Yet

Concurrency features are often judged as much by what a language refuses to expose as by what it includes. Vela omits several primitives found in C, Rust, or Go — either because they conflict with Vela's core philosophy of safety through static structure, or because safely supporting them requires stronger static guarantees that are intentionally deferred.

1. No Raw Thread Spawning or Shared-Memory Locks Omitted by Design

Missing primitives: arbitrary thread.spawn(...), Mutex[T], RwLock[T], semaphores, atomics

You cannot launch an arbitrary task or lambda onto an unmanaged OS thread that captures shared references to stack locals or heap pointers, nor can you wrap mutable state in user-managed mutexes, read-write locks, or atomic compare-and-swap primitives.

Why we didn't implement this:

  • Locks trade data races for deadlocks and torn invariants: Manual mutexes make it easy to lock in inconsistent orders (deadlock), forget a lock on one code path (data race), or release a lock mid-update (half-broken state). Vela prefers isolating mutable state inside an Actor where concurrency is impossible inside message handlers.
  • Protecting closures and regions would bloat the type system: Allowing arbitrary closures to run concurrently with shared variables or pointers would require Rust-style Send / Sync marker traits and cross-thread borrow lifetimes on every signature and region. Keeping multithreading scoped to actor mailboxes and own T transfers eliminates shared aliasing without complicated lifetime annotations.

2. No Colored async / await Functions — Solved via Colorless rush Colorless Model Shipped

Omits: colored async task keywords and infectious Future[T] viral function splitting

Vela tasks remain ordinary colorless C11 functions: calling a task normally awaits by default with zero runtime overhead, while writing rush task_call(...) launches it on the concurrent scheduler returning a structured Commitment[T] handle.

Why we keep concurrency colorless:

  • Zero "function coloring": Standard utilities, collections, and lambdas never split into duplicated sync and async APIs.
  • Pay-for-what-you-use execution: Sequential calls compile to plain direct C11 calls without heap state frames, while rush handles support <<-, non-blocking .poll(), select racing, |> pipes, and inline => / .then() continuations.
  • Actors + Commitments together: Use spawn Actor(...) for long-lived encapsulated state daemons, and rush commitments for finite structured parallel tasks.

3. No Whole-Region Channel Transfer (Chan[own region]) Deferred for Channels • Shipped for Commitments

Missing on channels: dispatch(c, own work_region) • Shipped on rush: single-destination O(1) region splicing

For Chan[own T] and actor messages, only self-contained values and moved own T shapes can cross threads today (while rush tasks already splice one isolated worker region directly into a destination caller region on settlement).

Why we didn't implement this yet:

  • Preventing dangling pointers across threads: In Vela, a region lives on the stack of the block that opened it and frees all of its allocations at fi. Because an actor or receiving thread can easily outlive the sender's block, allowing @r pointers across threads would cause use-after-free bugs as soon as the sender leaves scope.
  • True $O(1)$ region transfer requires linear region ownership: To safely hand off a whole arena without copying, the compiler must track the region handle itself as linearly moved (own r) and prove that no leftover pointers into @r remain readable in the sender. Deferring Chan[own region] keeps memory safety airtight until linear region moves are built.

4. No Data-Parallel Loops (parallel each) Deferred

Missing primitives: fork-join loop execution across CPU cores, parallel map/reduce

each x in items always executes sequentially on the current thread. There is no syntax yet to automatically slice an array or collection across the worker pool and wait for all iterations to finish.

Why we didn't implement this yet:

  • Safe parallel bodies need stricter isolation checks: If two iterations of a loop run on different threads simultaneously, the compiler must prevent both iterations from writing to the same captured outer local (flex), altering the same slice element, or allocating concurrently into one unsynchronized region without locks.
  • Explicit worker Actors work today: CPU-heavy batches can already be split into chunks, dispatched to a small pool of worker Actors over channels, and gathered back through a reply channel without risking hidden races.

5. shared flex Fields Are Not Thread-Synchronized Design Caveat

Implementation detail: shape shared fields compile to plain C static globals

A shared flex field on a shape (such as Player.alive) compiles to a plain C global variable with no mutex or _Atomic wrapper.

Why it works this way:

  • Zero-cost reactive tracking for normal program flow: shared fields were built for program-wide counters, configuration, and reactive events (on init, on drop, on Player.alive) inside ordinary execution without paying atomic bus overhead on every read or event trigger.
  • Do not share mutable globals across concurrent Actors: Because C static variables are not protected against simultaneous multi-thread writes, concurrent coordination should always go through messages into a dedicated Actor that owns the counter or registry state instead of mutating shared flex fields from parallel actor handlers.

🧭 What to Use Instead Today

Even without those primitives, every common concurrent pattern maps directly onto Actors, Channels, and own T ownership transfers:

Common Primitive Elsewhere Vela Pattern Today Why It Works Safely
Mutex<State> / shared lock An actor holding State as private fields The actor processes one message step at a time, so state needs zero locks and cannot deadlock on lock ordering.
thread::spawn + join handle spawn Worker(...) + reply Chan[Result] Work runs on the M:N POSIX thread pool; the caller blocks on reply.wait_and_receive() when it needs the answer.
select across N channels select ... case x <<- ch ... otherwise ... fi Built-in multi-channel select waits atomically on receives, bounded sends, channel close (none <<- ch), and after ms timeouts.
async fn / Promise fan-out fixed c = rush fetch() → <<- c (plus select) Functions remain uncolored synchronous C11 while concurrent branches run asynchronously with automatic scope cancel/join.
Parallel batch loop N spawned worker actors + collector Chan[T], or sibling rush calls Each worker owns its chunk and isolated state or region, dispatching finished items cleanly back to caller.

Summary Example: Spawning work concurrently, keeping state race-free, and collecting a reply without locks or async keywords: 
actor Compute(factor: int)
    on Square(n: int, reply: Chan[int])
        reply.dispatch(n * n * factor)
    fi
fi

task main()
    fixed worker = spawn Compute(2)
    fixed done = chan_new<int>(1)

    worker.dispatch(Compute.Square(5, done))
    show("result: ", done.wait_and_receive())   ; result: 50

    worker.close()
    done.close()
fi
