Safety

What a compiled Vela program can't do wrong, what stops it with a message when it runs, and the concerns still open.

Language Regions Library Studio Comparison Future Future (Kimi) Safety May Waste Events Tricks Review

A Vela program has no null pointers, no memory used after it is freed, no value read before it is set, and no integer that wraps: the compiler refuses what it can tell is wrong, and the program stops with a message saying where for what only running it tells. This page lists those rules, and the concerns neither settles yet, to come back to. Most of the concerns are about places two names share. In Vela a value behaves as a copy: giving it to a task, binding it to another name, or putting it in a shape never lets two names change one thing. A few features give that up on purpose, since they are how two names share one place: a reference (flex&, bind&, fixed&), a pointer (^T), a shared field, a slice (a view of items in a region, so a copy of it sees the same items), and a File (a copy names the same open file). Nothing here changes the language.

How to read the marks. checked is refused by the compiler today; trapped stops the running program with a message saying where; warned builds, with a warning; by design is how the feature is meant to work, written down so it is known; open is a concern neither catches; later waits for a feature Vela doesn't have yet.

What is checked

Rule When What it prevents
A place a call changes is given once: two parameters that may change it (flex& or bind&), or one of those and a fixed& or a plain parameter, never name one place, and nor do &xs[i] and &xs[j], which may. A method that alters the value it is called on counts as changing it. Two slices count as two places even when they view the same items (see below). checked A task changing a value through one parameter while it reads it through another. See Parameters.
A large plain parameter, x: T, is read where the caller keeps it only when nothing can change it while the task runs: a local variable, or a field or an array item of one, with no later argument that calls a task. Anything else is copied first. checked A value given as a copy changing under the task. See Large values.
A reference names a place: never an item of a slice, which moves when the slice grows, a part taken of a value, a call's value, or a result. (The value an alters method is called on may be an item of a slice; see below.) checked A reference to memory that has moved, or to a value that is gone. See References.
A pointer always points to something (a missing one is a maybe ^T). A pointer, a slice, and text of a region (text@r) point into a region that outlives them: none is sent from a task, kept in a longer-lived variable, field, or shared field, or given to a parameter that could keep it, where its region would end first. checked Null pointers, and pointers into memory that was freed. See What regions guarantee and A region lives until its block closes.
A task value always holds a task (a missing one is a maybe), is called with the values its type takes, and its type says the regions of what it takes and sends, as a header does, so it holds nothing in any region and can go anywhere. A place or a region it takes is given at each call and checked there as at a named call: marked, given once where it changes, never an item of a slice, and a region the caller allocates in, where what it sends then lives. A task taking types never finds one of them in a region a task type takes, whose name is the type's own and says nothing of the caller's regions. A type group holding places gives them on as places, checked where the call giving them is, and never holds a region, which is named beside it. A method wrapping a method of every value alters the value exactly when the wrapped method does, so neither sees a value that never changes change under it. checked Calling through a null or stray function pointer, or with the wrong values; a place changed through one parameter while read through another; a value sent in a region that ends first. See Places and regions.
A plain lambda takes nothing from the code around it, and one that keeps what it uses, [@r], keeps copies in a block of r, which its type names, so neither reads a variable after the task that wrote it has ended, nor what it keeps after r is freed. It keeps no copy of a value of another region, and its copy of a slice never changes the slice's length. A variable it keeps as a place, [flex& count, @r], is one declared before r, in its block or one around it, so the lambda ends first. checked A closure reading a dead stack frame, or memory its region freed. See Lambdas and Lambdas that keep what they use.
A [flex @r] lambda, which changes what it keeps, is never copied: held in a flex variable, given as a place, or named by a reference. checked Two copies changing one hidden block, each seeing the other's changes as its own (a shared mutable closure). See Lambdas that keep what they use.
A tuple's items never change, neither assigned nor changed by a method that alters them, and hold nothing that changes through a pointer, a slice, or an array. checked A value that looks unchangeable changing through another name. See Tuples.
Nothing is read before it is set: every binding has a value, every field of a literal is given or falls back on one, a named result is set on every path that reads or sends it, and a task that sends a value sends one on every path. checked Reading memory that holds nothing yet. See Tasks, field defaults, and Named Results.
A maybe is opened before its value is used, and == compares it only with none. checked Using a value that isn't there, and mistaking an empty value for one that holds something. See Maybe and Errors and comparing a maybe.
The error of a T ~ E isn't dropped by a call written as a statement, or bound to _. checked A failure going unnoticed (one kept in a variable still can; see below). See Maybe and Errors.
A match covers every variant of its kind. checked A value no case handles. See Kinds.
A shared field holds nothing in a region, its first value is worked out before the program runs, and shared fields whose first values name each other in a circle are refused. checked A shared field pointing into freed memory, or read before it has a value. See Shared fields.
A decorator's and a wrapper's values, worked out where the program starts, hold nothing in a region and leave no task with <-. A wrapper's are worked out after those of every task they may call, a call of a task held as a value counting as a call of every task named as one in what can run there; a value that may call its own task, and values whose tasks call each other in a circle, are refused. checked A wrapper reading its value before it is set, which for a task value would call through a null pointer, and a decorator's value skipping the decorators after it. See Decorators.
Code nests at most 100 levels deep, and a type given to a generic is at most 24 types deep and 1000 parts. checked The compiler running out of stack or memory on a program instead of saying what is wrong. See Current Limits.
An int never wraps: overflow, and division or remainder by zero, stop the program; written with numbers alone, they are refused when compiling. A unit and a char never wrap either: a result outside 0 to 255 stops the program, and unit(n) and char(n) do the same for a number that doesn't fit. trapped The undefined behavior C has for them, and a byte that quietly wraps around. See Numbers, Units, and Chars.
int(x) of a float that is nan or too large for an int stops the program. trapped A number that means nothing. See Conversions.
Every index and range of an array, a slice, or text is checked (a constant one when compiling), a count below zero stops the program, and a part of text can't cut through a character. m[k] on a key a map doesn't hold stops the program too, and m[#k] gives none. xs[#i] and t.at(i) give none out of range instead, and a byte of text, t[i], is never a place, so text still never changes. trapped Reading or writing outside a value, and text that isn't UTF-8. See Arrays, Slices, Safe index, and parts of text.
add and del check their index, and del() on an empty slice stops the program. trapped Changing a slice outside its items. See Adding and taking out items.
A File whose region closed it fails with NotOpen from every method, never reaching a file opened since. trapped Writing to a file the program didn't mean. See Regions and copies.
Running out of memory prints vela: out of memory and stops the program. trapped Going on with memory that was never given. See What regions guarantee.

Concerns: places two names share

A reference parameter changed through a pointer open

The rule that a call gives a place it changes once compares the places written at the call. A pointer reaches a place the call doesn't write, so a task given &p^ as a fixed& and p itself can change what the reference reads: 

shape Box
    v: int
fi

task f(fixed& x: Box, flex p: ^Box@r)
    p^.v = 99
    show(x.v)                      ; 99: x is where p points
fi

task main()
    region r
    flex p = new Box(Box { v: 1 }) at r
    f(&p^, p)
fi

Two pointers that hold one address slip past the same rule, since the compiler can't tell they do: 

task two(flex& a: int, flex& b: int)
    a = 1
    b = 2
    show(a, " ", b)                ; 2 2
fi

flex q = p
two(&p^.v, &q^.v)

The value an alters method is called on is given the same way, so p^.set(p), where set writes q^.n = 2 through the pointer it is given, reads .n as 2.

Why it is hard
Whether two pointers hold one address is known only when the program runs. A rule written for the compiler has to be cautious: it would refuse or warn about every call that gives a place behind a pointer together with another pointer of that type, or into the same region, most of which are fine.
Ways it could go
A warning where a call gives &p^ (or a part of it) to a reference parameter and also gives a pointer of the same type, or a place behind another pointer of it. Or, in a build for finding mistakes, a check that the two addresses differ when the call starts, trapping when they don't.

A reference to a shared field the task changes open

A shared field that changes (shared flex) is one place for the whole program, and every task can reach it by name. A task given it as a fixed& reads it where it is, so its own change to the field shows through the reference: 

shape Tally
    n: int

    alters grow(flex m: [int: Tally]@r)
        each i in 1..9
            m[i] = Tally { n: 0 }      ; the ninth key moves the table
        fi
        .n = 9                         ; written where the value was
    fi
fi

task main()
    region r
    flex m = [0: Tally { n: 1 }] at r
    m[0].grow(m)
    show(m[0].n)                       ; 1, not 9
    each k, v in m                  ; the entries there when the loop started
        m.del(k)                       ; taking out and adding may pack them in place
        m[k + 100] = v
    fi
fi

A plain parameter given a shared field is copied first, so it never sees the change. A method called on a shared field is the same: in Tally.last.bump(), a bump that sets Tally.last to a new value reads the new one's fields through .this.

Why it is hard
The change may come from a task the body calls, or one that task calls, so the compiler would have to know every shared field each task can change.
Ways it could go
The checker could learn, for each task, which shared fields it or the tasks it calls may change, and refuse a call that gives one of them to a reference parameter, as it refuses a place given twice. A shared read field, which only its shape's methods change, narrows where to look.

A reference reads the place as it is now by design

fixed& y = &x can't change x, but it reads x as it is each time it is read, and x may change between two reads: 

flex x = 1
fixed& y = &x
show(y)                            ; 1
x = 2
show(y)                            ; 2

That is what a reference is for, and a fixed& parameter is the same inside the task. What the word promises is that the reader doesn't change the place, not that nothing does. A reader who needs the value to stay as it was keeps a copy: fixed v = y, or a fixed x parameter.

A place a lambda keeps, given beside it open

A call never gives one place twice where one of them changes it (see Places and regions). A lambda that keeps a variable as a place, [flex& count, @s], is a second name for it that the call doesn't see, so it can be given beside the place itself: 

task f(flex& x: int, g: [@s]() -> nothing)
    g()                            ; changes x, through count
    show(x)                        ; 5
fi

task main()
    flex count = 1
    region s
    fixed g = [flex& count, @s]() -> nothing count = 5 fi
    f(&count, g)
fi

No memory is misused: the variable outlives the lambda, and no reference names an item of a slice that could move. But x changes under f while f holds it, as a reference's place may (above). A call could refuse a lambda that keeps a place it is also given, where the compiler sees which places a lambda keeps; one handed on through a variable or a parameter hides it.

Where a plain parameter is warned

A plain parameter, x: T, is a copy, or for a value larger than 64 bytes, the caller's own place. Its value is the same either way, but what reads where the value is sees the difference: &x, and == on a shape, an array, or a tuple, which compare by where the value is. Such a read is a warning that says which way the compiler went; fixed x and fixed& x say which is meant.

A method on an item of a slice that grows open

An alters method called on an item of a slice changes the item where it is. If the method makes the slice grow, through a pointer to what holds it, the items move to a new block, and the method's own change goes to the old one: 

shape Bag
    items: [Item]
fi

shape Item
    n: int

    alters poke(flex b: ^Bag@r, r: region)
        b^.items.add(Item { n: 2 })
        b^.items.add(Item { n: 3 })
        .n = 9                         ; written to the block the items left
    fi
fi

task main()
    region r
    flex b = new Bag(Bag { items: new [Item]([Item { n: 1 }]) at r }) at r
    b^.items[0].poke(b, r)
    show(b^.items[0].n, " ", b^.items.len)   ; 1 3, not 9 3
fi

No memory is misused, since the old block stays in the region until it is freed, but the change is lost. The same item given to a task as &b^.items[0] is refused, since a reference never names an item of a slice; the value a method is called on isn't held to that rule.

Why it is hard
The slice grows through a pointer, which the rule that a place is given once can't follow, and refusing every alters call on an item of a slice would refuse the common case, a method that touches only its own item.
Ways it could go
Refuse an alters call on an item of a slice when the call also gives a pointer or region through which that slice could be reached. Or have the method work on a copy of the item and write it back to its index when the call ends. Or read the item through the slice and its index at each use of .this.

A value in a map, while the map changes open

A map's values are in its table, which moves when the map grows and is packed again in place when most of its keys were taken out. So a reference never names a value in a map (flex& v = &m[k] is refused, as for a slice's item), and a slice never points into one (m[k][0..2] is refused for an array value, whose part would come to point at another key's value). Two uses aren't held to that rule, and see the table as it was: 

shape Tally
    n: int

    alters grow(flex m: [text: Tally]@r)
        m["b"] = Tally { n: 0 }          ; may move the table
        .n = 9                         ; written where the value was
    fi
fi

task main()
    region r
    flex m = ["a": Tally { n: 1 }] at r
    m["a"].grow(m)
    each k, v in m                  ; the entries there when the loop started
        m.del(k)                       ; taking out and adding may pack them in place
        m[k + "!" at r] = v
    fi
fi

The first is the slice case above (a method on an item of a slice that grows): the method's change can be lost. The second is a loop through a map that takes keys out and adds others: when the table is packed in place during the loop, an entry can move under it, so it may see one twice or skip one. No memory is misused either way, since a table stays in its region until the region ends.

Why it is hard
As for a slice, the map changes through a name the rule that a place is given once can't follow. And a loop that sees each entry once while the map changes needs the table to wait until it ends.
Ways it could go
The ways listed for a slice's item. For the loop, packing a table only by growing it into new room while a loop goes through it, or refusing m[k] = v and m.del(k) on the map a loop goes through, as long as it can be told apart.

Copies of a map are one map by design

A map value is a handle to its table, so every copy of it, a variable, a field, an argument, names the same map, and a key one of them adds is there for all: 

flex a = ["x": 1] at r
flex b = a
b["y"] = 2
show(a.len, " ", a == b)                 ; 2 true
flex c = a.copy() at r                ; a map of its own

This is what Go does, and what copying a slice does for its items. Copying every key and value at each assignment would hide a cost that grows with the map; .copy() says when one is wanted, and == says whether two names are the same map.

A copy of a slice shares its items by design

A slice is a view of items in a region, a twofold value, so a copy of it, a fixed of it, or a parameter given it, sees the same items, and a write through one is seen through all. Nothing is written through a fixed name or a plain parameter, at any depth, but a flex one that shares the items may write them, and the fixed one sees the change: 

task change(flex xs: [int]@r)
    xs[0] = 99
fi

task main()
    region r
    flex xs = new [int]([1, 2, 3]) at r
    fixed seen = xs
    change(xs)
    show(seen[0])                      ; 99
fi

For the same reason, keeping a copy in a variable doesn't separate a slice given twice to a call that changes it: flex ys = xs and then f(&xs, &ys) gives two views of the same items. xs.copy() at r makes items of its own. A flex copy that adds or takes out items stays linked or not by where its items happen to be: an add that needs more room copies the items to a block of its own, after which writes are no longer seen, while one that finds room, and a del, keep the two on the same items (see Copies and parts), and the compiler warns where a task leans on it (see below). A bind slice never adds or takes out items, so its copies stay on the same items, and a task taking one as bind goes where a task type says flex.

Ways it could go
The given-twice message could suggest .copy() at r when the place is a slice, and two slices coming from the same variable could count as one place.

A [bind @r] lambda is never copied later

A [bind @r] lambda changes the contents of the copies it keeps, and every copy of the lambda's value would name the same kept copies, so a change through one would be seen through all. For now it is held as a [flex @r] lambda is: in a flex variable, called, or given on as a place, never copied (the author's decision, 2026-10-12). A lambda that changes only the items of a slice it keeps a copy of changes nothing every copy wouldn't share anyway, so the rule refuses some programs that would be safe.

Ways it could go
A [bind @r] lambda whose copies are all twofold, changing only what they name, could be copied freely, and only one changing a whole copy's contents, a shape's field say, held.

A view after its slice changes by design warned

A part of a slice, xs[a..b], is a view of the items where they were when it was taken. After del the items move under it, and it may read one past the slice's new length; after a growth that moves the items, it keeps viewing the old block: 

region r
flex xs = new [int]([1, 2, 3, 4]) at r
fixed v = xs[2..4]
xs.del(0)
show(v[0], " ", v[1])                  ; 4 4: the items moved under v

each v in xs is the same: it goes through the items where they were when it started, as many as there were, so an item deleted during the loop is still read. each v in &xs goes through xs as it is at each pass instead (see Arrays).

The compiler warns where a task does this: a copy or part used after a del on the slice it was made of, an item written through either after an add, and an add or del on a flex slice parameter, once in each task for each case (--repeat-warnings shows every place; see Warnings).

Ways it could go
The warning follows copies made in one task by a binding or an assignment; it could follow slices in fields, given to calls, or kept by lambdas, and a loop's next pass.

A copy of a File names the same open file by design

A File is a value, and its open file belongs to the region it was opened in, so a copy names the same open file. Closing one closes it for both, and the other finds out only when a method of its own runs: 

include std/files {File, FileMode}

task main()
    region r
    flex a = File { path: "fa.txt" }
    a.open(FileMode.Write) at r { failure e
        show("no")
    }
    fixed b = a
    a.close() { failure e
        show("no")
    }
    b.write("x\n") { failure e
        show("b: ", e)                 ; b: NotOpen
    }
    show(b)                            ; fa.txt (open): what b last saw
fi

Each open file has a number that changes when it closes, so no copy ever reaches a file opened since (see Regions and copies). Only the state a copy shows is behind.

Threads later

Vela has no threads, so every change above happens at a point the program's own order decides. Once two tasks can run at once, each reference, pointer, and shared field is memory two threads may change together, and the rule that a place is given once would have to hold between threads as well as within one call. Whatever Vela adds for running work at once (see Events for one idea) will need its own answer here before it is built.

Concerns: running

An error kept in a variable that is never read open

A call written as a statement can't drop the error a T ~ E may hold, and neither can binding it to _. Binding it to a name that is never read does: 

task main()
    fixed x = int("oops")
    show("went on")                    ; went on: nothing read the ParseError
fi

So does a flex given a new value before the old one was read, and one of several results bound by name, fixed a, b = int("7"), int("x").

Why it is hard
Telling that a value is never read needs to follow every path through the block: a match, an is, or a plan B on any of them reads it.
Ways it could go
An error for a T ~ E variable that no path reads before it ends or is replaced. Or a warning for every variable never read, which would catch this and more.

Running out of stack open

A task that calls itself without end, or an array too large for the stack, stops the program with the system's own crash and no vela: message: 

task f(n: int) -> int
    <- f(n + 1) + 1
fi

task main()
    show(f(0))                         ; Segmentation fault, exit 139
fi

An array held by value lives on the C stack, so flex big = [1#20000000] crashes the same way, as does a new of a very large array, whose value is made on the stack before it is copied.

Why it is hard
How deep a program calls is known only when it runs, and the stack's size is the system's. The checker allows an array of up to 1 TiB.
Ways it could go
A limit on the size of an array held by value, pointing to a slice for more. new filling the array where it goes, rather than copying one made on the stack. A handler for the crash that prints vela: out of stack. A count of the call depth in a build for finding mistakes.

A value made for one line lasts as long as its region open

A region frees its memory all at once, when it ends. A value made in it only to be shown or passed, and never kept, holds its memory until then too: 

task main()
    region r
    each i in 0..1000000
        show([i, i + 1, ...] at r)       ; a million slices in r, freed when main ends
    fi
fi

Nothing is read after it is freed, so this is memory held longer than needed, never memory misused. A region made inside the loop (region pass default) frees each pass's values as it ends, which is how to write this today.

Why it is hard
An arena frees everything it holds at once, not one value. And a value given to a task that takes [int]@r may be kept by the task in something else in r, so only the compiler's own uses (show, a comparison) are known to keep nothing.
Ways it could go
A value only shown or compared going in a hidden region freed when its line ends, as the text show builds for a value's own str already does. Giving the space back when the value is the last thing the region made, by moving the arena's end back. A warning for a value made in a loop into a region the loop doesn't declare.

Which of two stops comes first by design

Calls, plan Bs, slice changes, and reading input run left to right, but plain operators don't promise an order, so when two parts of one expression would each stop the program, which one stops it isn't defined: 

flex xs = [1, 2]
flex i = 5
flex n = 9223372036854775807
show(xs[i] + (n + 1))                  ; vela: integer overflow at 5:21 in task 'main', not the index

Either way the program stops, with a message saying where. Ordering every part that may stop the program would take the C compiler's freedom to arrange arithmetic (see Current Limits).

nan compares with nothing by design

A float that is nan (as 0.0 / 0.0 gives) is neither equal, similar, smaller, nor larger than anything, itself included, as in C and every language following IEEE 754: 

fixed nan = 0.0 / 0.0
show(nan == nan, " ", nan ~= nan, " ", nan < 1.0, " ", nan >= 1.0)   ; false false false false

So ~= isn't always true of a value and itself, and the largest of a list holding nan depends on its order. int(nan) stops the program.
